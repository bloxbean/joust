# ADR-0014: MerkleMap claims v2 — namespaced claim keys, MerkleMaps with native assets

**Status:** Accepted, implemented
**Date:** 2026-11-07
**Builds on:** ADR-0002 (MerkleMaps, the map verifier), ADR-0007 (native assets), ADR-0012 (owned MerkleMaps).
**Stack:** #1–#15, then this.

## 1. Context

Two limits remained after ADR-0012:
- **Claim keys were not namespaced.** A map claim was found by `(owner, field)`, where `owner` is the input whose map
  it is: the instance's or object's own input, or the creation's seed. Two contracts creating from the same seed in
  one transaction, or using an input both as a seed and as their own, would look up the same claim. Each validator
  still checked that claim against its own old root and writes, so this could only make a transaction fail (liveness),
  never move funds.
- **MerkleMaps could not be combined with native assets**, neither in the state (ADR-0007) nor in owned records
  (ADR-0012). The asset-aware generated code and runtime paths had no map handling.

## 2. Decision

### D1. Claims keyed by `(policy, owner, field)`

- `MapClaim` gains `policy`, the script hash of the contract whose map it is: `MapClaim(policy, owner, field, oldRoot,
  reads, writes, newRoot)`.
- `MapWitnesses.claimFor(claims, policy, owner, field)` matches all three. Every generated `openAll`/`commitAll` and
  creation passes the validator's own policy, so a claim made for one contract can never be read by another.
- **Within one contract the key is almost unique:**
  - an instance's maps and owned objects never coexist (ADR-0003 r2);
  - a transaction carries one mint redeemer per policy, so two creations of one contract never share a transaction;
  - every spend is keyed by its own input.

- **Creations use fields -1, -2, ….** A creation's seed may be an input of the same contract that is spent in the same
  transaction, and a spend's claims use fields 0, 1, …, so the two keys never meet (Codex review: before this, such a
  transaction could not be satisfied). `MerkleSupport.prepareCreation` builds a creation's claims.
- **`claimFor` takes the first claim with the key.** Duplicates are verified by the map verifier and otherwise
  ignored; their cost falls on the submitter.
- The map verifier is unchanged in logic (it verifies every claim's proofs), but its redeemer's shape changed, so its
  hash changes with every contract embedding it.
- `MerkleSupport.prepare` takes the policy.

### D2. MerkleMaps with native assets

- **The generated asset-aware transition** already opened and committed maps (ADR-0012 changed both transition
  generators). The asset-aware owned creation now commits the creation's writes from empty roots, as the plain one
  does. Asset-aware instance creation already did. The two refusals in the reader are gone.
- **The runtime's asset paths** (deploy, instance calls, object creation and object calls) now:
  - run the method against the mirror;
  - prepare the claims (with the policy);
  - replay the method on the witnessed read set;
  - attach the map verifier alongside the output verifier.

  The value equation is unchanged: maps live in the datum, assets in the value.

- **Purposes.** Owned maps were also refused in contracts with a `@Withdraw` handler, because that handler makes the
  generated code asset-aware. They are now allowed there too.

## 3. Consequences

- Every MerkleMap contract's script and the map verifier's hash change, through the new claim shape.
- **Destroys.** A destroy of a map holder still opens its maps, so it needs a verifier withdrawal and a claim even
  when it reads nothing. That costs budget; the mirror is not needed (ADR-0012 r4). The processor warns that an
  `@OwnedDestroy` discards the object's maps, as it already did for `@Destroy`.
- **Script size.** A contract with maps and assets carries both sets of helpers. The examples are 14.3 KB (an
  instance) and 14.4 KB (owned objects), under the 16 KB reference-script limit but close to it.

## 4. Tests

- **Example `locker`:**
  - `Locker` holds a native token for many users, with balances in a MerkleMap;
  - `Safes` has owned safes, each holding tokens and a MerkleMap written at creation.
- **Harness:**
  - creation;
  - lock (accepted tokens, a map write), with the attack suite;
  - unlock (a send, a map write);
  - the accepted tokens missing from the state output;
  - a forged root.
- **DevKit:**
  - lock, unlock, an over-unlock refused, close, with every token back;
  - a safe opened with tokens and a note, noted again, emptied, with every token back.
- The existing map tests (token, dsl points, armory) run with namespaced claims; one armory test forges a claim keyed to
  another input and is refused.

## 5. Test infrastructure

DevKit's admin faucet can run dry on a long-lived devnet. `DevKit.topUp` now falls back to DevKit's default-mnemonic
accounts, funded in genesis.

## 6. Review

A security reviewer and Codex reviewed the implementation.

**Security reviewer:** no Critical, High or Medium findings:
- claims are checked by proof against the validator's own root;
- the value is settled apart from the map;
- destroys cannot leave tokens behind.

**Codex** found two Mediums:
- **A creation seeded by a spent state input of the same contract collided with that spend's claim.** Creations now
  use negative fields (D1).
- **The off-chain replay check compared only the next state and the payouts.** It now compares every effect: sends,
  mint, accepted, events and deposits.

Both are tested in `LockerTest`.

The security reviewer's Lows are resolved above:
- the uniqueness argument corrected;
- the first match documented;
- the warning for `@OwnedDestroy`;
- the change for `@Withdraw` contracts;
- the cost of destroys;
- the size margins.
