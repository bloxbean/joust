Status and roadmap

Status: experimental, a research and learning project

JOUST is an experimental project created mainly for research and exploration of state-oriented smart contracts on Cardano. It is AI-generated, with human-assisted design, testing and verification. Do not use it in production. Expect rough edges, incomplete features and bugs.

JOUST is pre-release. Every feature on this page is implemented, tested at three levels (the method on the JVM, the compiled validator in a harness with the attack suite, and end to end on Yaci DevKit) and recorded in an architecture decision. Nothing has a stable release yet: APIs can still change.

What is published

Section titled “What is published”

Every release is on the releases page, with its version and notes. A release brings the JuLC and cardano-client-lib versions it was built with (gradle/libs.versions.toml at its tag).

Where What
BloxBean release repository, https://repo.bloxbean.org/maven/releases JOUST’s Maven modules (below), the Gradle plugin org.julclang.joust, and the JuLC releases they need. See Quick start: Java & Gradle
Maven Central Nothing yet: each release stages a deployment, which a maintainer publishes by hand
npmjs.org @julclang/joust, @julclang/joust-runtime, @julclang/state-client and create-joust, with provenance: npm create joust@latest. See Quick start: JavaScript & TypeScript
GitHub releases The native joust (macOS arm64, Linux x86_64 and arm64) with SHA-256 sums and provenance; the Homebrew formula bloxbean/tap/joust follows it. Releases that include the editor assets list the VS Code extension (vscode-joust-<ext>.vsix) and the tree-sitter grammar (tree-sitter-jsc-<version>.tar.gz) among their assets (Editors)
Visual Studio Marketplace The listing is julc.vscode-joust: a release that includes the extension publishes the same attested .vsix there (Editors)

Features on main come with the next release.

JavaScript and npm (ADR-0015)

Section titled “JavaScript and npm (ADR-0015)”

ADR-0015 ships JOUST to JavaScript developers as two prebuilt Wasm engines inside npm packages: a toolchain that compiles .jsc and .java contracts in Node, and a runtime that prepares transactions in Node and in the browser. Its milestones M0 to M5 are implemented; their evidence is recorded in ADR-0015 §13.

Milestone What it delivered
M0 The runtime builds QuickTx Tx (never ScriptTx), and fixtures recorded on DevKit (fixtures/m0) became the oracle for everything after
S0 to S2b (gates) The runtime in a Web Image; the toolchain engine compiling Counter, Bank and .jsc in Node; transition programs evaluated in the engine; read discovery for MerkleMaps
M1 Description v2 with call recipes; one description-driven runtime core shared by the JVM and the engine; deterministic replay from a call request and a snapshot
M2 The packages @julclang/joust-runtime, @julclang/joust and create-joust, beside @julclang/state-client; publishing to a local registry; the no-Java acceptance run
M3 Feature parity through npm: every example’s DevKit flow passes through the npm path, byte-identical to the JVM on the recorded fixtures (fixtures/m3)
M4 joust deploy (preview through Blockfrost), joust dev, joust serve, the Vite plugin (@julclang/joust/vite), the engine in a page worker with SRI, pluggable chain providers (Blockfrost and Yaci Store, Ogmios), cardano-js-sdk instead of CSL, the Cardano Foundation’s wallet connector, and MerkleMap mirrors
M5 The release pipeline: both Wasm engines built with GraalVM in CI, and the four packages published to npmjs.org through npm trusted publishing, with provenance

M4’s exit was a counter dApp on the preview testnet, made with npm create joust from the local registry, prepared in the page’s worker, verified by the page and signed by a browser wallet (ADR-0015 §13.11).

Experimental

Section titled “Experimental”
  • Option F is a spike, not a product. ADR-0006 §3 lists what is not built: data availability at scale, deposits and exits, large states, liveness and censorship resistance, and generating the L2 program from a contract.

Known limits

Section titled “Known limits”
  • Not through npm yet: @Votes and @Propose calls (the JVM client has no calls for them either); @Init/@OwnedInit inside compositions; quorum and governors on owned objects; batches over maps or assets (ADR-0015 §13.8). No example needs them.
  • Batches are memory-bound at about 8 intents (ADR-0004 §6).
  • Script size: a transaction is at most 16 KB, so a script must stay well below it. Heavy contracts (three owned types with moves and maps) have exceeded it. See Fees and script size.
  • Mirrors over Ogmios alone cannot be rebuilt from the chain: Ogmios serves no history, so it needs Kupo or an indexer beside it (ADR-0015 §13.12).
  • DevKit pays no rewards within a test (rewards take epochs), so staking flows on DevKit collect a zero balance.
  • Keyed objects (ADR-0016) are refused in contracts with native assets, MerkleMaps, @Batched actions or migration (keyed types in asset-aware contracts are ADR-0016’s M4, a follow-up), and a page runs keyed calls one at a time and never in a composition. See Keyed objects.

What is next

Section titled “What is next”

Designs

Section titled “Designs”
  • Programmable tokens (CIP-113), ADR-0019: issuers, holders, and contracts paid in such tokens. Proposed, not implemented.
  • Keyed types in asset-aware contracts, ADR-0016’s M4: a follow-up ADR.
  • .jsc as the recommended language for JavaScript developers: ADR-0018’s recommendation gate waits for an independent security review of the lowering, the generated checks and the bindings. Until then .jsc is a language preview.

Follow-ups found on preview

Section titled “Follow-ups found on preview”

The maintainer’s preview run with a real wallet (ADR-0015 §13.11) found two fee follow-ups:

  • Issue #33: the fee overpays by one vkey witness (4,563 lovelace per call in that run).
  • Issue #34: the reference-script fee was 29 % of a call’s fee. Script size is now the largest part of a simple call’s cost (ADR-0008).

Upstream

Section titled “Upstream”
  • JuLC. JOUST needs @StateContract as a fixed alias of @OnchainLibrary with a robust library-source scan (bloxbean/julc#311), and the scoped attribution query the npm toolchain uses (bloxbean/julc#313). Both are in the JuLC release JOUST pins (gradle/libs.versions.toml), from the BloxBean release repository. JuLC’s CIP-57 blueprint still lacks vocabulary for vote and propose handlers (hence -Ajulc.blueprint=false).
  • cardano-client-lib. ADR-0001 §12 and ADR-0015 list: an option to keep an inline datum’s map order instead of always writing canonical CBOR; documenting that QuickTx takes the fee from an output at the fee payer’s address; duplicate keys in MapPlutusData; and keeping required signers in a stable order.

Later

Section titled “Later”

ADR-0015 §11 named work outside its scope: editor support (since built, ADR-0021), making .jsc the default language for JavaScript developers (above), and a Kotlin front end (queued). ADR-0015 Q2 keeps open an export of a built call as a CCL TxPlan, and JOUST as a QuickTx extension once CCL’s prerequisites are met.

How JOUST is published

Section titled “How JOUST is published”

The process is in docs/release-ops.md.

Piece What it does
.github/workflows/build.yml CI on pushes to main and release/** and on pull requests: ./gradlew build -PnoDevnet (JVM and harness tests, the JavaScript client’s tests), the DevKit tests in shards (-PdevnetOnly) on Yaci DevKit, and the publication scope check
.github/workflows/tag-release.yml Runs when version in gradle.properties changes on main (releases come from main only): after a release owner approves, it tags v<version>
.github/workflows/release.yml Runs on a v* tag: builds and signs the Maven artifacts once, publishes them to https://repo.bloxbean.org/maven/releases, stages a Maven Central deployment that a maintainer publishes by hand, and builds the Wasm engines and publishes the npm packages (or only checks them, with npm_publish=false)
.github/workflows/editor-assets.yml, publish-vscode.yml Called by the release: the VS Code extension and the tree-sitter package, built from the tag, attested and attached to the GitHub release; then that .vsix published to the Visual Studio Marketplace
.github/workflows/bloxbean-snapshot.yml Manual, from main only. Publishes a development snapshot of a commit whose build.yml run passed to https://repo.bloxbean.org/maven/snapshots (versions <version>-<sha7>-SNAPSHOT)
.github/workflows/docs.yml This site: builds it (with its link and version checks) on pull requests that change it; from main, pushes it to the gh-pages branch, which GitHub Pages serves once its deployment is approved

The published Maven modules are julc-state-api (with its onchain jar, the on-chain sources for a consumer’s annotation processor path), julc-state-dsl, julc-state-processor, julc-state-runtime, julc-state-server, julc-state-testkit and julc-state-verifier, and the Gradle plugin julc-state-gradle-plugin (org.julclang.joust). The toolchain and the runtime engine ship only inside the npm packages.

Before a release, the npm packages can be tried from a local registry: ./gradlew npmPublishLocal -PgraalvmHome=... builds both engines and runs js/publish-local.sh (the packages’ in-repository -snapshot versions), and ./gradlew npmAcceptance -PgraalvmHome=... runs the npm-only developer flow on DevKit in a shell where no Java can be found.
