Native assets, mints and sends

By default a JOUST state UTxO holds lovelace and its own thread token, and an action pays lovelace to key hashes. That covers counters and vaults, but not a DEX that holds a token reserve, a marketplace that holds the NFT it sells, or a treasury that pays a royalty script with a datum. This page covers the four pieces that make those possible (ADR-0007):

  • Funds: the native assets a method sees (received, held) and the contract’s own policy id;
  • accepted: exactly which assets a method takes in;
  • mint: user tokens minted or burned by the contract’s own policy;
  • Send: an output to any address, key or script, with any datum and any value.

A native asset (or token) on Cardano is identified by a policy id (the hash of the script that controls minting) and a token name; a value is lovelace plus any number of these. See the glossary.

A constant-product AMM

Section titled “A constant-product AMM”

The dex example is one ADA/token pool. Its reserves are what its UTxO holds, so state and funds can never drift apart: lovelace above the deposit (ctx.balance()) and the token (funds.held()).

addLiquidity takes ADA and tokens in (accepted), mints LP tokens under the contract’s own policy (mint), and sends them to the provider (sends), all in one result record. The DEX tutorial walks through the whole contract.

Funds

Section titled “Funds”

Declare Funds as the last parameter, after Ctx if there is one. The client fills it in; the validator checks every field.

Field What it holds
policy This contract’s policy id (its script hash). Name your own tokens with it
self The token name of what the method acts on: the instance id, or the object id in an owned method
received Native assets the caller adds in this call. No lovelace entry (that is ctx.received()); positive amounts; empty unless the method is @Payable
held Native assets the UTxO holds before the call, without lovelace and without its own thread token; empty when creating
deposits Deposits from other contracts in this transaction, for a @Receives action only (see Deposits)

Only received travels in the redeemer. The validator computes policy, self and held from the transaction.

The result record

Section titled “The result record”

A method that does more than return the state returns a record whose components are recognised by name and type:

Component Type Meaning
state the state or owned record The next state. Required for actions and inits; forbidden for destroys
payouts JulcList<Payout> Lovelace to key hashes, tagged with this input (cheapest)
sends JulcList<Send> Outputs to any address with any datum and value
mint Value User tokens this contract’s policy mints (positive) or burns (negative)
accepted Value Exactly the native assets this call takes in

deposits and events are covered in Deposits and Params, invariants and events. A destroy may still return a bare JulcList<Payout>. @Init and @OwnedInit may take Funds and return accepted, but cannot mint, send or pay out.

Assets: values in contract code

Section titled “Assets: values in contract code”

Value arithmetic goes through Assets. It has the same API on the JVM and on chain: the JVM body works on maps, the on-chain body (julc-state-api/src/onchain/java) uses the Plutus V3 native value builtins. Every value it returns is canonical (sorted, no zero quantities), as the ledger requires.

Method Returns
Assets.none() The empty value
Assets.of(policy, name, quantity) quantity of one asset (empty if zero)
Assets.lovelace(quantity) Lovelace as a value
Assets.add(a, b), Assets.subtract(a, b) Entry-wise sum or difference (negative entries stay)
Assets.quantity(v, policy, name) One asset’s quantity, zero if absent
Assets.lovelaceOf(v) The lovelace in v
Assets.withoutLovelace(v) v without its lovelace
Assets.isEmpty(v) Whether v holds nothing
Assets.covers(a, b) Whether a holds at least b of every entry (both non-negative)

The JVM also has Assets.check(v, what), which the runtime and the harness run on every value a method returns, so a JVM test never passes on a value the chain would reject.

accepted: no unwanted tokens

Section titled “accepted: no unwanted tokens”

A @Payable method with Funds must return accepted, and the validator requires funds.received == accepted exactly. This stops a caller pushing junk tokens into your UTxO, which could make it unspendable through its min-ADA or the size of its value. A method that takes anything says so by returning funds.received().

@Payable governs both ctx.received() and funds.received(): without it, both must be zero.

mint: tokens of your own policy

Section titled “mint: tokens of your own policy”

The contract’s policy mints its lifecycle tokens (instances, objects, intents) and can also mint user tokens. The token name decides which is which:

  • reserved: 32 bytes (an instance), or 29 bytes starting with 0x4F (an object) or 0x49 (an intent);
  • user: any other name, 0 to 31 bytes.

Return mint from an action: positive amounts mint, negative burn. The dex burns LP tokens on the way out:

The caller sends the LP tokens in (accepted = lpTokens) and the method burns them (mint = −lpTokens).

How minting is checked. The transaction’s mint redeemer for the policy is ByAction(by), naming the state input whose method mints. The minting policy checks that the input at by sits at the state address, holds a reserved token and is spent with a method that can mint. That method’s validator checks the mint redeemer names its own input, that every declared entry has a user-kind name under the own policy and a non-zero amount, and that the whole mint under the policy equals the declared mint exactly (I28). One transition per transaction owns the policy’s mint. A method whose mint is empty needs no mint redeemer, and requires that nothing is minted under the policy.

Name per-instance tokens after the instance, as the dex does with blake2b_224(funds.self()): one name per pool, so one pool’s LP tokens can never redeem another’s reserves.

Send: outputs to anyone

Section titled “Send: outputs to anyone”

Send(Address to, Value value, OutputDatum datum) asks for an output at any address, key or script, with any datum (none, a hash or inline) and at least value. Build lists with Sends.none(), Sends.of(to, value, datum) and Sends.add(sends, to, value, datum), and datums with Datum.inline(data) or Datum.none(). Payout stays the cheap form for lovelace to a key.

The market’s buy pays the seller with a payout, delivers the NFT with a send, and pays a royalty to a script address with an inline datum:

Build datums with Builtins, not casts

(PlutusData) (Object) record works on chain but throws on the JVM. Build a datum with Builtins.constrData, bData, iData and mkCons, which run on both: a record R(a, b) is constrData(0, mkCons(a, mkCons(b, mkNilData()))).

The output verifier

Section titled “The output verifier”

A send cannot be tagged with the sender’s input, because its datum belongs to the recipient. Without a tag, one output could satisfy two obligations: two instances owing Bob 10 ADA with the same datum would both accept a single 10 ADA output (double satisfaction). So sends are claimed in a transaction-wide registry, kept by a shared withdraw-zero script, OutputVerifier in julc-state-verifier (ADR-0007 D5):

  • The verifier runs as a withdrawal; its redeemer lists OutputClaim(output, by) with output indices strictly increasing and in range. So each output is claimed at most once.
  • Each transition with sends reads the registry from the transaction’s redeemers, takes its own claims (those with by equal to its input), and requires exactly one claim per send, in order.
  • A claimed output must sit at send.to, carry exactly send.datum, have no reference script and hold at least send.value. It may not sit at the payment credential of any input the transaction spends, so a continuing output (of this or any script) never passes as a send. And its inline datum may not equal any input’s reference or IntentRefund of one, so it can never also count as a JOUST payout or refund.

The runtime publishes and registers the verifier once per network, adds the withdrawal with the claims, and re-checks every send after balancing.

What the validator checks: the exact value

Section titled “What the validator checks: the exact value”

A contract is asset-aware if any method takes Funds or returns sends or mint. Every transition of an asset-aware contract checks, over full multi-asset values (I26):

For a creation, the input is the deposit plus the minted thread token. For a destroy there is no output: everything except the burned token must be allocated. Contracts that are not asset-aware keep the cheaper lovelace-only check.

Invariant Meaning (ADR-0007 §3)
I26 The state output’s value is exactly the input plus what was received and minted, less what was paid and sent; a destroy allocates everything
I27 Only reserved-kind names are lifecycle tokens; lifecycle redeemers never mint or burn user tokens
I28 User tokens are minted or burned only through ByAction(by), by the transition at by, exactly as declared
I29 Every send has its own claim in the output registry; each output is claimed at most once
I30 A claimed output is never at a spent input’s payment credential and never carries a JOUST payout or refund tag
I31 funds.received equals accepted; no reserved-kind token of the own policy is received, sent or minted

Rules and limits

Section titled “Rules and limits”
  • Funds is the last parameter. @Payable with Funds requires accepted in the result; accepted without @Payable and Funds is an error.
  • @StateContract(assetSlots) (default 4 for asset-aware contracts, 0 otherwise; 0 to 64) sizes the min-ADA deposit for the assets a state UTxO may hold, about 80 bytes each. Set it to what you expect: the dex uses 2.
  • One minting transition per transaction per policy, and no user minting at init.
  • An asset-aware contract cannot have @Batched actions: intents carry only lovelace.
  • The 32-byte CIP-68 shape (label plus a 28-byte hash) is a reserved name under your own policy; such tokens need their own minting policy.
  • Asset-aware contracts pay for full-value accounting, and a transaction with sends runs the output verifier too. The dex validator is 12,008 bytes plus the 703-byte output verifier, shared (examples/README.md).

Pitfalls

Section titled “Pitfalls”

Send to the enterprise address, not the fee payer's

The runtime’s transaction builder (QuickTx, from cardano-client-lib) may take the fee from an output at the fee payer’s address. A send there could be eaten by the fee, so the runtime refuses it before submitting with an error that says so. Send to the recipient’s enterprise address (payment key, no stake part), as the examples’ wallet(key) helpers do. Payouts go to enterprise addresses already.

  • Do not take a Value method argument. JuLC decodes a redeemer field typed Value as a constructor, and it fails. Take quantities as BigInteger and names as byte[] (as the dex does), or PlutusData if you must. Values a method builds (Send.value, mint) are fine.
  • A Value cannot be a loop accumulator in JuLC. Use recursion.
  • Datums must be canonical. cardano-client-lib writes inline datums in canonical CBOR, map keys sorted. A datum or memo with a map must already be in key order (SortedMaps), or the on-chain equality fails.
  • A send with no datum to a script address locks its funds. The runtime warns.
  • Off-chain code of your own: a QuickTx ScriptTx balances only lovelace from the fee payer. The JOUST runtime collects the UTxOs holding the offered assets for you; code that builds its own transactions must do the same.
  • Debugging a refusal: build with -Pjoust.traces (-Ajoust.traces=true) so every failing check traces its name.
