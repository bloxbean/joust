Deposits

A deposit moves value from one JOUST contract’s call into another contract’s instance, in the same transaction: a market stall sends 5% of each sale into a fee pot, a vault forwards interest into a treasury. A Send cannot do this, because a send may never land on a spent script’s continuing output (invariant I30), and the receiving instance is exactly that. Deposits are the safe path (ADR-0011 D3).

Both sides take part:

  • the depositor returns deposits, and its validator subtracts them from its own value;
  • the receiver declares an action @Receives, sees the deposits in funds.deposits(), and decides what to credit.

The two calls run in one composed transaction.

Calling it

Section titled “Calling it”

A deposit needs its receiver in the same transaction, so a lone sell is refused before anything is built.

  • Java
  • JavaScript

The receiver may come first or last in the composition. The runtime runs the calls in two passes: in the first, a receiver sees the deposits made so far, and if one placed before its depositors refuses, the pass is rerun with the deposits found; in the second, every receiver sees every deposit.

What the validators check

Section titled “What the validators check”

Deposit claims sit in the same output registry as sends, kept by the shared output verifier, in their own list.

The output verifier requires each deposit claim’s value to be canonical, non-empty, strictly positive and free of reserved-kind token names under any policy; each by to be an input of the transaction; output indices in range and non-decreasing (several claims may name one output).

The depositor’s validator:

  • subtracts the deposits in its value equation, like sends;
  • requires each deposit to target a distinct instance with a 32-byte id, whose token an input holds, so the receiver’s validator runs;
  • requires one claim by its own input on the target’s unique continuing output, with the same value and memo;
  • requires the number of claims naming its input to equal its number of deposits, so no claim can be attributed to it falsely.

The receiver’s validator:

  • adds every claim on its continuing output to its value equation, each counted once: out = in + received + accepted + Σ deposits + mint − payouts − sends;
  • gives the method exactly that list as funds.deposits().

Every other continuing transition of a contract with @Receives refuses a deposit claim on its output. That is why Pot.handOver fails if anyone tries to deposit through it.

Invariant Meaning
I40 A deposit is counted only by its receiver, which runs in the same transaction and counts each claimed deposit exactly once in its value equation

Rules

Section titled “Rules”

The target must be a @Receives contract, fixed in params

A depositor checks that the target is spent and that its claim exists; it cannot check what the target’s validator does. A contract generated before deposits existed, a plain contract or a foreign script could take the value without counting it. So choose the target when you write the depositor, and fix it in @Params (a ForeignInstance), never in an argument a caller supplies.

  • A contract may not deposit into itself.
  • by is not authenticated beyond naming an input of the transaction. A receiver that credits by depositor must check the input at by itself. A memo is whatever the depositor’s method wrote: trust it as far as you trust the depositor contract.
  • Memos must be canonical. A memo with a map built out of key order would be reordered by serialisation and fail the depositor’s check; the runtime refuses it. Keep maps sorted (SortedMaps).
  • Reserved names cannot be deposited, under any policy: an NFT named by a 32-byte hash cannot be a deposit. Send it instead.
  • @Receives needs Funds and goes on an action or owned action, never a creation or destroy.

Cost

Section titled “Cost”

From ADR-0011 §7, for one sale: the stall 280.7M CPU and 895k memory, the pot 209.6M and 669k, the output verifier 41.7M and 135k. Pot is 8.6 KB and Stall 9.4 KB.
