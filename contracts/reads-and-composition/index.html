Reads and composition

Contracts work together. A shop prices its goods from an oracle; a market pays into a fee pot; a counter migrates to its next version. On Cardano this happens at the transaction level: one transaction spends several scripts’ UTxOs, and each script checks its own part. JOUST gives you two tools for it (ADR-0011):

  • @Reads: a method parameter that reads another JOUST contract’s state, through a reference input, checked on chain;
  • Compose: one transaction built from several ordinary client calls, all or nothing.

A reference input is a UTxO a transaction reads without spending it: its datum is visible to the scripts, and its own validator does not run.

The rules

Section titled “The rules”
  • The source is pinned in params. @Reads("params.x") names a ForeignInstance(byte[] policy, byte[] instance) field of the contract’s @Params record. Params are applied to the script at deploy, so the trusted contract and instance are fixed then. A state field could be changed by an action; a param cannot. See Params, invariants and events.
  • The parameter’s type is the other contract’s state record, here Oracle.State.
  • Placement: the @Params record parameter comes right after the state, and @Reads parameters right after it.
  • Not yet: @Reads in a creation, in a move or an @Admits action, or in a @Batched action; and foreign state holding MerkleMaps (a reference input has no proof path for map reads).

What the validator checks

Section titled “What the validator checks”

For each @Reads parameter, the reference input must:

  • hold exactly one token of policy, named instance, which is 32 bytes (an instance, not an object or intent);
  • sit at an address whose payment credential is the script policy;
  • carry an inline datum, decoded as the foreign state after a shape check (constructor 0 and the record’s number of fields), which refuses another version’s layout.

This is invariant I39. The runtime finds the reference input and adds it for you: the call looks like any other.

Freshness is your rule

A reference input’s validator does not run, so an old oracle state stays readable. Give the source state a timestamp and check it, as Shop.buy checks updatedAt against ctx.validFrom() and maxAgeMs. See Time.

Compose: several calls, one transaction

Section titled “Compose: several calls, one transaction”

Compose runs ordinary client calls inside one composition and submits them as one transaction: every call’s checks pass, or nothing happens. On chain nothing changes: each validator checks only its own transition, so composing adds no new trust.

  • Java
  • JavaScript
Method What it does
Compose.of(runtime, payer) Starts a composition; payer pays the fee
add(Runnable call) Adds any client call: an action, a destroy, a deploy, an owned call
allowSharedSigners() Lets one key’s signature count for several calls (refused by default)
submit() Builds, checks, submits and confirms; returns the transaction hash
prepare() Builds and checks it for a wallet to sign, without signing (Wallets)

Each step is { contract, method, args, pay, instance, object, into, cosigners }, where contract is a JoustContract (a generated client’s .contract). rt.compose(wallet, steps) is the runtime’s shortcut for runComposed({ service, chain, api, steps }): the engine prepares the transaction, the page verifies each call and the whole, and one wallet signature covers it. See JavaScript clients.

How it builds the transaction

Section titled “How it builds the transaction”

The calls run in capture mode: instead of submitting, each client call writes its inputs, outputs, redeemers and signers into one shared transaction.

  1. Windows first. A first pass learns every call’s validity window. The second pass runs every call in their intersection, so each method’s Ctx equals the final bounds. A call whose result depends on time is never reused with another window.
  2. Shared verifiers. Each verifier withdrawal (map, output) appears once, with every call’s claims merged, and the output registry is rebuilt from the final output order.
  3. Checks after balancing. Every state output, payout and send is verified after balancing, before submission.

Refused before building:

  • the same UTxO spent by two calls (for example two calls on one instance);
  • two calls minting under one policy (the ledger allows one mint redeemer per policy);
  • an empty common window;
  • a key that signs for more than one call, unless you call allowSharedSigners().

Why shared signers are opt-in

A signature on a transaction counts for every @SignedBy and @Quorum check in it. If Ann signs for her own call, her signature also satisfies a second call’s @SignedBy("ann"). That is how the ledger works, so Compose asks you to say you mean it.

A composition can be nested: a call that composes internally (such as an owned move’s <move>Admitted) joins the outer transaction. Owned-object moves and deposits run only inside a composition.

Migration is a composition

Section titled “Migration is a composition”

Moving an instance to a new contract version is two calls in one transaction: the old version’s @Destroy @MigrateTo(...) and the new version’s @Migrate creation. Each side names the other, and the funds move only into the named successor (I41).

  • Java
  • JavaScript

Migration is not supported yet for contracts with MerkleMaps, owned objects or native assets. Upgrades and migration covers the design.

Limits

Section titled “Limits”
  • One transaction’s limits apply: 16 KB of transaction, and the CPU and memory budget (10,000M CPU, 14M memory on mainnet). Each contract adds its reference script’s size fee and its execution.
  • One mint per policy per transaction, so two calls that both mint under one contract cannot compose.
  • Foreign validators that ignore JOUST’s payout tags and output registry can still be double-satisfied by a JOUST output. Compose with them needs care (ADR-0007 D5).
