Upgrades and migration

A deployed script never changes: its hash is its identity. To ship a new version of a contract you deploy a new script and migrate each instance into it. JOUST makes migration a two-sided handshake, checked by both validators in one transaction:

  • the old contract ends the instance with a @Destroy marked @MigrateTo, which may send its funds only into the successor it names;
  • the new contract creates the replacement with a @Migrate method, which adopts only an instance of the predecessor it names, and only if that instance ends in the same transaction.

Neither side alone can move funds. The example is examples/upgrade: CounterV1 migrates into CounterV2, which adds a step size and keeps the admin, the count and the funds.

The old side: @MigrateTo

Section titled “The old side: @MigrateTo”

@MigrateTo("field") goes on an instance @Destroy. The field is a byte[] holding the successor’s policy id: a state field an admin sets, or params.<component>.

A migrating destroy does not pay out ctx.balance(): the funds go to the successor instead. What its validator checks, besides the usual destroy checks (the method’s rules, @SignedBy, Ctx, its own token burned, payouts paid and tagged):

  • exactly one token is minted under the successor policy, named blake2b_256(own input): the instance id the successor derives from this state UTxO;
  • exactly one output holds that token, at an address whose payment credential is the successor script;
  • that output holds at least this instance’s lovelace, plus what was paid in, minus the method’s payouts.

So the funds can only move into an instance of the contract the field names.

The new side: @Migrate

Section titled “The new side: @Migrate”

@Migrate(from = "params.previous") marks a creation method that adopts an instance of the previous version. from must name a byte[] component of the new contract’s @Params record, holding the previous policy id. The method takes the params, then the previous contract’s state record, then any arguments and an optional Ctx, and returns the new state:

The adoption’s validator (its MINT side, with its own Adopt redeemer) checks:

  • the seed it names is a state UTxO of the previous policy: one 32-byte token of that policy, at that policy’s script address, with an inline datum;
  • the datum has the shape of the previous state record: constructor 0 and the record’s number of fields (JuLC’s casts are unchecked, so this is what refuses another layout);
  • the previous instance’s token is burned (−1) in the same transaction, so the old instance ends;
  • exactly one new token is minted, named blake2b_256(seed), and one output holds it at the new contract’s state address, without a reference script;
  • the output’s datum equals adopt(params, old) and fits maxDatumBytes;
  • its value is exactly the old UTxO’s lovelace plus the new token, and at least the new minAda.

Why the old side names its successor in the state

Section titled “Why the old side names its successor in the state”

Both sides pin each other. If both did it through @Params, each script hash would depend on the other’s: v1’s params would hold v2’s hash and v2’s params v1’s. That is circular, so the example splits it:

  • v2 pins v1 in its params (Config(previous)), fixed when v2 is deployed;
  • v1 names v2 in a state field, successor, that only its admin may set (setSuccessor, @SignedBy("admin")).

This puts trust in v1’s admin: the admin decides where every instance may migrate. Users of v1 should know that. A contract that must never move needs no @MigrateTo at all.

The migration transaction

Section titled “The migration transaction”

The two halves must be in one transaction: v1’s destroy is only valid if v2 mints the successor, and v2’s adoption is only valid if v1’s token burns. The Java runtime builds it with Compose, which runs several client calls into one transaction:

The generated CounterV2Client.adopt(runtime, params, caller, prior) takes the old instance’s StateInstance. Called outside a Compose, it refuses: adopt runs inside a Compose, together with the old instance's migrating destroy.

The instance id changes

The new instance’s id is blake2b_256 of the old state UTxO’s reference, not the old id. Store the new id (adopted[0].instanceId()). Anything that refers to the old instance by (policy, id), including other contracts that read it through @Reads pinned in their params, must migrate too.

Rules and limits

Section titled “Rules and limits”
  • At most one @Migrate per contract. @Migrate is its own kind of creation: no other lifecycle annotation on the same method, and no @Quorum or @AuthorizedBy.
  • @MigrateTo goes only on an instance @Destroy, and names a byte[].
  • Not supported yet with MerkleMaps, owned objects or native assets, on either side. The processor reports an error.
  • A migrating destroy should return Payouts.none(): the new side requires the new instance to hold exactly the old UTxO’s lovelace, so nothing can be paid out of it.
  • Migration is an atomic transaction of two contracts, so both reference scripts’ fees and both executions count toward one transaction’s limits (see Fees and script size).

What the harness tests

Section titled “What the harness tests”

examples/upgrade/src/test/.../UpgradeTest.java evaluates the migration transaction with each contract’s harness and checks that the handshake holds:

  • v1 refuses a successor its admin did not name;
  • both sides refuse when the new instance holds less than the old;
  • v1 refuses when no successor token is minted;
  • v2 refuses to adopt when the old token is not burned.
