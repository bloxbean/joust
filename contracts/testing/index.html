Testing

A JOUST contract is one class, but it runs in three places: your methods on the JVM, the compiled validator on chain, and the client building real transactions. Each example in the repository tests all three, at increasing cost:

Level Tool Needs Catches
Plain Java JUnit Nothing Wrong business logic, Require messages
On-chain harness StateHarness (julc-state-testkit) The build’s compiled validator What the validator accepts and rejects; script budgets
Attack suite Attacks An accepted harness transaction Every mutation the invariants forbid must be rejected
End to end The generated client on Yaci DevKit DevKit running Building, balancing, submitting, confirming, contention
JavaScript node --test, Playwright DevKit, built JS packages JS clients, the runtime engine, the page verifier, pages in a browser

Add the test kit to your build (it brings JUnit 5 with it):

The compiled validator: StateHarness

Section titled “The compiled validator: StateHarness”

StateHarness evaluates the generated validator as compiled by your build (loaded from META-INF/plutus/<Name>Validator.plutus.json) in JuLC’s VM, against transactions shaped like the ones the runtime submits. A transaction is accepted when every script it triggers accepts: SPEND for each state input, MINT if it mints or burns under the policy, and the shared verifiers when the contract uses them.

The pattern: compute the next state on the JVM (as the client would), build the matching transaction, and assert:

The redeemers are the generated validator’s records: <Name>Validator.CreateInstance, BurnInstance, and one per action or destroy (Increment, Reset, Close), with Ctx as their last field when the method declares it.

The ledger’s value rules come first. Before any script runs, evaluate refuses a transaction the ledger itself would refuse for its values: an output holding a negative quantity or more than 2^64 − 1 of anything, or a mint entry of zero or outside Int64. The verdict then has one entry, LEDGER, and no script result. This catches a method that sends or burns more than the instance holds: the value equation can still balance (the continuing output would hold a negative quantity), so the validator alone would accept it. A test that measures scripts at quantities no output may hold (a worst-case budget) can turn the check off with h.ledgerRules(false); use it for that run only. The rest of the ledger (the minimum lovelace per output, fees, balance, conservation) is not modelled here: the testkit’s Ledger (the full transaction model, used for keyed objects) checks those and refuses non-positive output quantities, but not yet the 2^64 − 1 and Int64 bounds. The two share no code yet (issue #86).

The attack suite

Section titled “The attack suite”

Attacks.assertAllRejected(h, tx) takes a transaction the harness accepts, applies every mutation the invariants of ADR-0001 §4 (and of the later ADRs) forbid that applies to it, and fails listing any mutation the validator accepted. It returns how many it tried. Call it on every accepted transaction in your tests.

A mutation applies only where it makes sense: removing a signer only if the call needed one, range attacks only if the transaction has a validity range, payout attacks only if it pays out. What it tries includes:

Invariant Mutations
I1, I9 Seed not consumed; two thread tokens minted; an extra token under the policy
I2, I4 Datum replaced; datum hash instead of inline datum; state output dropped
I3 Token dust added; one lovelace skimmed; one lovelace added
I4, I12 Thread token sent to a key address; stake credential on the state address; reference script on the state output
I5, I11 Required signer missing
I6, I11 Upper or lower bound unbounded; range shifted by 1 ms; range wider than maxValidityMs
I7 A payout untagged, tagged with another input, under-paid by one lovelace, paid to someone else, or to a script with the same hash
I8 Destroy without burning the token
I10 A junk UTxO (no thread token) spent as the state
ADR-0007 Native tokens skimmed; sends under-filled, redirected, re-tagged or unclaimed; user mints off by one

End to end on Yaci DevKit

Section titled “End to end on Yaci DevKit”

The last level runs the generated client against a live local network. The examples tag these tests devnet and skip them when DevKit is not reachable, so ./gradlew build works anywhere:

DevKit (in examples/devkit) builds a runtime for DevKit and funds fresh accounts from its faucet; the quick start shows a trimmed copy for your own project. Use fresh accounts per test, keep the TTL short (DevKit’s time horizon is minutes), and expect each call to take a few seconds.

The JOUST build adds two switches for these tests:

Property Effect
-PjoustFixtures Records every transaction the examples’ tests build, with the chain reads behind it, into fixtures/m0/<example> (the oracle the JavaScript runtime is checked against; ADR-0015 M0). DevKit must be running
-Pjoust.dumpTx=<dir> Writes each submitted transaction’s CBOR to <dir>

When a test fails

Section titled “When a test fails”

  • assertAccepted fails: the message lists each script, ok or REJECTED, with its CPU and memory, the traces and the error. Require messages appear in the traces.

  • Which generated check failed? Build with the processor option -Ajoust.traces=true: every failing check then traces its name (larger scripts; for debugging only). For example:

  • -Pjoust.failedTerm (JOUST build) adds the failing UPLC term to the harness output.

  • The JVM accepts, the validator rejects (or the reverse) on the same input: that is a divergence between the two runs. Look for byte[] compared with .equals, or arithmetic outside BigInteger; see Java.

Pages in a browser

Section titled “Pages in a browser”

Node tests cannot catch a page that fails to load. js/joust/test/page.test.js drives the template’s page in Chromium with Playwright, on DevKit: it connects the in-page DevKit key, tops it up, creates a counter, increments it, sees the contract refuse +0, and closes it, with every transaction prepared in the page’s worker and verified before signing. It also runs the built page as static files (with its engine checked against the hashes pinned in the page) and a MerkleMap contract whose mirror survives a reload. The tests skip themselves when DevKit is not reachable. If Playwright has no browser yet, install Chromium with npx playwright install chromium.

The dApp example runs its page flows from Gradle: DappDevnetTest drives examples/dapp/frontend/e2e/run.mjs in Node on DevKit, including a malicious prepare service whose every transaction the page must refuse.

Tip

A good test file for a new contract has, for each method: a JVM test of the happy path and of each Require; a harness test that is accepted and runs Attacks.assertAllRejected; a harness test per rule the validator must enforce (assertRejected); and one DevKit test of the whole lifecycle.
