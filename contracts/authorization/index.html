Authorization

By default anyone can call any method. Authorisation is how you restrict that: to one key stored in the state, to a quorum of a council, or to another script’s decision. Each form is a check the generated validator runs on chain, against the current state, before your method’s result is accepted. The client runs the same check first and refuses a call that would fail.

The options at a glance

Section titled “The options at a glance”
You need Use Checked against
The caller’s identity inside your logic Ctx and ctx.caller() The transaction is signed by caller
One key stored in the state @SignedBy("field") A byte[] field of the current state
The key in a field named owner @OnlyOwner Same as @SignedBy("owner")
M of N keys @Quorum(keys = "…", threshold = "…") A JulcList<byte[]> and a BigInteger field
A key or a script (a DAO, a governor) @AuthorizedBy("field") A Credential field of the state or the params

Caller identity: Ctx.caller

Section titled “Caller identity: Ctx.caller”

A method that declares Ctx receives ctx.caller(), the payment key hash of the party calling. The validator checks that the transaction is signed by that key, so the value is authenticated: it is JOUST’s msg.sender.

Use it when the rule is more than “this one field”:

and to record who did something (new State(ctx.caller(), …) in an @Init makes the deployer the owner).

Caution

Compare keys with ByteStringLib.equals(a, b). On the JVM, a == b and a.equals(b) compare array references and are almost always false; on chain they compare bytes. Shared code must give the same answer on both sides.

@SignedBy and @OnlyOwner

Section titled “@SignedBy and @OnlyOwner”

@SignedBy("field") requires the transaction to be signed by the key hash held in the named byte[] field of the current state. @OnlyOwner is shorthand for @SignedBy("owner").

  • Java
  • .jsc
  • JavaScript

only <field> lowers to @SignedBy("<field>") and needs a Key field. A .jsc action or destroy that pays out must say who may call it: only <field>, or open if anyone may (the body’s requires are then the only guard). Otherwise it does not compile.

Rules and behaviour:

  • The field must be a byte[] component of the state record. It is read from the current state, not the method’s result, so an action cannot authorise itself by changing the field.
  • The method does not need Ctx. The counter’s reset has none: @OnlyOwner alone makes the client add the owner’s key as a required signer.
  • It cannot go on an @Init (there is no current state yet): use Ctx and Require.that in the body.
  • It cannot go on a @Batched action: the batcher, not the intent’s owner, signs a batch.
  • The Java client checks the caller first and throws RequireException("Vault.withdraw: must be called by the key in 'owner'").

On chain the generated check is one line, ContextsLib.signedBy(tx, current.owner()).

@Quorum: M-of-N signatures

Section titled “@Quorum: M-of-N signatures”

@Quorum(keys = "council", threshold = "quorum") requires at least threshold of the transaction’s signers to be among keys. Both name fields: keys a JulcList<byte[]> of key hashes, threshold a BigInteger, in the state, in the owned record, or in the @Params record ("params.x").

What the validator checks:

  • The count. The transaction’s signatories that appear in keys number at least threshold, and threshold is at least 1. The ledger’s signatory set has no repeats. The cost grows with signatories × keys.
  • The current state. The check reads the input state, never the method’s result. rotate(council = [attacker], quorum = 1) cannot authorise itself.
  • Every output keeps a reachable quorum. On every state the validator accepts as an output (creation and every action), and on the params at creation, it checks that the keys are strictly ascending (so distinct), each 28 bytes, and 1 ≤ threshold ≤ number of keys. No rotation can lock the contract.

Co-signers

Section titled “Co-signers”

The caller’s signature counts toward the quorum. The other members sign the same transaction as co-signers:

  • Java
  • JavaScript

A method may combine @Quorum with @SignedBy, and ctx.caller() may be one of the keys. When several calls are composed into one transaction, a signature counts for every call that requires it; Compose refuses that unless you call allowSharedSigners() (see Reads and composition).

@AuthorizedBy: a key or a script

Section titled “@AuthorizedBy: a key or a script”

@AuthorizedBy("field") needs the approval of a credential held in a Credential field of the state, the owned record, or the params ("params.guardian"). A credential is either a key or a script, and the check differs:

  • Key credential: the key signed the transaction.
  • Script credential h: script h ran in the transaction, for a withdrawal from its reward account. This is the withdraw-zero pattern: withdrawing zero lovelace from a script’s reward account makes the ledger run that script, so the transaction proves the script approved it. The validator requires:
    • h is in the transaction’s withdrawals (native scripts count too);
    • h is not this contract’s own script, nor JOUST’s map verifier or output verifier, which approve any withdrawal;
    • if h has a Rewarding redeemer (every Plutus script does), it is an Approvals list containing Approval(policy, target, action): this contract’s policy id, this instance’s (or object’s) token name, and this method’s redeemer tag.

The binding means one approval never authorises another instance, another action or another contract. The action tag is the method’s constructor index in the generated Calls redeemer: the actions first, then the destroys (then any owned methods), each in declaration order. The treasury’s fund, pay, rotate, freeze and close are 0 to 4, so freeze is 3. The contract description lists each method’s index.

Writing a governor

Section titled “Writing a governor”

A governor is a plain JuLC withdraw validator. The example’s Guardian approves whatever its redeemer lists when its owner signs, and refuses any purpose other than Rewarding:

A governor’s obligations:

  • list only the approvals its own rules grant (votes, another contract’s state, a signature);
  • refuse certificates (the Certifying purpose), so nobody can deregister its stake credential and block every @AuthorizedBy call;
  • have its stake credential registered once, so withdrawals from it are possible.

Note

@Quorum and @AuthorizedBy read the current state, so neither can go on an @Init or @Migrate creation. Neither can go on a @Batched action: an intent’s owner is the caller. .jsc gets quorum and authorized in milestone M2; until then write those contracts in Java.

Which to use when

Section titled “Which to use when”
  • One fixed party (an owner, an admin, a creator): @SignedBy("field") or @OnlyOwner. Cheapest, and the client checks it before anything is built.
  • A choice among parties, or a rule that mixes identity and time (escrow’s “seller or arbiter, or anyone after the deadline”): Ctx and Require.that with ByteStringLib.equals.
  • A committee: @Quorum. Keep the council in the state if it must change (with a quorum-guarded rotate), or in @Params if it is fixed for the deployment.
  • Another contract’s or a DAO’s decision: @AuthorizedBy with a script credential, kept in @Params so the governor is fixed by the script hash and cannot be swapped by an action.
  • Anyone: no annotation. The method’s Requires are then the only guard, so make sure they are enough, especially for anything that pays out.

Pitfalls

Section titled “Pitfalls”
  • Unsorted council keys. @Quorum rejects any state whose keys are not strictly ascending, at creation too.
  • An admin field changed by an unguarded action. @SignedBy protects the method it is on, not the field. Guard every action that writes the field.
  • A governor that accepts anything. @AuthorizedBy trusts the script’s rules completely. Bind its approvals to real conditions, and pin it in @Params.
  • Forgetting to register the governor’s stake credential. Without registration the zero withdrawal is invalid, and no @AuthorizedBy call can succeed.
