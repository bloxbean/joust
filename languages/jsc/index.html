.jsc

.jsc is JOUST’s contract language. Version 2 reads like TypeScript: a contract is its state, an init that returns the first state, actions that return the next one ({ ...state, count: count + by }), destroys that pay out, and views. Values never change, every if and match is an expression, and lists, records, enums, options and maps are built in. The build lowers each file to an ordinary Java @StateContract class; from there everything is the same as for a contract written in Java: the JOUST processor generates the validator and the typed client, and JuLC compiles the validator to UPLC.

A language preview

.jsc is a language preview (ADR-0018 D14), not to be confused with Cardano’s preview network. The language and the compiler’s output may change before it leaves preview, so the same file may compile to a different script hash in a later JOUST (milestone M1e changed once the hash of every .jsc script with a generated check). Use it on DevKit and testnets, and don’t deploy it to hold value; a deployed preview contract is rebuilt with the JOUST version recorded for it: each record of build/joust/deployments.<network>.json states it (commit those files if you must rebuild a deployed script later; build/ is ignored), or the plugin’s version. It covers the contract model (milestones M1 to M4): the core language, native assets, sends, mints, deploy parameters, events, reads of other contracts, owned and keyed objects, script purposes, migration, .jsc libraries and offline tests. A few combinations remain Java’s (below). .jsc becomes the recommended language for JavaScript developers only after an independent security review of the lowering.

Why it exists

Section titled “Why it exists”

A Java @StateContract is readable, but it is Java: BigInteger.compareTo, ByteStringLib.equals, records rebuilt field by field. .jsc gives JavaScript developers the same contract model in the syntax they know, and it removes the ways to get the subset wrong: there is no byte[] ==, no fixed-width integer, no mutable local.

.jsc lowers to Java, not to UPLC. Nothing new is trusted on chain. The validator’s invariants (thread token, exact datum, exact value, verified Ctx, tagged payouts) come from the JOUST processor, exactly as for a Java contract, and the same generated method runs on the JVM to build the transaction and on chain to check it.

A miscompile is still your bug

The trusted base does not grow, but a wrong lowering would produce a contract that the validator then enforces faithfully. The checker’s rules, the four-way differential tests (a reference interpreter, the JVM, the transition program and the validator must agree) and the generated checks are the defence. Read the generated Java of any contract that holds real value: every line carries a comment with its .jsc position.

A guided tour

Section titled “A guided tour”

The file

Section titled “The file”

A .jsc file may start with the header jsc 1 (comments may come before it; a file without it is version 1 too), then a package, then any number of imports, types, enums and fns, and exactly one contract:

Comments are // and /* … */. Newlines do not end statements; ; between statements is optional. An index’s [ and a call’s ( must be on the line of what they follow (on a later line they start a new expression), and a line that starts with - continues the expression above it, with a warning (JSC9007): see the reference. The generated class goes to <package path>/<Contract>.java: its name comes from the contract line, not from the file name.

The contract’s options are the @StateContract elements of the same name (Annotations):

Option Meaning Default
minAda Lovelace locked as the state UTxO’s min-ADA deposit (2 ada is allowed) derived from maxDatumBytes
maxDatumBytes Largest serialised state the validator accepts 512
maxValidityMs Widest validity interval a call that reads the transaction may use, in POSIX ms 3600000 (one hour)

State

Section titled “State”

state { … } declares the state record once, its fields in order: state { owner: Key, goal: Int, raised: Int }. A field has any type the language has, a BigMap included. Inside a method a bare field name reads the input state, and state is the whole input state. The input never changes, so the order of reads cannot matter.

Type What it is
Int The only number type: arbitrary precision, as on chain. 1_000_000, 5 ada (5,000,000 lovelace)
Bool true, false
Bytes A byte string: #cafe, or utf8("text")
Key A 28-byte key hash. A Key is also Bytes; Bytes become a Key only through asKey(b), a checked conversion
Hash A 28-byte script hash or policy id (asHash(b))
List<T> [a, b], [x, ...xs]
Option<T> Some(x) or None
Map<K, V> An inline map in the datum, in canonical key order; keys are Bytes, Key or Hash of at most 64 bytes
BigMap<K, Int>, BigMap<K, Bytes> A Merkle map: any number of entries behind a 32-byte root (MerkleMaps); a state field only
type R = { … } Your records
enum E { A, B { x: Int } } Your sum types

The reference gives each type’s on-chain encoding.

Methods and their results

Section titled “Methods and their results”
Member Form Its value
init init(params) [payable] { … } (exactly one, no name) the first state: return { count: 0, owner: caller }
action action name(params) modifiers { … } the next state: return { ...state, count: count + by }
destroy destroy name(params) modifiers { … } nothing: it ends the instance, and must pay out what it holds
view view name(params): T = expr, or a block a value, computed off chain without a transaction

A block’s value is its last expression; return e as the last statement means the same, and there is no early return. An object literal of the state type gives every field, explicitly or through one leading ...state; unknown fields, a field given twice and a spread of another type are errors. { goal } is short for { goal: goal }. An action that changes nothing returns state.

An init has no input state, so its parameters may share the names of the fields it creates:

In every other method a parameter, const or binding may not take a state field’s name or a built-in’s (JSC0213, which suggests newOwner): goal always means the state’s goal.

The transaction: built-ins

Section titled “The transaction: built-ins”
Name Type Meaning
caller Key The signer the validator verified
received Int Lovelace this call adds (a payable method)
balance Int Lovelace the instance holds, the min-ADA deposit included
validFrom, validTo Int The bounds of the transaction’s validity interval, POSIX ms: time values

A method gets the transaction (a generated Ctx ctx parameter) only when it reads one of these, or has a modifier that needs it. Views and fns never do (JSC0415): pass what they need as arguments.

require, pay and modifiers

Section titled “require, pay and modifiers”

require(cond, "message") fails the call unless cond holds: on the JVM it throws RequireException before anything is submitted, on chain it fails the script with the message as a trace. pay(to, amount) adds a payout of amount lovelace to the Key to: payouts are in source order, an amount of 0 is skipped and a negative one fails. pay is allowed only in an action or destroy, never in init, a view, a fn, a lambda or a value block (JSC0404, JSC0413). See Ctx, funds and payouts.

Modifiers follow the parameter list:

Modifier Annotation Allowed on
payable @Payable: the call may add lovelace (received) init, action
only f @SignedBy("f"): the Key field f must sign action, destroy
after f @ValidAfter("f"): valid only after the Int field f action, destroy
before f @ValidBefore("f"): valid only before the Int field f action, destroy
open none: you state that anyone may call a method that pays action, destroy
batched @Batched: the action also runs as an intent that a batcher applies (Batched intents) action
batched only @Batched(only = true): the action runs only as an intent action

A method that can pay needs an audience

An action or destroy that can reach a pay in any arm or loop must say who may call it: only <key field>, or open if anyone may, in which case its requires are the only guard (JSC0408). A destroy must pay at least once (JSC0409), and the checker warns when it never reads balance (JSC9001): a destroy must pay out everything the instance holds, the deposit included, or every call is rejected.

Immutable values

Section titled “Immutable values”

A name is bound once, with const, and never changes. The JavaScript habits that would change one are errors that say what to write instead:

You write You get
let x = 1, var x = 1 JSC0128: values are immutable in .jsc: write const x = …
x = 2, x += 1, x++ JSC0130 (JSC0135 for a prefix ++): build a new value, e.g. return { ...state, x: x + 1 }
a === b JSC0133: write ==: .jsc equality is always by value
for (let i = 0; …), while, for … in JSC1001, JSC1003, JSC1002: use xs.fold(…), range(a, b), for (const x of xs) or a recursive fn
function f() {} JSC0115: functions are written fn name(x: Int): Int = …
class, this, new JSC0116/JSC0140, JSC0139, JSC0142: records are type Name = { f: T }, a bare field name reads the state
null, undefined JSC0138: use Option<T> with None and Some(x)
async, await JSC0123/JSC0141: a call runs in one transaction
switch JSC0908: write match e { A => …, B { x } => … }
return before the end of a block JSC0129: a block’s value is its last expression

Every const must be used (JSC0215): JuLC may drop an unused binding on chain while the JVM still evaluates it, so const x = 100 / d must not look like a check. Write a require instead.

Conditionals and match

Section titled “Conditionals and match”

if c { a } else { b } is an expression when both arms end in a value; c ? a : b is its short form. Without an else, or with arms that end in statements, an if is a statement: its arms may require and pay. Only the taken arm runs, on the JVM and on chain.

match takes an enum or an Option, must be exhaustive, and is an expression or a statement. From Ledger.jsc:

Patterns are a variant (Open), a variant with fields bound by name (Closed { by }, or Closed { day: d } to rename), Some(x), None, and _ for every case not named by an earlier arm. A binding must be used; nested patterns are not supported (bind the value and match it again). An arm whose value is an object literal needs parentheses, since an arm’s { starts a block: Some(it) => ({ ...state, items: items.delete(id) }).

Functions and recursion

Section titled “Functions and recursion”

A fn has typed parameters and a typed result, at the top of the file or in the contract. It is pure: no pay, no transaction built-ins, no state (pass what it needs). A function may call itself directly; mutual recursion is refused (JSC0602), and so is a recursive call from inside a lambda, an if or match arm, a value block or a ?? default (JSC0601), since the generated helper would join a cycle. Write cond ? base : … f(…) instead, as digits does.

Lists

Section titled “Lists”
Member Result
xs.length, xs.isEmpty, xs.head Int, Bool, Option<T> (properties: no parentheses)
xs.contains(x) Bool, by structural equality
xs.any(x => …), xs.all(x => …) Bool; they stop at the first decisive element
xs.find(x => …) Option<T>: the first match
xs.filter(x => …), xs.map(x => …) a new list
xs.fold(init, (acc, x) => …) the accumulated value
xs.sum() (on List<Int>), xs.reverse(), xs.concat(ys)
xs.take(n), xs.drop(n) a new list; a negative n fails on both sides
range(a, b) the Ints from a up to b, exclusive, as the receiver of any, all, fold, filter, map or a for list; no list is built

Lambdas (x => e, (acc, x) => e, or a block of const and require ending in its value) exist only as arguments of these methods. for (const x of xs) { … } is a statement whose body may hold const, require, if, match and pay; accumulate with fold. std/list adds last, nth and indexOf (standard library).

Records

Section titled “Records”

type Share = { to: Key, bps: Int } declares a record. Build one with Share { to, bps: 0 }, or with { to, bps: 0 } where the type is known (a typed parameter, field or const, a list element). Read a field with s.bps. Two record types with the same fields are distinct, and records compare by value: shares.contains(from), s == from. Type, enum and variant names start with a capital and share one namespace.

Option

Section titled “Option”

Some(x) and None. o ?? d is o’s value, or d when it is None (d runs only then). match o { Some(x) => …, None => … } reads it. Option<Option<T>> and Some(None) are refused: JavaScript cannot tell Some(None) from None. ?? is not mixed with && or || without parentheses, as in JavaScript.

Map and BigMap

Section titled “Map and BigMap”

Two map types, for two sizes:

  • Map<K, V> is an inline map in the datum: every entry is in the state UTxO, so its size is bounded by maxDatumBytes. m.get(k) (an Option), m.has(k), m.set(k, v) and m.delete(k) (new maps, always in canonical key order), m.size, m.keys, m.values, m.isEmpty, m.any((k, v) => …), m.all(…), m.fold(init, (acc, k, v) => …), Map.empty(). Maps compare by value.
  • BigMap<K, Int> and BigMap<K, Bytes> are Merkle maps: any number of entries behind a 32-byte root; each call proves only the keys it reads and writes. A state field only.

A BigMap is read with m.get(k), m.has(k) and, on BigMap<K, Int>, m[k] (0 when absent). It is changed only in its own field of the next state, by set and delete: { ...state, balances: balances.set(to, v) }. Its Int values are never negative, and set(k, 0) removes the entry. It is never bound to a const, passed to a fn, captured by a lambda, compared or chosen by a condition; BigMap.empty() starts one in an init, and m.isEmpty (“empty before this call”) is read only in a destroy. A method reads its own writes through the chain, as transfer does.

Time

Section titled “Time”

validFrom and validTo are chosen by whoever submits the transaction, within maxValidityMs. So .jsc keeps them from deciding anything (ADR-0018 D11):

  • Decide only with after(t) and before(t). They hold for the whole validity window, and they are allowed only at the top of a require, alone or under && or ||: require(after(deadline) || raised == 0, "too early"). Never negated, in an if, a ?:, a const, a fn or a lambda.
  • A time value never decides. Any value computed from validFrom or validTo (through arithmetic, a const, a fn call, a record, a stored field) is a time value. It may not be a condition, an operand of &&, || or !, a predicate, or a comparison: require(validFrom < deadline, …) is refused (JSC0502).
  • A time value never makes an operation fail. It may not be a divisor, a map key, a list index or count, a domain-checked std argument, or a BigMap<K, Int> value. A payout may depend on one only as pay(to, max(0, …)).
  • Time values may flow into amounts and state, with a warning that names the bias (JSC9003 to JSC9005). A field that any method sets from a time value becomes a time field, and the ABI manifest lists it.

std/time has elapsedSince(t) (max(0, validFrom - t), never an over-estimate), elapsedSinceAtMost(t), windowStart() and windowEnd(). For a field-based rule on a whole method, prefer the after f and before f modifiers. See Time and the precise rule.

Checked inputs

Section titled “Checked inputs”

Every value that crosses into the contract from a caller (an init argument or an action’s parameter, in the redeemer) is checked by generated code before your code sees it, recursively: every Key and Hash in it is 28 bytes, and every Map has unique keys of at most 64 bytes in strictly ascending canonical order. A failing check is a located require failure. So reassign(from: Share, to: Key) can trust that to and from.to are real key hashes.

The standard library

Section titled “The standard library”

std/bytes, std/crypto, std/math (div and mod floor, where / and % truncate), std/bits, std/list and std/time, plus the prelude (min, max, abs, utf8, asKey, asHash, range, Some, after, before). Every function, its domain and its Java target: .jsc standard library.

How it lowers

Section titled “How it lowers”

The lowering is mechanical, and the output is meant to be read. The counter above becomes (imports omitted):

What to notice:

  • Modifiers became annotations: only owner is @SignedBy("owner").
  • Ctx appears only where needed: init reads caller, close reads balance; increment and reset take none, so they need no signature and cost less.
  • No loops and no reassigned locals in the generated Java: fold, for, map and the other list methods become typed, self-recursive static helpers; if and match arms become helpers that run only when taken.
  • Equality is generated: == on bytes lowers to ByteStringLib.equals, and on records, enums, lists, options and maps to generated helpers, never Java equals or a reference comparison.
  • Every line carries its .jsc position (// Counter.jsc:20:5), and the generated checks carry it in their messages, so a failure on chain points back to your source.

The generated Java is on disk: build/generated/sources/jsc/java/main/ on Gradle, build/joust/generated/ with joust build. Beside each file, <Contract>.jscmap.json maps each generated line to its .jsc line and column; a javac or processor diagnostic on generated Java is reported at the .jsc position, with the generated location as a note.

The ABI manifest

Section titled “The ABI manifest”

The build writes <Contract>.abi.json for every .jsc contract: the encoding of its datum and of every redeemer (constructor indices, field names and order, data shapes, the schemas they reach) and its time fields. The project commits it beside the .jsc file. Every build compares what the lowering produces with the committed copy, so a change that would alter how a deployed instance’s datum or redeemer is encoded cannot pass unnoticed:

The build finds Result
The same manifest builds
No committed manifest fails: JSC0003
A different manifest fails: JSC0002, naming the first line that differs

When the change is intended (a new contract, or a new script you will deploy afresh), accept it, review the diff and commit it:

  • Java
  • JavaScript

Nothing else accepts a manifest: no Gradle or system property switches the check off. Each build also checks the manifest against the processor’s own description of the contract (JSC0004, an internal error of the lowering if it ever fires; on Gradle the checkJscAbi task, part of check). See the reference.

Building .jsc

Section titled “Building .jsc”
  • Java
  • JavaScript

With the Gradle plugin org.julclang.joust (Quick start: Java), put .jsc files under src/main/jsc/, in directories that match their packages. The plugin adds:

Task What it does
generateJsc Lowers src/main/jsc/**/*.jsc to build/generated/sources/jsc/java/main/ before compileJava; fails on a refused or missing ABI manifest
acceptJscAbi Writes the ABI manifests beside the .jsc files, accepting new and changed ones
checkJscAbi After compileJava, checks each manifest against the processor’s description; part of check
  • Directorysrc/main/jsc/org/example/vault
    • Vault.jsc
    • Vault.abi.json committed
  • Directorybuild/generated/sources/jsc/java/main/org/example/vault
    • Vault.java generated, then processed like hand-written Java
    • Vault.jscmap.json its source map

Each run empties the output directory first, so a deleted or renamed .jsc leaves no stale contract behind, and two files that generate the same class are an error. examples/dsl/build.gradle wires the same three tasks by hand.

Put .jsc files beside (or instead of) .java files in the project’s contracts/ directory. joust build compiles both with no JDK: the lowering runs inside the toolchain’s Wasm engine, exactly as in the Gradle build. joust dev rebuilds when you save a .jsc file, and keeps serving the last good build when a manifest is refused.

Errors and warnings carry their position and a stable code, printed alike on both paths (Gradle and joust build): app/Counter.jsc:20:13: error[JSC0502]: a time value cannot decide here: …. Each code is in the diagnostics catalogue.

Testing a .jsc contract

Section titled “Testing a .jsc contract”

Test it exactly like a Java contract: the generated class, validator and client are ordinary code (Testing). examples/dsl’s Dsl2Test calls the generated methods on the JVM, inputs checked and refused included, and evaluates the validators with the harness; julc-state-toolchain’s four-way tests run every call through the reference interpreter, the JVM, the transition program and the validator, and require all four to agree.

What still needs Java

Section titled “What still needs Java”

Every feature of the contract model has a .jsc form (.jsc reference). This table lists what .jsc refuses and a Java contract accepts; limits both languages share are in the diagnostics catalogue:

Combination Code
stakeSelf or a withdraw handler beside owned objects; a withdraw handler beside BigMap state JSC1305
Beside an owned type that keeps a BigMap: a move, a batched action, deposits, a read of another contract, a certify, vote or propose handler, or an invariant by type JSC1217
import contract of a Java contract JSC0741
Importing a contract whose state, declared types, events or memos use a type from a library it imports JSC0746

Write such a contract in Java; you can start from the generated Java of a .jsc version.
