.jsc reference

This page defines .jsc, as the front end in julc-state-dsl implements it (v2/Lexer.java, v2/Parser.java, v2/Checker.java, v2/JavaEmitter.java) and ADR-0018 states it. For a guided introduction, read the .jsc guide; for the functions, the standard library.

A preview

.jsc is a preview: the core language of milestone M1, M2a’s values and native assets (Value, Address, Credential, funds, send, mint, burn, accept), and M2b’s params, invariants, events, quorum and authorized, M2c’s composition (other contracts’ instances and states, deposits made and received, send datums, stored values), .jsc and Java libraries (M4, below), and M3’s owned and keyed objects, script purposes and migration.

Lexical rules

Section titled “Lexical rules”
Element Rule
Header Optional: when the first word of the file, after whitespace and comments, is jsc, it is followed by 1. A file without a header is version 1. Any other version is refused (JSC0113), jsc 2 included: it was the header of the previews, and there is no alias
Line ends LF or CRLF only. A lone CR, NEL, U+2028, U+2029, VT and FF are refused (JSC0147): some editors break lines there and a // comment could hide the code after them
Format characters No Unicode format character (category Cf: the bidirectional controls, zero-width characters) anywhere in the file, comments and strings included (JSC0145); a leading byte-order mark is allowed
Comments // to the end of the line, and /* … */
Identifiers [A-Za-z_][A-Za-z0-9_]*: ASCII only (JSC0146), so no two names can look alike. Case-sensitive
Integers Decimal digits, _ between groups (1_000_000). No sign: -5 is unary minus. 5 ada is 5,000,000
Bytes # then an even number of hex digits (#cafe, JSC0102); upper case is lower-cased
Strings "…" on one line, with the escapes \", \\ and \n; no control characters (JSC0104). Only require messages and utf8("…") arguments
Separators and newlines Newlines do not end statements: a statement ends where its expression cannot continue, or at ; (optional). Two tokens look at the line: a [ or a ( continues an index or a call only on the line of what it follows, so m[k] and f(x) start on one line, and on a later line [ or ( starts a new expression. A line that starts with a binary - continues the expression above it (a subtraction) and warns JSC9007: join the lines, parenthesise, or end the line above with ;

Grammar at a glance

Section titled “Grammar at a glance”

A file holds one contract (JSC0114), a contract one state block (JSC0121) and exactly one init (JSC0401). Members may come in any order. A block’s last expression is its value; a statement after it is JSC0127.

Contract options

Section titled “Contract options”
Option Java element Default Meaning
minAda long minAda() derived from maxDatumBytes Lovelace locked as the state UTxO’s min-ADA deposit; below the derived value is a compile error
maxDatumBytes int maxDatumBytes() 512 Largest serialised state the validator accepts
maxValidityMs long maxValidityMs() 3600000 Widest validity interval a call that reads the transaction may use
assetSlots int assetSlots() 4 when a method moves native assets, else 0 Native assets the state UTxO’s deposit is sized for (ADR-0007 D2); 0 to 64
stakeSelf boolean stakeSelf() = true off M3c (ADR-0010 D2): a flag, written without a value (JSC1301). The state’s address is staked to the contract’s own script, so its funds earn rewards; needs a withdraw and a certify handler (JSC1302)

Values are non-negative integer literals (ada allowed); anything else is JSC0402 or JSC0403.

Types and their encodings

Section titled “Types and their encodings”

The encoding is fixed and is what the ABI manifest states. It is JuLC’s encoding of the generated Java, so a .jsc contract and a Java contract with the same state agree on chain.

.jsc Java On-chain data (manifest data) Notes
Int BigInteger integer (int) unbounded on both sides
Bool boolean Constr 0 [] false, Constr 1 [] true (bool)
Bytes byte[] bytes (bytes) <, <=, >, >= compare bytes
Key byte[] bytes, 28 of them (bytes28) a Key is a Bytes; the reverse only through asKey
Hash byte[] bytes, 28 of them a script hash or policy id; asHash
List<T> JulcList<T> list (list<…>)
Option<T> Optional<T> Constr 0 [x] / Constr 1 [] (option<…>) Option<Option<T>> is refused (JSC0305)
Map<K, V> JulcMap<K, V> map with unique keys in canonical order (map<…>) K is Bytes, Key or Hash, at most 64 bytes (JSC0308)
BigMap<K, Int>, BigMap<K, Bytes> MerkleMap the MerkleMap record: its root, and the reads and writes of the call (merkleMap<…>) a state field only (JSC0803)
type R = { f: T, … } a generated record Constr 0 with the fields in declaration order no generic records
enum E { A, B { x: Int } } a generated sealed interface and one record per variant Constr i, i the variant’s declaration index, then its fields
Credential the ledger’s Credential Constr 0 [key hash] (KeyCred) / Constr 1 [script hash] (ScriptCred) built with keyCred(k), scriptCred(h); read with match c { KeyCred { key } => …, ScriptCred { hash } => … }

Value the ledger’s Value a map of maps, each policy’s token names in canonical order (shorter first: its wire form) a local’s, a fn‘s, funds’ and the effects’; M2c: a field of the state, the params, a record or a variant, never in a List, Option or Map (wrap it in a record) nor a method parameter (JSC0341)
Instance<C> the API’s ForeignInstance Constr 0 [policy, instance id] (ForeignInstance) M2c: another contract’s instance, C imported (import contract); a params field only (JSC0445), used whole as a deposit’s target and by reads
C.State, C.T the imported contract’s own records (Oracle.State) as that contract encodes them M2c: read, not stored: a const’s, a fn’s or a lambda’s type, never a field, a method parameter, a memo or a datum (JSC0446); not matched (JSC0446)

There are no strings at run time, no implicit conversions, no null and no generic user types. Type, enum and variant names start with a capital (JSC0205), have no _ (JSC0206), share one namespace (JSC0910), and may not be a name the processor generates (Lifecycle, Calls, Step, Funds, … : JSC0220).

Checked inputs

Section titled “Checked inputs”

Every init argument and every action and destroy parameter (the redeemer) is checked by generated code before the method’s body runs, recursively through records, enums, lists and options: every Key and Hash is 28 bytes, and every Map has unique keys of at most 64 bytes in strictly ascending canonical order; every Credential holds a 28-byte hash, and every Address the ledger’s encoding with a well-formed payment credential and, if it has one, a staking hash (an address with a staking pointer is refused). A checked address may still be your contract’s own script, and send to it always fails (#send:). If you store an address you will send to later (a refund list, a beneficiary), refuse it when you take it: require(paymentScript(a) == None || asHash(paymentScript(a) ?? #00) != funds.policy, "not this contract"). A failure is a located require failure. View parameters are not checked: a view runs off chain on your own inputs.

Names and scope

Section titled “Names and scope”
  • A name is bound once and never redeclared or shadowed (JSC0212).
  • In an action, destroy or view, no parameter, const, lambda parameter, loop variable or match binding may take a state field’s name or a built-in’s (caller, received, balance, validFrom, validTo, state, params, funds): JSC0213. In an init, which has no input state, parameters may share the names of the fields it creates.
  • No binding and no state field takes the name of a declared type, enum, variant or fn (JSC0222): const Open: Phase = phase would make phase == Open always true.
  • Names cannot contain __ (JSC0210) or be Java keywords and literals, members of Object, or names the generated code uses (ctx, State, Outcome, deploy, instance, seed, ByteStringLib, Int, List, Option, …: JSC0211). The full list is RESERVED in Checker.java.
  • The generated client binds s and r in actions and destroys, s in views, and seed and result in an init; a parameter may not take them (JSC0216).

Method names are unique, and a fn may not share one (JSC0202); nor may an invariant (JSC0224). A method gets Ctx ctx when it is a destroy, has a modifier other than open, only, quorum and authorized, or mentions caller, received, balance, validFrom, validTo, after or before.

Params (ADR-0009 D1) are fixed when the contract is deployed: the script is applied to them, so each set of params is its own script (pin policyIdFor(params)), and they are in no redeemer. An init takes them (first) whenever the contract declares them; any other method or view takes them (directly after the state) when it reads them. Config is then a reserved type name, as Event is in a contract with events (JSC0225). A batched action does not read them yet (JSC0437). M2c: the init checks them as a checked input (#params:: every Key and Hash 28 bytes, maps canonical, addresses the ledger’s, every Value of lovelace’s or 28-byte policies), so no instance is made under params whose values a reader would refuse.

Owned objects (ADR-0003, M3a). An owned method names its type, owned action Account.deposit(). A parameter bank: shared is the instance’s state, read through a reference input (never spent, so owners do not queue behind each other), and comes first (JSC1205, JSC1206); read its fields as bank.paused. In an owned action or destroy, received is what the call pays into the object and balance what the object holds. A method with a shared parameter takes Ctx, as the Java examples’ owned methods do. An owned action or destroy without an audience warns (JSC9010: anyone could call it on anyone’s object); say open when that is meant. A contract may declare several owned types (M3a2): each type’s objects have their own datum constructor (Holding_T), so a method only ever runs on its own type’s objects, and each type needs its own owned init and escape hatch (JSC1208, JSC1209, at the type). An owned type may keep BigMaps (the instance then keeps none, JSC1211), and an owned init may write them and accept native assets; an owned destroy may be payable. An instance’s init does not accept native assets (JSC0426). An owned action with a parameter to: into moves its object to another instance, which consents with an action admits T in the same transaction (first parameter the object’s id, then optionally the arriving object, obj: T). Each half reads the other’s input, never its outcome; each half is its own call, with its own refusal class; the transaction is accepted only if both halves are, and Compose reports the first refusal in the order its calls were added. An admission’s conditions hold for the object as it arrives (its input), not for the object that lands: if the move changes what the admission reads, check it on the move’s side too. A destination admits one object per transaction (it has one redeemer), and an object that keeps a BigMap cannot move yet (JSC1212). invariant T.name = … holds for every object of type T.

Keyed objects (ADR-0016, M3b). owned Entry keyed by name (maxKeyBytes = 64) { name: Bytes, owner: Key, … } makes Entry unique by name within an instance: each key is its own UTxO, a node of a sorted list whose head the instance’s creation makes. An owned init inserts after the node whose gap the key falls into (the runtime finds it); the key cannot be one already taken, live or retired. A keyed type’s methods are an owned type’s, with its rules:

  • The key is fixed for the object’s life (JSC1248): an action returns { ...state, … } without it, or with it unchanged. To change a key, retire or remove the object and insert another.
  • signed: the key is a 28-byte key hash that signs the insert, so nobody can take someone else’s key. Without it, an initializer that does not take the key from caller warns (JSC9011: anyone may take a free key first).
  • Exits. retire keeps the node, retired, with its key for good: the owner leaves with all but the deposit, and needs no neighbour, so this is the escape hatch every keyed type has (JSC1245). An owned destroy without retire removes the node and frees its key; it needs its predecessor, which anyone can delay, so it is never the escape hatch.
  • Audiences. Every keyed action says who may call it with only, quorum or authorized; open is not enough (JSC1246), and an action authorized by someone other than the retire’s signer warns (JSC9013).
  • Time. An insert or a removal relinks a node: its window is at most linkWindowMs long and starts at least linkCooldownMs after that node’s last relink (the runtime waits for it). linkCooldownMs = 0 warns (JSC9012). A key is never set from a time value (JSC1251).
  • Limits (the processor’s, JSC1244): no native assets, batched actions or BigMaps in a contract with keyed types; at most 16 keyed types; maxDatumBytes at most 2048, and a retired node’s worst case must fit it (JSC1250). Keyed objects do not move (JSC1247). The validator’s generated names are reserved (JSC1249: Link, Insert_m, Remove_T, Head_T, Keyed_T, Retired_T; the client’s tList, tExists, tKeys; the handle’s members; the parameters anchor, removed, instance).

Script purposes (ADR-0010, M3c). A handler runs when the contract’s script is used for a purpose other than a spend or a mint: withdraw for its own staking credential’s rewards, certify for a certificate, vote for its votes as a DRep or committee member, propose for a proposal. No instance is spent, so a handler reads only its parameters, the params and (a withdraw handler) the transaction, and the params say who may: quorum params.council params.n or authorized params.governor. The purposes’ data is the ledger’s: TxCert, Voter, Vote, GovernanceActionId, ProposalProcedure, GovernanceAction and the types they hold, with JuLC’s constructors and fields, read by a field or an exhaustive match; never stored, passed by a caller, encoded or compared (JSC1320–JSC1325). A LedgerMap<Credential, Int> (a treasury withdrawal’s, a committee update’s) is read-only: size, isEmpty, keys, values, get, has, any, all, fold. std/certs holds the exact certificate tests (isRegistration, delegatesOnlyTo, isDRepLifecycle); a vote delegation to a given DRep is a match over the delegatee. Two limits: ParameterChange.parameters is PlutusData in the ledger and is never read (JSC1320), so a constitution guardrail over proposed parameter changes stays in Java; and a handler reads no funds (JSC1315). A withdraw handler’s sends are Value.lovelace(n) written as such (JSC1340), each positive. stakeSelf and a withdraw handler are not accepted beside owned types yet (JSC1305).

A contract with a vote or propose handler compiles without a CIP-57 blueprint: JuLC’s blueprint writer has no vocabulary for those purposes yet, so pass -Ajulc.blueprint=false to compileJava, as examples/dsl and examples/staking do (every validator’s own <Name>Validator.plutus.json is still written).

Migration (ADR-0011 D4, M3c). An instance moves into its successor version in one transaction: the old version’s destroy upgrade() only admin migrates to successor { } (a Bytes or Hash state field the admin sets; never a params field, JSC1331) burns its token and moves its whole value, and the new version’s init migrate from params.previous(old: CounterV1.State) { … } mints the new instance for it, from the old state. A migrating destroy has no effects (JSC1332) and an audience (JSC1333). An action that writes the successor field warns (JSC9014: it can redirect the migration after users relied on it) unless it requires the field unset, require(successor == #, "the successor is set once"), which fixes it once; check then that the new successor is a 28-byte policy (require(length(next) == 28, …)), since a set-once successor of another length could never migrate (review F8). The adopting version imports a previous version that declares a migrating destroy (JSC1336), and its ordinary init never consumes an instance of that version: only init migrate adopts one.

Invariants (ADR-0009 D4) are checked by the validator on every state it accepts as an output (a creation and every action; a destroy has none), and by the runtime before it submits. A state that breaks one can only be destroyed.

quorum k t (ADR-0009 D2) holds when at least t ≥ 1 of the transaction’s signatories are in k, read from the input state, never the result. Every state the validator accepts as an output keeps each state quorum well formed (keys strictly ascending, so distinct, each 28 bytes, and 1 ≤ t ≤ their number), and a params quorum is checked at creation, so no rotation can lock the contract. authorized c (ADR-0009 D3) holds when the key credential c signed, or the script c is withdrawn from in the transaction with an Approvals redeemer listing (policy, instance, action) (a native script, which has no redeemer, approves through its withdrawal alone); never this contract’s own script or a JOUST verifier. Both are an audience (J16). Neither is allowed in an init (JSC0405) or a batched action (JSC0417), and neither field holds a time value (JSC0524). A contract with a quorum over state fields has no batched actions (JSC0440, ADR-0009 r3): a batch’s states are not checked, so a batched action could make the quorum unreachable; a quorum over params may be combined with them. quorum and authorized are modifier words only in a method’s header: a state field may be called quorum (quorum council quorum).

Modifiers name state fields (quorum and authorized also params.f), never parameters (JSC0310). Each is given at most once (JSC0416). A batched action cannot also have only, after or before (JSC0417): the batcher signs a batch and sets its window, so check the caller or the time in the body. A paying one says open (JSC0420): an intent authorises its action until its deadline, against the state a batcher applies it to, in the batcher’s order, so keep deadlines short and bound order-sensitive arguments. A contract with BigMap state cannot have batched actions (JSC0419). batched only followed by an identifier that is not a modifier reads as batched plus only f (then refused), and the modifier words are no field or binding name (JSC0211).

Composition (M2c, ADR-0011). A parameter p: reads params.f is the state of the instance the params field f (an Instance<C>) names, read from a reference input the validator authenticates (@Reads("params.f") C.State p, placed right after the params): in an action or a destroy (JSC0443), of a contract without BigMap state (JSC0451); the state is a checked input (#read:). A field the other contract sets from its own window is a time value: check staleness with require(before(p.updatedAt + maxAge)). An action that receives takes the deposits claimed on its output, funds.deposits (JSC0448 elsewhere), each with d.value and, for receives T, d.memo (each memo decoded and checked where the action starts: #memo:). It also takes Ctx.

What composition trusts. Nothing on chain binds an Instance<C> to C: the deployer who sets the params must point it at an instance of C (for a deposit, one whose contract receives), and a deposit into a script that ignores deposit claims is value the transaction’s builder can take. A read state is the datum of any script at that instance’s policy whose outer shape is C.State’s; its nested Bool, Option and enum tags are taken as C wrote them, which holds when C is a .jsc build (its validator refuses malformed tags in what it stores). A deposit may come from any input of the transaction, a wallet’s included, and its memo is the depositor’s claim, not proof of who deposited: credit by d.value, never grant anything by the memo alone.

Equality

Section titled “Equality”

== and != are defined on Int, Bool, Bytes, Key, Hash, lists, maps, options, records and enums whose components are comparable. They lower to generated helpers: field by field, ByteStringLib.equals on bytes, compareTo == 0 on integers, element by element on lists and maps, tag then fields on enums and options. No .jsc equality is Java equals or a reference comparison. xs.contains, indexOf, m.get, m.has use the same rules. A BigMap, or a state holding one, is not comparable (JSC0812): it is a witness of a Merkle root, not its contents.

Laziness

Section titled “Laziness”

Only the taken arm of if, match and ?:, the needed side of && and ||, and the default of ?? when the option is empty run, on the JVM and on chain. A division, a failing require or a map read in an untaken branch never happens.

Values and funds

Section titled “Values and funds”

A Value is a multi-asset value: quantities by (policy, token name), lovelace under the empty policy and name. It is canonical in the ledger’s order, and every quantity stays within the signed 128-bit range; an operation that would leave it fails, as the ledger’s builtins do on-chain.

Expression Meaning
Value.none(), Value.lovelace(n), Value.asset(policy, name, n) the empty value; lovelace; a token (policy a Hash, name at most 32 bytes)
v + w, v - w, v == w, v != w entry by entry; equality of entries
v.lovelace, v.of(policy, name) a quantity, 0 when absent
v.covers(w) v holds at least w of every entry (fails on a negative quantity)
isEmpty(v), withoutLovelace(v), scale(k, v) from std/value
paymentKey(a), paymentScript(a) from std/address: the key or script an address pays to, as an Option

funds is the native assets a call sees, in an init, action or destroy: funds.received (what the caller offers, no lovelace: that is received), funds.held (what the instance holds besides lovelace and its own token), funds.policy (the contract’s policy) and funds.self (the instance’s token name). A method that reads funds, or sends, mints, burns, accepts or receives, is lowered with the processor’s Funds parameter. funds.deposits (M2c) is a receiving action’s deposits.

Stored values (M2c). A field of the state, the params, a record or a variant may be a Value. It is stored in its wire form (cardano-client-lib’s canonical order) and read back in the ledger’s: the lowering converts where the field is read (ValueAdapter.fromWire, which also refuses a malformed one) and where the record is built (ValueAdapter.toWire), so the datum the validator compares is the one the runtime writes.

Effects and audiences

Section titled “Effects and audiences”
Statement Effect Generated check (key)
pay(to, n) a payout of n lovelace to the key to; 0 is skipped n is not negative (#pay:)
send(to, v), send(to, v, d) an output of v to the address to; M2c: with the inline datum d, any value of the contract’s own types, built by a generated encoder every quantity positive, no reserved name of the own policy, never to the contract’s own script (#send:)
deposit(i, v, m) M2c (ADR-0011 D3): v into the instance i (an Instance<C> from the params), which C’s receiving action takes in the same transaction; m the memo, any value of the contract’s own types v not empty, every quantity positive, no reserved-kind name under any policy (#deposit:). mint(name, n), burn(name, n) n more, or fewer, of the own policy’s name; the net is what the transaction mints n positive, name a user token of at most 32 bytes (#mint:)

emit(e) an event (a value of the contract’s Event), in source order none in the method; the validator requires the redeemer to carry exactly these events (ADR-0009 D5)

Each kind accumulates in source order (in a for, in list order; an effect in an untaken branch does not happen); mint and accept are net sums. An init takes no effect but may read funds (JSC0404; accept in an init is not supported yet, JSC0426). accept needs payable (JSC0422), and a payable method that reads funds, sends, mints or burns must state what it takes in, accept(Value.none()) for nothing (JSC0423). A method that can reach a pay, send, mint, burn or deposit in any arm or loop must have only <field> or open (JSC0408). A deposit alone takes no Funds (a payable method that only deposits takes ADA). An action that deposits returns Outcome with deposits; a destroy that deposits returns Settled. A contract with native assets has no batched actions (JSC0424). An action with effects returns Outcome, or Received when it takes native assets; a destroy that sends, mints, burns or emits returns Settled (the processor’s result records). A batched action never returns events: when a direct action’s Outcome holds them, a batched action that pays returns Stepped(state, payouts). These names, and the annotations the lowering imports (Invariant, Params, Quorum, AuthorizedBy), are reserved. Events (M2b) come last in each record, and a method whose record has them carries them last in its redeemer (empty when it emits none). An emit is allowed in an action or a destroy (JSC0413), not in a batched action (JSC0425); the contract must declare an event (JSC0438).

Time (D11)

Section titled “Time (D11)”

validFrom and validTo are the only sources of time values. A value is a time value if it depends on one through any expression (min, max and abs included), a const, a fn argument, a record, list, map or option, a lambda or match binding, or a time field: a state field any method sets to a time value, contract-wide (the ABI manifest lists them as timeFields).

  • Deciding. A time value may not be a condition of if, ?: or require, an operand of &&, || or !, a collection predicate, or a comparison whose result is used (JSC0502, JSC0514). The only comparisons with time are after(t) and before(t), which hold for the whole window and are allowed only as the condition of a require or an operand of && or || at its top (JSC0506); never under !, in an if, a ?:, a const, a fn or a lambda (JSC0504), nor in a view (JSC0503). t may be a stored time, but not one computed from this call’s window (JSC0505: after(validFrom - 1)).
  • Shapes are never time values: a value’s constructor, an option’s presence, a list’s length and a map’s keys. So match may scrutinise a value holding a time value (its bindings stay time values), and xs.isEmpty, m.has(k) and == None are ordinary.
  • Failing. A time value may not be a divisor (JSC0515), a domain-checked std argument (JSC0509), a map key (JSC0517), a range bound (JSC0516), a take/drop count (JSC0512), an nth index (JSC0510), a Key or Hash conversion (JSC0507), a BigMap<K, Int> value (JSC0518), a Value’s quantity (JSC0519), any part of a sent or accepted value (JSC0520, JSC0522) or a mint or burn quantity (JSC0521), and it never decides whether paymentKey or paymentScript is Some (JSC0523). A field that holds a time value is never a quorum’s keys or threshold or an authorized credential (JSC0524), and an invariant never depends on one (JSC0525). A fn called with a time argument is checked with that parameter as a time value.
  • Flowing. Arithmetic on time values is allowed, and they may set state and amounts. A payout set by one must be exactly pay(to, max(0, …)) (JSC0501). Warnings name the bias: a stored window value (JSC9003), a value derived from a stored time (JSC9004), a payout (JSC9005), an event that carries one (JSC9008).

The submitter chooses the window, within maxValidityMs: validFrom can be that much early, validTo that much late. For accrual that pays the caller, measure from validFrom (elapsedSince(t)); for a charge the caller pays, from validTo (elapsedSinceAtMost(t)).

BigMap rules

Section titled “BigMap rules”
  • A field of the state only (JSC0803), with Int or Bytes values (JSC0804).
  • Its new value is its own field transformed by set and delete, in that field of the next state: { ...state, balances: balances.set(to, v) } (JSC0811, JSC0827). set and delete appear nowhere else.
  • Never bound to a const, passed to a fn, held in an option or a list, captured by a lambda (JSC0814), compared, chosen by a condition or match, or used as a fold accumulator (JSC0813). A state whose BigMap is written is never bound, chosen or accumulated either.
  • BigMap.empty() only as a field’s value in an init (JSC0810, JSC0817); m.isEmpty (“empty before this call”) only in a destroy (JSC0808).
  • Int values are non-negative and set(k, 0) removes the entry; an Int value is stored in at most 8,192 bytes. BigMap<K, Bytes> tells absence from empty bytes. Keys of set and delete are at most 64 bytes.
  • A method reads its own writes through the chain: balances.set(caller, left)[to].

Every read and write is proven against the root by the shared map verifier (MerkleMaps).

Libraries

Section titled “Libraries”

A file headed library <package> is a .jsc library (ADR-0018 D9): imports, types, enums and fns, and no contract (JSC0711). Contracts and other libraries import from it by its path relative to the importing file:

Rule
The class A library lowers to a JuLC @OnchainLibrary class of its package, named by its file: fees.jsc is app.Fees (JSC0705 when the file name makes no class name). Its fns are public static, its types nested records and sealed interfaces (Fees.Line, Fees.Tier), so Java contracts call it as they call any on-chain library (examples/dsl’s JavaShop.java). Its generated helpers are package-private, named with __. A Java caller skips .jsc’s ingress checks: the library’s fns assume a Key of 28 bytes, a Hash of 28 or 32 and canonical maps, which only .jsc callers guarantee, so a Java contract that builds new Fees.Line(bytes, …) checks those lengths itself
Imports ./x.jsc and ../dir/x.jsc, resolved from the importing file and never outside the source folder (JSC0706). Only a library can be imported (JSC0708), and only names it declares (JSC0708). Libraries may import libraries, without cycles (JSC0707)
Scope A file sees its own declarations and the names it imports; importing an enum brings its variants. A library’s other declarations are not in scope (JSC0710), but its values flow: a fn may return a record whose type the caller did not import, and the caller reads its fields. std imports are per file
One namespace The declarations of a build (a contract and every library it imports, transitively) share one namespace: no two of them, in any of its files, have the same name (JSC0709), and none takes a library’s class name. No binding (a parameter, const, lambda parameter or match binding) takes a library’s class name either, and two libraries of a build never share a file name, even in different packages (JSC0709): the generated Java names a library by its class. A method of the contract named like a library variant is refused as for its own (JSC0203). Known limit: two third-party libraries that declare one name cannot be combined, as there is no aliasing yet
Checking A library is checked on its own, and again in each contract that imports it. The time rule (D11) runs through library calls: a library fn called with a time value is checked with that parameter marked, so a division or a require on it is refused at the call. An error in a library is reported at the import that brings it into the build, naming the library’s own position (JSC0712)
Inputs A library’s types are checked inputs like the contract’s: a Line in a redeemer has its Key checked to 28 bytes before the method runs
Artifacts A library has no ABI manifest of its own: each contract’s manifest states the library types its datum and redeemers reach ("kind": "library", with the library’s class). Each contract’s IR export carries the libraries it imports (format 2), so the JavaScript reference interpreter evaluates their fns, and its message map lists a library’s messages with the library’s file ("file": "fees.jsc")
Identity A library’s package and file name are its class, which importing files and Java contracts name: renaming either is a code change of every importer, and may change the scripts that use it: JuLC’s shape-check ids follow library class names (JuLC ADR-078)

Library packages and joust.lock

Section titled “Library packages and joust.lock”

An npm package ships libraries under its joust-lib/ folder: .jsc libraries, and the on-chain sources of Java libraries (joust-lib/<package path>/<Class>.java). A .jsc file imports a package’s .jsc library by the package name and the path under joust-lib/, and a Java library by its class:

A package library’s own relative imports stay inside its package (JSC0706). A Java library from a package is certified like one from Gradle’s joustLibrary, and the same codes apply. Of a package’s Java sources, a build compiles only the source closure of each library a .jsc file imports with java: or a hand-written Java contract imports; no other package source reaches the build. Links under joust-lib/ are not followed, and two packages that ship one Java path are refused, as is a library that declares a class in one of the project’s own packages.

joust.lock (committed at the project’s root) pins every library that comes from outside the project’s sources by the SHA-256 of its on-chain sources: a package’s .jsc library (with the libraries it imports), or a Java library’s source closure (every source file its class’s file names, transitively; keyed by its path inside joust-lib/), whether a .jsc file imports it with java: or a hand-written Java contract imports it (ADR-0018 J12). joust build lists every library it used with its hash. It fails with JSC0731 when such a library is not pinned, and with JSC0732 when its sources differ from the pin. Review the library, then run joust build --accept-lock, which writes the lock to commit. The project’s own .jsc libraries are part of its sources and are not pinned. On Gradle, generateJsc checks joust.lock for the joustLibrary libraries, and acceptJoustLock writes it.

Java libraries (java:)

Section titled “Java libraries (java:)”

A .jsc file may import the public static methods and records of a Java (JuLC) on-chain library whose on-chain sources are on the library path and certified (ADR-0018 D9, M4b):

On Gradle, the library’s jar goes in the joustLibrary configuration, as sources only:

The build extracts the library’s META-INF/plutus-sources, compiles them into the project (the JVM side runs these sources, never the jar’s classes), and certifies them before any import is admitted. Certification covers:

  • each signature’s exact Java types, mapped to .jsc or refused;
  • every reachable body, checked with SubsetLint;
  • no casts and no reference equality;
  • only calls into the trusted base (D8’s table, JOUST’s Require and adapters, an allow-list of BigInteger, JulcList, JulcMap and Optional operations);
  • none of the catalogue of known JVM/on-chain differences.

checkJoustLibraries fails when a library class also reaches the runtime class path from a jar. When a contract is loaded, the runtime checks the bytes of each library class against the build’s.

Rule Code
No sources of the class on the library path JSC0720
The library is not certified (each problem, with its file and line) JSC0721
A fn whose signature does not map (PlutusData, maps, values, void, generics, fixed-width numbers) JSC0722
An overloaded name JSC0723
A Java record is read-only: built by the library’s fns, never by an object literal JSC0724
An opaque record (a field that does not map) is never written as a type, read or compared JSC0725

byte[] maps to Bytes (a Java signature cannot say Key): make a Key of a result with asKey(b). The reference interpreters do not evaluate a Java library’s body: a call that reaches one has no answer there, and such calls are differential-tested on the JVM, the transition program and the validator, beside the library’s own per-function vectors. The details, and the catalogue, are in jsc-2-java-libraries.md.

The ABI manifest

Section titled “The ABI manifest”

For every .jsc contract the lowering writes <Contract>.abi.json (format "abi": 2), which the project commits beside the .jsc file:

Key Content
contract, source the qualified contract name and the .jsc file
datum the State constructor, its fields in order, each with its .jsc type and data shape
params (M2b) the Config constructor the script is applied to, when the contract declares params
redeemers.spend one constructor per action, then per destroy, in source order, with its index and fields (the generated ctx, M2’s assetsIn and M2b’s events included)
redeemers.mint CreateInstance (seed, ctx) and BurnInstance
types every schema the datum and the redeemers reach: records, enums, imported library types ("kind": "library", with the library’s class), and API and ledger types such as Ctx, TxOutRef, MerkleMap
timeFields the state’s time fields

Views are not encoded, so moving or adding a view does not change the manifest.

The gate. Every build compares the lowering’s manifest with the committed one. Equal passes. A missing manifest fails with JSC0003; a different one with JSC0002, naming the first line that differs; and Java lowered from a file whose manifest is refused is not written. The only ways to accept a new or changed manifest are explicit:

Path Accept
npm joust build --accept-abi, joust dev --accept-abi
Gradle (plugin org.julclang.joust) ./gradlew acceptJscAbi
JVM JscMain <srcDir> <outDir> --accept-abi

No Gradle property, system property or gradle.properties line switches the gate off. Review the diff and commit the manifest: a change means a deployed instance’s datum or redeemers would be read differently, so the new contract must be deployed as a new script.

The cross-check. Each manifest is also compared, structurally, with the processor’s description of the same contract (constructor indices, field names and order, data shapes, every reachable schema): at every npm build, and on Gradle in checkJscAbi, after compileJava, as part of check. A difference is JSC0004, an internal error of the lowering; please report it.
