<Aside type="caution" title="Experimental">
The npm path runs JOUST's toolchain and runtime as WebAssembly built with GraalVM Web Image, which is itself experimental. Java with Gradle and cardano-client-lib is the supported, first-class path: see [Quick start: Java](/start/quick-start-java/).
</Aside>

This page takes you from an empty folder to a Cardano contract you can call from Node and from a browser page, with
Node and npm only: no JDK, no Gradle, no GraalVM. The contract is written in JOUST's [.jsc](/languages/jsc/) language
(or in Java), and `joust build` compiles it with a toolchain engine that runs as WebAssembly in Node.

You will:

- create a project with `npm create joust`: a `Counter` contract and a short Node script that calls it;
- build the contract into a validator and a typed JavaScript client;
- deploy it on a local network (Yaci DevKit) and call it from the script and from a test;
- then create the browser version, connect a wallet and call the contract from a page.

## Prerequisites

- **Node 22 or newer.** The engines need Wasm exception references, which the runtime switches on itself on Node 22.
- **Yaci DevKit**, a local Cardano network, started with its indexer, Yaci Store:

  ```sh
  yaci-devkit up --enable-yaci-store
  ```

  This gives a Blockfrost-compatible chain API on `http://localhost:8080/api/v1`, DevKit's admin API (slot clock,
  faucet) on `:10000`, and the Yaci Viewer explorer on `http://localhost:5173`.
- **The JOUST npm packages**, from a local registry until they are published (see below).

<Aside type="caution" title="Pre-release: the npm packages come from a local registry">

`@julclang/joust`, `@julclang/joust-runtime`, `@julclang/state-client` and `create-joust` are **not released yet**
(npmjs.org holds only placeholders). Once they are, `npm create joust@latest my-app` is all you need. Until then,
publish them to a local registry from a JOUST checkout:

```sh
# in a JOUST checkout: builds both Wasm engines, then publishes the four packages to http://127.0.0.1:4873/
./gradlew npmPublishLocal -PgraalvmHome=/path/to/graalvm
# later, with the engines already built:
bash js/publish-local.sh
```

The script starts [Verdaccio](https://verdaccio.org/) with `js/verdaccio/config.yaml` if no registry answers on
`:4873`, so `verdaccio` must be on your `PATH`. Building the engines is the only step that needs a JDK and GraalVM;
your app never does. Every other package is proxied from npmjs.org, so one registry setting is enough:

```sh
export npm_config_registry=http://127.0.0.1:4873/
```

</Aside>

## Create and build the app

<Steps>

1. **Create the project.** The package version is part of the command until the packages are released (then it is
   `npm create joust@latest my-app`):

   ```sh
   npm create joust@0.1.0-pre1-snapshot my-app
   cd my-app
   npm install
   ```

   `create-joust` writes a `Counter` contract in `.jsc` (`contracts/app/Counter.jsc`) and a Node script that calls it
   (`index.js`), and names the package after the folder. It refuses a folder that is not empty. Two options change
   what it writes (after `--`, as `npm create` passes them on):

   | Option | Values |
   |---|---|
   | `--lang` | `jsc` (the default) or `java`: the same counter in Java, `contracts/app/Counter.java` |
   | `--template` | `node` (the default): `index.js`; `web`: a browser page instead ([below](#a-browser-page)) |

   ```sh
   npm create joust@0.1.0-pre1-snapshot my-app -- --lang java
   ```

   The contract is the same in both languages:

   ```jsc title="contracts/app/Counter.jsc"
   jsc 2
   package app

   contract Counter(maxDatumBytes = 128) {
     state { count: Int, owner: Key }

     init() {
       return { count: 0, owner: caller }
     }

     action increment(by: Int) {
       require(by > 0, "increment must be positive")
       return { ...state, count: count + by }
     }

     action reset() only owner {
       return { ...state, count: 0 }
     }

     destroy close() only owner {
       pay(owner, balance)
     }

     view count(): Int = count
   }
   ```

   It is written in `.jsc` 2, a preview ([.jsc](/languages/jsc/)). Beside it, `create-joust` writes
   `Counter.abi.json`, the contract's ABI manifest: how its state and its calls are encoded on chain. A build fails
   when the manifest is missing or differs from what the contract now compiles to, so an encoding change cannot slip
   through; `npx joust build --accept-abi` accepts a change you intend, to review and commit.

   `joust build` generates the same description and the same JavaScript client from `Counter.jsc` as from
   `Counter.java`, so nothing else in the project depends on the language.

2. **Build the contract.**

   ```sh
   npm run build
   ```

   `joust build` compiles every `.java` and `.jsc` file under `contracts/` into `build/joust/`:

   ```txt
   app.Counter: … bytes, hash …, 4 transitions
   built 1 contract(s) into build/joust in … ms
   ```

   The size and hash depend on the contract, its language and the toolchain's version. The four transitions are the contract's
   four methods (`init`, `increment`, `reset`, `close`), compiled so the runtime engine can run them off chain.

3. **Deploy it on DevKit.**

   ```sh
   npm run deploy
   ```

   `joust deploy` publishes the validator as a **reference script**: a UTxO that carries the script, so later
   transactions point to it instead of including it. (A UTxO, an *unspent transaction output*, is a coin on Cardano:
   an address, a value and optional data. See the [glossary](/reference/glossary/).) On DevKit it pays with a key it
   makes and keeps in `.joust/devkit-wallet.json`, topped up from DevKit's faucet. It writes what it published to
   `build/joust/deployments.devkit.json`:

   ```json title="build/joust/deployments.devkit.json"
   {
     "network": "devkit",
     "networkId": 0,
     "chain": "http://localhost:8080/api/v1",
     "clock": { "zeroSlot": 0, "zeroTimeMs": 1793975371000, "slotLengthMs": 1000 },
     "contracts": {
       "app.Counter": {
         "contract": "app.Counter",
         "policy": "572399fa2a90a0452c3b29da48af6b90905ac8cfb503e1af803c942c",
         "address": "addr_test1wptj8x0692g2q3fv8v5a5j90dwgfqkkge76s8cd0sq7fgtq9nldys",
         "networkId": 0,
         "referenceScripts": ["1e4834390dae0f76de76b65d83b0f15fd99b7eb7d2e1da50e0cb1e7c10bd15c0#0"]
       }
     }
   }
   ```

4. **Run the script.**

   ```sh
   node index.js
   ```

   ```txt
   wallet      addr_test1qzsnkv3kupara60hylhrxc26ga5dn42mhc92ehmmzjzayjmdsj2justfnutk5my5a7xcdem62trnx0968tflw2mgswssjma7mj
   created     50c92ecfef4443fb9010be5e06d6a4ac24f2943a5a0f0a49ae16d239bb3247d6 tx 3c81eceba21fc5624fb0632c6268c220cba9758771e50a64b5cdb30c439560f4
   increment 5 tx bf03fd41a39d3298e6dcd5550ee2422b30477738af255552bd02dc71bb6b5670
   increment 2 tx 132896a73abd88de4f3791c821ff2ee3529132f8239ebd890af12dcde5009272
   count       7n
   refused     increment must be positive
   closed      tx 9421540ed8a497c54734d29dcd0700246f5c653296d6da4fde9ab52b02ca9081
   state       null
   ```

   `npm start` runs steps 2 to 4 in one go. `index.js` is the whole app:

   ```js title="index.js (abridged)"
   import { joustRuntime, devWallet, devkitTopUp } from '@julclang/joust-runtime';
   import { Counter } from './build/joust/Counter.js';   // generated by `joust build`

   const rt = joustRuntime({
     chainUrl: deployed.chain, networkId: deployed.networkId, clock: deployed.clock, ttlMs: 20_000,
     contracts: read('build/joust/contracts.json'), deployments: deployed.contracts,
   });
   // A throwaway wallet, funded with 100 ADA by the DevKit's faucet.
   const wallet = devWallet({ chain: rt.chain, mnemonic: generateMnemonic(wordlist, 256) });
   await devkitTopUp(wallet.address, 100, config.networks.devkit.admin, { chain: rt.chain });

   const counter = new Counter(rt.options('app.Counter'));
   const { instance } = await counter.deploy(wallet, {});        // init: a new counter, owned by this wallet
   await instance.increment(wallet, { by: 5n });                 // anyone may call it
   console.log((await instance.state()).count);                  // read from the chain
   await instance.increment(wallet, { by: 0n });                 // throws: increment must be positive
   await instance.close(wallet);                                 // owner only; the deposit goes back to the owner
   ```

   Each call runs the contract's own code in the runtime engine to compute the next state, builds the transaction,
   signs it with the wallet's key and submits it. On chain, the validator runs the same code again and checks the
   result. `counter.deploy()` creates a counter (the contract's `init`); `joust deploy` published the contract.

5. **Run the test.**

   ```sh
   npm test
   ```

   `test/counter.test.js` makes the same calls with `node:test` and checks each result: the count is 7, an increment
   of 0 is refused, and the counter is gone after `close`.

</Steps>

## The project

<FileTree>

- contracts/
  - app/
    - Counter.jsc the contract (Counter.java with --lang java)
    - Counter.abi.json its ABI manifest (.jsc only)
- index.js the app: deploys a counter and calls it
- test/
  - counter.test.js a Node test on DevKit
- build/ written by joust build and joust deploy
  - joust/
    - generated/ the Java lowered from Counter.jsc, with its source map
    - Counter.js the typed client, with the contract's description pinned
    - Counter.d.ts its TypeScript types
    - Counter.json the description
    - Counter.plutus the compiled validator (CBOR hex)
    - contracts.json what the runtime engine needs
    - deployments.devkit.json what joust deploy published
    - joust.lock.json the versions that built it
- joust.config.json contracts, output and networks
- package.json

</FileTree>

In `.jsc`, a contract is its `state` and its `init`, `action`, `destroy` and `view` declarations; `joust build`
lowers it to a Java contract and compiles that ([.jsc](/languages/jsc/)). In Java, it is a `State` record and static
methods marked `@Init`, `@Action`, `@Destroy` and `@View`, in the subset JuLC compiles
([Your first contract](/start/first-contract/)). `package.json` holds these scripts:

| Script | Runs | What it does |
|---|---|---|
| `npm start` | `joust build && joust deploy && node index.js` | build, deploy (once per script) and run the app |
| `npm run build` | `joust build` | compile `contracts/` into `build/joust/` |
| `npm run deploy` | `joust deploy` | publish the reference scripts on the config's network (DevKit) |
| `npm test` | `node --test test/*.test.js` | the Node tests |

## A browser page

`--template web` makes the same project with a page instead of `index.js`:

```sh
npm create joust@0.1.0-pre1-snapshot my-web-app -- --template web
cd my-web-app
npm install
```

<FileTree>

- contracts/
  - app/
    - Counter.jsc the same contract
    - Counter.abi.json its ABI manifest
- page/
  - index.html the Counter page
  - main.js the page's code: wallet, review dialog, calls
  - engine.worker.js the runtime engine, in a Web Worker
- test/
  - counter.test.js a Node test on DevKit
- joust.config.json
- vite.config.js the page's Vite config, with @julclang/joust/vite
- package.json

</FileTree>

The [Counter dApp tutorial](/tutorials/counter-dapp/) walks through every file. Its `package.json` has these scripts:

| Script | Runs | What it does |
|---|---|---|
| `npm run build` | `joust build` | compile `contracts/` into `build/joust/` |
| `npm run deploy` | `joust deploy` | publish the reference scripts on the config's network (DevKit) |
| `npm run deploy:preview` | `joust deploy --network preview` | the same on the preview testnet |
| `npm test` | `node --test test/*.test.js` | the Node tests |
| `npm run dev` | `joust dev` | build, deploy, serve the page; rebuild and redeploy on save |
| `npm run dev:preview` | `joust dev --network preview` | the same on preview |
| `npm run build:page` | `vite build` | the page as static files in `dist/` |
| `npm run build:page:preview` | `vite build --mode preview` | the same, for preview |
| `npm run serve` | `joust serve` | serve `dist/` with the chain API at `/chain` |
| `npm run serve:preview` | `joust serve --network preview` | the same on preview |

### Open the page

```sh
npm run dev
```

`joust dev` attaches to DevKit, builds and deploys, then serves the page at **http://127.0.0.1:5178**. It keeps
watching `contracts/`: save `Counter.jsc` and it rebuilds and redeploys.

<Steps>

1. Wait for the activity log to say *Runtime engine ready*. The page loads JOUST's runtime engine (about 20 MB of
   Wasm) into a Web Worker once per page load, and prepares its own transactions with it.

2. Choose **DevKit key (in this page)** and press **Connect**. Browser wallets cannot join a private devnet, so on
   DevKit the page offers a key it keeps in `localStorage`. Press **Top up 1000 ADA** to fund it from the faucet.

3. Press **Create a counter**. A dialog shows what the page checked in the prepared transaction: the redeemer is this
   call on the pinned script, what your wallet pays in all, the next state, and that nothing else is in it. Press
   **Sign in the wallet**.

4. Press **+1** a few times. Then press **+0**: the contract refuses it (`increment must be positive`) while the
   transaction is being prepared, so no wallet is ever asked to sign.

5. Press **Close**. Only the owner can close; the counter's deposit comes back to your wallet.

</Steps>

Each transaction hash in the log links to Yaci Viewer, DevKit's explorer.

### Build the page as static files

```sh
npm run build:page   # vite build -> dist/
npm run serve        # dist/ at http://127.0.0.1:5178, with the chain API at /chain
```

A build is for one network: the network, its deployments, the contracts and the engine's integrity hashes are inlined
into the page, and the engine's two files are copied into `dist/joust/engine-<id>/`. `joust serve` serves `dist/` as
plain files, adds the chain API at `/chain` (and DevKit's faucet), and does nothing else: no build, no deploy, no
prepare service. See [Pages](/apps/pages/).

<Aside type="note">
DevKit's slot clock changes when DevKit restarts. After a restart, run `npm run deploy` and `npm run build:page`
again.
</Aside>

### Use TypeScript

The page can be TypeScript. Vite compiles `.ts` files (it does not type-check them), so renaming is enough to run:

```sh
mv page/main.js page/main.ts
sed -i.bak 's#./main.js#./main.ts#' page/index.html && rm page/index.html.bak
npm install --save-dev typescript
```

The generated client is typed already: `npm run build` writes `build/joust/Counter.d.ts` beside `Counter.js`, with a
type for every state, argument and result. A call with a wrong argument name fails to compile:

```ts
await counter.at(id).increment(wallet, { amount: 1n });
// error TS2353: Object literal may only specify known properties, and 'amount' does not exist in type '{ by: Int; }'.
```

Two modules a page imports ship no declarations yet (`virtual:joust/network` and `@julclang/joust-runtime/page`).
Declare them in `page/joust-env.d.ts`, add a `tsconfig.json`, and type-check with `npx tsc --noEmit`: the
[TypeScript page](/languages/typescript/#typing-a-page) has both declarations and a typed `main.ts`, checked with
`strict` on. The template's `main.js` is plain JavaScript: under `strict` it needs parameter types before `tsc` passes.

### Try it on preview with Eternl or Lace

Preview is a public Cardano testnet, so real browser wallets work there. You need a Blockfrost project id for
preview and a funded preview key to pay the deployment:

```sh
export BLOCKFROST_PREVIEW_PROJECT_ID=preview...   # stays in the dev server; never reaches the page
export JOUST_MNEMONIC="..."                       # a funded preview key that pays the deployment
npm run dev:preview
```

Switch Eternl or Lace to preview, reload the page, choose it in the wallet list and connect. The
[Deploy to preview](/tutorials/deploy-preview/) tutorial covers this and static hosting step by step.

## What you just used

- **The toolchain engine** (in `@julclang/joust`) compiled `.jsc` or Java to a Cardano validator, a description and a
  typed client, in Node.
- **The runtime engine** (in `@julclang/joust-runtime`) prepared each transaction from the chain, in Node for the
  script and the test, and in a Web Worker for the page. It holds no keys.
- **The page verifier** (in `@julclang/state-client`) checked every prepared transaction against the contract's
  description and the chain before the wallet was asked to sign.
- **The validator** re-ran each method on chain and checked that the new state is what the method computes.
