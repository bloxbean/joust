<Aside type="caution" title="Experimental">
The npm path runs JOUST's toolchain and runtime as WebAssembly built with GraalVM Web Image, which is itself experimental. Java with Gradle and cardano-client-lib is the supported, first-class path: see [Quick start: Java](/start/quick-start-java/).
</Aside>

`@julclang/joust` is JOUST's command line and Vite plugin. It carries the **toolchain engine**: JOUST's annotation
processor and JuLC's compiler, compiled to Wasm, which build `.java` and `.jsc` contracts in Node exactly as the
Gradle build does. Source: [`js/joust`](https://github.com/bloxbean/joust/tree/main/js/joust). For a guided tour, see
[The joust CLI and projects](/apps/cli-and-projects/).

<Aside type="caution" title="Pre-release: from a local registry">
Version `0.1.0-pre1-snapshot`, not on npmjs.org yet: install it from a local registry, as the
[npm quick start](/start/quick-start-npm/#prerequisites) shows. Node 22 or newer.
</Aside>

| Entry point | Contents |
|---|---|
| bin `joust` | the CLI |
| `@julclang/joust` | `build`, `deploy`, `loadConfig`, `network`, `loadToolchain`, `VERSION` (the commands as functions) |
| `@julclang/joust/vite` | the Vite plugin, `joust(options)` (also the default export) |

## Commands

Every command reads `joust.config.json` from the working directory (see [`joust.config.json`](/reference/config/)).
`--network <name>` defaults to the config's `network` (`devkit`).

| Command | Flags | What it does |
|---|---|---|
| `joust build` | `--src <dir>` (default config `contracts`), `--out <dir>` (default config `out`), `--accept-abi`, `--accept-lock`, `--traces` | compiles every `.java` and `.jsc` file under the source folder into the output folder, with the libraries of the project's npm packages (`joust-lib/`); exits 1 on a compile error, on a `.jsc` 2 ABI manifest that is missing or changed unless `--accept-abi` writes it ([the ABI manifest](/languages/jsc/#the-abi-manifest)), or on a library from a package that `joust.lock` does not pin at its hash unless `--accept-lock` writes it ([library packages](/languages/jsc-reference/#library-packages-and-joustlock)). `--traces` keeps the contracts' traces in the scripts (larger scripts; for debugging) |
| `joust test` | `[-- <node --test args>]` | builds, then runs `test/*.test.js` with Node's test runner (one file at a time). Tests that use `@julclang/joust/test` run offline: see [offline tests](#offline-tests) |
| `joust migrate` | `[<file.jsc>…]`, `--in-place` | translates `.jsc` v1 files (with no file named, every v1 file under the contracts folder) to `.jsc` 2, written to `build/joust/migrated/<same path>`; `--in-place` replaces each v1 file and keeps its text as `<Name>.jsc.v1`. Refusals are `JSC11xx` errors ([migration](/languages/jsc-migration/)) |
| `joust deploy` | `--network <name>` | publishes each contract's reference script (once) and writes `<out>/deployments.<network>.json` |
| `joust dev` | `--network <name>`, `--port <port>` (default config `dev.port`, else 5178), `--accept-abi` | attaches to the chain (starting it with the network's `start` command if needed), builds, deploys, serves the page; rebuilds and redeploys on save |
| `joust serve` | `--network <name>`, `--dir <dir>` (default `dist`), `--port <port>` (default as `dev`) | serves a built page as static files, with the chain API at `/chain` and on DevKit the faucet |
| `joust version` | (also `joust --version`, `-V`, `-v`) | prints `joust <version> (npm)` |
| `joust help` | (also `--help`, `-h`, `<command> --help`) | the usage; never runs a command |
| `joust new` | | prints the `npm create joust` command to run (Gradle projects come from the native `joust`); creates nothing |

In a project, a project command (`build`, `test`, `migrate`, `deploy`, `dev`, `serve`) runs at the project's root (the nearest directory
with `joust.config.json`, or a `package.json` that depends on `@julclang/joust`), and by the project's own
`@julclang/joust`: a global or other copy hands over to it, as [the native `joust`](#the-native-joust) does.

`joust` with no command prints the usage; an unknown command prints it and exits 1. Errors are printed as
`joust: <message>` with exit status 1. `joust dev` and `joust serve` bind to `127.0.0.1` and stop on `SIGINT` or
`SIGTERM`.

### Outputs of `joust build`

| File | Content |
|---|---|
| `contracts.json` | `[{ description, script, transitions, built: { joust } }]` for the runtime |
| `<Contract>.json` | the description (CIP-57 + `x-joust`, version 2) |
| `<Contract>.plutus` | the validator, CBOR hex |
| `<Contract>.js`, `<Contract>.d.ts` | the typed client and its types |
| `generated/<package path>/<Contract>.java`, `.jscmap.json` | the Java a `.jsc` file lowered to, and its source map (`.jsc` only) |
| `validators.json` | plain JuLC validators: `[{ name, package, purpose, script, scriptHash, params, built }]` (only if there are any) |
| `<Validator>.plutus` | each plain validator's script, parameters not applied |
| `joust.lock.json` | `{ joust, descriptionVersion, contracts: { <title>: { scriptHash } }, validators? }` |

### Offline tests

`@julclang/joust/test` runs a project's contracts without a chain (ADR-0018 D14):

```js
import { offline } from '@julclang/joust/test';
import contracts from '../build/joust/contracts.json' with { type: 'json' };
import { Counter } from '../build/joust/Counter.js';

const net = await offline({ contracts });
const owner = await net.wallet(100);                       // a funded key wallet, in ADA
const counter = new Counter(await net.options('app.Counter', owner));
const { instance } = await counter.deploy(owner, {});
await instance.increment(owner, { by: 5n });
assert.deepEqual(net.ledger.acceptedAttacks(), []);        // every mutation of the offline attack suite was refused
```

`net.ledger` is an in-memory ledger behind the same provider interface as Yaci Store or Blockfrost. Before it applies
a transaction it checks these phase-1 rules (each refusal names the node's error):

- the transaction is tagged valid, is at most `max_tx_size` bytes, and its inputs, reference inputs and collateral exist
  and are unspent;
- the validity interval holds at the ledger's slot (`ledger.advance(ms)` moves its clock);
- withdrawals come from registered reward accounts and take exactly their balance (always 0: no rewards are paid);
- the transaction balances, with the fee and the deposits, and every output holds its minimum ADA;
- the fee is at least the size's, the declared execution units' and the reference scripts' fee;
- every key that must sign has a verifying witness, every script credential that must authorise (a script-locked input,
  a mint policy, a script withdrawal or certificate) has its script, witnessed or referenced; native scripts are
  evaluated; each Plutus purpose has a redeemer and no redeemer is extra; a spent datum hash has its datum;
- with Plutus scripts: the collateral is key-locked, at most `max_collateral_inputs`, ADA only unless returned, at least
  `collateral_percent` of the fee, and matches `total_collateral` when it is declared; the script integrity hash
  matches; the declared units are within the per-transaction limit;
- phase 2: every Plutus script that must run, evaluated by the runtime engine (`joust.evaluate`, the evaluator that
  prices transactions), within its redeemer's declared units.

Concurrent submissions are applied one at a time. Not modelled: rewards, governance and pool rules, the treasury,
PlutusV1's integrity hash, and the collateral loss of a failing script (an invalid-tagged transaction is refused; a
failing script refuses the whole transaction).

A refusal is a `LedgerRefusal`. For each transaction a script ran in, the ledger also runs the attack suite
(`joust.attacks`, a subset of the JVM testkit's `Attacks`) on it: the state datum replaced or hashed, one lovelace
skimmed, token dust added, the output sent to a key address or given a stake credential, the output dropped, the
required signer replaced, the validity bounds moved or removed. Only a script's refusal counts as refused; any other
failure of a mutation is reported as accepted, with its reason, so that it fails the test. `ledger.attacks()` lists
every attack with its outcome; `ledger.acceptedAttacks()` lists those the scripts accepted, which should be none. Pass
`{ attacks: false }` to `offline` to skip the suite. `joust test` runs offline: a network provider (Blockfrost, Yaci
Store, Ogmios) refuses to start under it.

The template's `test/counter.test.js` is such a test: `npm test` runs `joust test`. Its DevKit test is in `test/devkit/`.

### `joust deploy`

`<out>/deployments.<network>.json` is `{ network, networkId, chain, clock, contracts: { <title>: deployment } }`, each
deployment `{ contract, policy, address, networkId, referenceScripts }` plus `params`, `mapVerifier` and
`outputVerifier` when the contract has them. The deployer is `JOUST_MNEMONIC`'s key; without it, on a network with an
`admin` API (DevKit), a key kept in `.joust/<network>-wallet.json`, topped up with 1000 ADA when it holds less than
200 ADA. A contract with `@Params` is deployed with the config's `params` for it (by title or simple name) and skipped
without them.

## Environment variables

| Variable | Read by | Meaning |
|---|---|---|
| `JOUST_MNEMONIC` | `joust deploy`, `joust dev` | the deployer's mnemonic; required on networks without an `admin` API |
| `BLOCKFROST_PREVIEW_PROJECT_ID` | any command on `preview` | the Blockfrost project id (the built-in `preview`'s `projectIdEnv`) |
| (a network's `projectIdEnv`) | any command on that network | its chain API's project id |
| `JOUST_NETWORK` | the Vite plugin, in `vite build` | the network a build is for, unless the plugin's `network` option names one |
| `JOUST_VITE_LOG` | `joust dev` | Vite's log level (default `warn`); `info` shows dependency bundling and reloads |
| `JOUST_DEBUG_NEEDS` | `@julclang/joust-runtime` | logs each chain read the engine asks for |

A command on a network whose `projectIdEnv` is not set stops and names the variable.

## The dev server

`joust dev` serves one origin (default `http://127.0.0.1:5178`):

| Route | Method | Answers |
|---|---|---|
| `/chain/<path>` | GET, POST (`/chain/tx/submit`) | the network's chain API, proxied with its project id; one upstream session (Blockfrost's affinity cookie) |
| `/joust/network.json` | GET | `{ network, networkId, chain: "/chain", engine: { url, integrity: { script, wasm } }, contracts: "/joust/contracts.json", service: "/joust/service", clock, ttlMs, explorer, deployments }` |
| `/joust/engine/<file>` | GET | the runtime engine (`joust-runtime.js`, `joust-runtime.js.wasm`), streamed, with an ETag |
| `/joust/service/prepare` | POST | the engine in the dev server as a prepare service (`httpService('/joust/service')`); 422 `{ error }` on a contract's refusal |
| `/joust/<file>` | GET | files of the build folder |
| `/dev/topup` | POST `{ address, ada? }` | DevKit only: funds the address from the faucet (default 1000 ADA) |
| anything else | | the page: Vite in middleware mode when the project has `vite` and an `index.html` in the page folder, else the page folder's files |

Responses carry `access-control-allow-origin: *`. The page folder is the config's `page`, else `page/` if it exists,
else the project root.

`joust serve` answers `/chain/<path>`, `/dev/topup` (DevKit only) and the files of its folder (`/` is `index.html`).
It has no `/joust` routes.

## The Vite plugin

```js title="vite.config.js"
import { joust } from '@julclang/joust/vite';

export default { root: 'page', plugins: [joust({ root: process.cwd() })] };
```

| Option | Default | Meaning |
|---|---|---|
| `root` | the working directory | the project: where `joust.config.json` and the build folder are |
| `network` | `JOUST_NETWORK`, else Vite's mode if it names a network, else the config's `network` | the network a `vite build` is for |

It returns a list of plugins that:

- alias Node's `buffer`, `events`, `util`, `stream`, `process` and `assert` to browser versions, resolved from the
  plugin's own package by absolute path, and inject the `Buffer` (one class, `src/shims/buffer.js`) and `process`
  globals;
- set `global` to `globalThis` and target es2022 for the dev server's dependency bundling and for builds;
- build workers as ES modules with the same aliases and globals (injected `post` in workers);
- scan `**/*.html` and `**/*.worker.{js,mjs,ts}` for dependencies (unless the config sets `optimizeDeps.entries`), and
  pre-bundle `node:buffer`;
- allow the project root in `server.fs.allow`, so a page imports `build/joust/*.js`;
- provide `virtual:joust/network`.

`vite-plugin-node-polyfills` and `@rollup/plugin-inject` are dependencies of the package; `vite` (5 or newer) is an
optional peer dependency.

### `virtual:joust/network`

The default export, in a build:

| Field | Value |
|---|---|
| `network` | the network's name |
| `networkId` | the network's `networkId`, else the deployments file's |
| `chain` | the network's `pageChain`, else `"/chain"` |
| `clock` | the deployments file's clock, else the network's |
| `ttlMs` | the config's `dev.ttlMs`, else 20 000 on a DevKit, 180 000 elsewhere |
| `explorer` | the network's `explorer`, or `null` |
| `deployments` | the deployments file's `contracts` |
| `contracts` | `contracts.json` |
| `validators` | `validators.json`, or `[]` |
| `engine` | `{ url: "<base>joust/engine-<id>/joust-runtime.js", integrity: { script, wasm } }` |

A build emits the engine's two files to `joust/engine-<id>/` (`id`: 8 hex characters from the files' hashes) and fails
without `contracts.json` or `deployments.<network>.json`. Under `joust dev`, the module instead fetches
`/joust/network.json` and then its `contracts` when the page loads (the fields of the dev server's `network.json`,
above).

## The native `joust`

ADR-0017 adds a native `joust` (no Node, no JDK needed to run it): `brew install bloxbean/tap/joust`, or the release
archives (macOS arm64, Linux x86_64 and arm64). It creates projects and hands project commands to the project:

| Command | Native `joust` |
|---|---|
| `joust new <dir> [-t gradle\|node\|web] [-l java\|jsc] [-p <package>]` | `gradle` (default, `java` by default): a Gradle project with the plugin `org.julclang.joust`; `node`, `web`: what `npm create joust` writes, fetched with `npm pack create-joust@<its version>` and run by its own `node`, isolated from the directory's npm configuration |
| `joust version` | `joust <version> (native)`, and in an npm project `project: @julclang/joust <version> (npm)` |
| `joust help`, `<command> --help` | the usage; never runs a command |
| any other command, in an npm project | the project's own `@julclang/joust` (`node_modules`), at the project's root, with the arguments unchanged and its exit code; `run npm install first` if it is missing, never a stand-in |
| `joust build`, `test`, `run`, in a Gradle build | the build's `./gradlew <task>` (a subproject's directory selects the subproject); `deploy`, `dev` and `serve` explain that they are npm commands |

Both `joust` commands answer `new`, `version` and `help` themselves, and both hand project commands to the project's
own `@julclang/joust`. So `joust build` does the same, whichever binary `PATH` finds. Install the native one globally and
`@julclang/joust` per project (both global at once is not supported: with Homebrew's Node they share one path).

The walk up to a project does not enter directories owned by another user (a planted `package.json` in `/tmp` is
ignored); list directories you trust, such as a container bind mount, in `JOUST_SAFE_DIRS` (`:`-separated). Both CLIs
apply this rule, as git's `safe.directory` does: in a container or CI job that runs as another user than the one owning
the checkout (for example root over a mounted workspace), run as its owner, or set `JOUST_SAFE_DIRS`. Its entries are
absolute paths and trust those exact directories, not their subdirectories: `JOUST_SAFE_DIRS=/workspace` works for
`joust build` run in `/workspace`; run from `/workspace/contracts`, list that directory too. Otherwise `joust build`
reports that it found no project.

To check a downloaded archive before using it: `shasum -a 256 -c joust-<version>-SHA256SUMS.txt --ignore-missing`, then
`gh attestation verify joust-<version>-<platform>.zip -R bloxbean/joust`; on macOS, `xattr -d com.apple.quarantine joust`
(the binary is not notarized; Homebrew installs need none of this).

## `create-joust`

```sh
npm create joust@0.1.0-pre1-snapshot [dir] -- [--template node|web] [--lang jsc|java]
```

Writes a new project into `dir` (default `joust-app`), which must be empty or absent, and names the package after the
folder. Every project has a `Counter` contract, `joust.config.json` for DevKit, a DevKit test
(`test/counter.test.js`) and `.gitignore`.

| Option | Values |
|---|---|
| `--template`, `-t` | `node` (default): `index.js`, a Node script that deploys and calls the contract; scripts `start`, `build`, `deploy`, `test`. `web`: a page (`page/`) with the Cardano Foundation's connect button and an in-page DevKit key, and `vite.config.js`; the scripts listed under [A browser page](/start/quick-start-npm/#a-browser-page) |
| `--lang`, `-l` | `jsc` (default): `contracts/app/Counter.jsc` in `.jsc` 2 (a language preview), with its ABI manifest `Counter.abi.json`. `java`: `contracts/app/Counter.java`. Both give the same description and client |
| `--help`, `-h` | the usage |

Options go after `--` with `npm create` (npm passes them on); `npx create-joust my-app --lang java` takes them
directly.

## Functions

The commands are also functions, for scripts and tests:

| Export | Signature | Description |
|---|---|---|
| `build` | `await build({ root?, src?, out?, options?, log?, keep? })` | `{ ok, contracts, validators, diagnostics }` |
| `deploy` | `await deploy({ root?, config, networkName?, log?, fetchImpl? })` | the deployments written |
| `loadConfig` | `loadConfig(root = process.cwd())` | the config, merged over the defaults |
| `network` | `await network(config, name?)` | the network with its clock resolved (a DevKit's from its admin API) and `projectId` read |
| `loadToolchain` | `loadToolchain({ dir? } = {})` | the toolchain engine (`engine.joust.build({ files, options })`) |
| `VERSION` | constant | the package version |
