`.jsc` is JOUST's contract language. Version 2 reads like TypeScript: a contract is its state, an `init` that returns
the first state, actions that return the next one (`{ ...state, count: count + by }`), destroys that pay out, and
views. Values never change, every `if` and `match` is an expression, and lists, records, enums, options and maps are
built in. The build lowers each file to an ordinary Java `@StateContract` class; from there everything is the same as
for a contract written in Java: the JOUST processor generates the validator and the typed client, and JuLC compiles the
validator to UPLC.

<Aside type="caution" title="A language preview">
`.jsc` 2 is a language preview ([ADR-0018](https://github.com/bloxbean/joust/blob/main/docs/adr/0018-jsc-2-immutable-contract-language.md)
D14), not to be confused with Cardano's preview network. The language and the compiler's output may change before it
leaves preview, so the same file may compile to a different script hash in a later JOUST (milestone M1e changes every
`.jsc` 2 script hash once). Use it on DevKit and testnets, and don't deploy it to hold value; a deployed preview
contract is rebuilt with the JOUST version recorded for it (`build/joust/joust.lock.json`, or the plugin's version).
It covers the core language (milestone M1). Native assets, sends, mints, deploy parameters, events and reads of other
contracts arrive in M2; owned and keyed objects, batched intents and script purposes in M3; `.jsc` libraries and
offline tests in M4. Until then, write a contract that needs one of them in [Java](/languages/java/). `.jsc` becomes
the recommended language for JavaScript developers only after M2, M4 and an independent security review of the
lowering.
</Aside>

A file that does not start with `jsc 2` is a `.jsc` **v1** file. v1 keeps compiling, with a deprecation warning
(`JSC9006`); [`joust migrate`](/languages/jsc-migration/) translates it. Its reference is [.jsc v1](/languages/jsc-v1/).

## Why it exists

A Java `@StateContract` is readable, but it is Java: `BigInteger.compareTo`, `ByteStringLib.equals`, records rebuilt
field by field. `.jsc` 2 gives JavaScript developers the same contract model in the syntax they know, and it removes
the ways to get the subset wrong: there is no `byte[] ==`, no fixed-width integer, no mutable local.

**`.jsc` lowers to Java, not to UPLC.** Nothing new is trusted on chain. The validator's invariants (thread token,
exact datum, exact value, verified `Ctx`, tagged payouts) come from the JOUST processor, exactly as for a Java
contract, and the same generated method runs on the JVM to build the transaction and on chain to check it.

<Aside type="caution" title="A miscompile is still your bug">
The trusted base does not grow, but a wrong lowering would produce a contract that the validator then enforces
faithfully. The checker's rules, the four-way differential tests (a reference interpreter, the JVM, the transition
program and the validator must agree) and the generated checks are the defence. Read the generated Java of any
contract that holds real value: every line carries a comment with its `.jsc` position.
</Aside>

## A first contract

This is the counter `npm create joust` writes:

```jsc title="contracts/app/Counter.jsc"
jsc 2
package app

// A counter anyone can increment and only its owner can reset or close.
contract Counter(maxDatumBytes = 128) {
  // The state, stored as the inline datum of the state UTxO.
  state { count: Int, owner: Key }

  // The deployer becomes the owner; the count starts at 0.
  init() {
    return { count: 0, owner: caller }
  }

  // Anyone can increment by a positive amount (it never reads caller: no signature needed, cheaper).
  action increment(by: Int) {
    require(by > 0, "increment must be positive")
    return { ...state, count: count + by }
  }

  // Only the owner can reset.
  action reset() only owner {
    return { ...state, count: 0 }
  }

  // Only the owner can close the counter; the deposit goes back to them.
  destroy close() only owner {
    pay(owner, balance)
  }

  // A read-only view (off-chain, no transaction).
  view count(): Int = count
}
```

Beside it the project commits `Counter.abi.json`, the contract's [ABI manifest](#the-abi-manifest): how its state and
its calls are encoded on chain. `joust build` (or Gradle) turns the file into `Counter.java`, then into the validator
and a client with `deploy`, `increment`, `reset`, `close` and `count`.

## A guided tour

### The file

A `.jsc` 2 file starts with `jsc 2` (comments may come before it), then a `package`, then any number of `import`s,
`type`s, `enum`s and `fn`s, and exactly one `contract`:

```jsc title="examples/dsl/src/main/jsc/org/julclang/state/examples/dsl/Pledges.jsc (head)"
jsc 2
package org.julclang.state.examples.dsl

import { blake2b_224 } from "std/crypto"
import { slice, length } from "std/bytes"

type Share = { to: Key, bps: Int }

fn total(shares: List<Share>): Int = shares.fold(0, (acc, s) => acc + s.bps)

contract Pledges(maxDatumBytes = 1024) {
  ...
}
```

Comments are `//` and `/* … */`. Newlines do not end statements; `;` between statements is optional. An index's `[`
and a call's `(` must be on the line of what they follow (on a later line they start a new expression), and a line that
starts with `-` continues the expression above it, with a warning (`JSC9007`): see
[the reference](/languages/jsc-reference/#lexical-rules). The generated class
goes to `<package path>/<Contract>.java`: its name comes from the `contract` line, not from the file name.

The contract's options are the `@StateContract` elements of the same name ([Annotations](/reference/annotations/)):

| Option | Meaning | Default |
|---|---|---|
| `minAda` | Lovelace locked as the state UTxO's min-ADA deposit (`2 ada` is allowed) | derived from `maxDatumBytes` |
| `maxDatumBytes` | Largest serialised state the validator accepts | `512` |
| `maxValidityMs` | Widest validity interval a call that reads the transaction may use, in POSIX ms | `3600000` (one hour) |

### State

`state { … }` declares the state record once, its fields in order: `state { owner: Key, goal: Int, raised: Int }`. A
field has any type the language has, a `BigMap` included. Inside a method a bare field name reads the **input** state,
and `state` is the whole input state. The input never changes, so the order of reads cannot matter.

| Type | What it is |
|---|---|
| `Int` | The only number type: arbitrary precision, as on chain. `1_000_000`, `5 ada` (5,000,000 lovelace) |
| `Bool` | `true`, `false` |
| `Bytes` | A byte string: `#cafe`, or `utf8("text")` |
| `Key` | A 28-byte key hash. A `Key` is also `Bytes`; `Bytes` become a `Key` only through `asKey(b)`, a checked conversion |
| `Hash` | A 28-byte script hash or policy id (`asHash(b)`) |
| `List<T>` | `[a, b]`, `[x, ...xs]` |
| `Option<T>` | `Some(x)` or `None` |
| `Map<K, V>` | An inline map in the datum, in canonical key order; keys are `Bytes`, `Key` or `Hash` of at most 64 bytes |
| `BigMap<K, Int>`, `BigMap<K, Bytes>` | A Merkle map: any number of entries behind a 32-byte root ([MerkleMaps](/contracts/merklemaps/)); a state field only |
| `type R = { … }` | Your records |
| `enum E { A, B { x: Int } }` | Your sum types |

The [reference](/languages/jsc-reference/#types-and-their-encodings) gives each type's on-chain encoding.

### Methods and their results

| Member | Form | Its value |
|---|---|---|
| `init` | `init(params) [payable] { … }` (exactly one, no name) | the first state: `return { count: 0, owner: caller }` |
| `action` | `action name(params) modifiers { … }` | the next state: `return { ...state, count: count + by }` |
| `destroy` | `destroy name(params) modifiers { … }` | nothing: it ends the instance, and must `pay` out what it holds |
| `view` | `view name(params): T = expr`, or a block | a value, computed off chain without a transaction |

A block's value is its last expression; `return e` as the last statement means the same, and there is no early
return. An object literal of the state type gives every field, explicitly or through one leading `...state`; unknown
fields, a field given twice and a spread of another type are errors. `{ goal }` is short for `{ goal: goal }`. An
action that changes nothing returns `state`.

An `init` has no input state, so its parameters may share the names of the fields it creates:

```jsc
init(goal: Int, deadline: Int, shares: List<Share>, label: Bytes) {
  require(goal > 0, "the goal must be positive")
  return { owner: caller, goal, deadline, raised: 0, shares, tag: slice(blake2b_224(label), 0, 8), lastBacker: None }
}
```

In every other method a parameter, `const` or binding may not take a state field's name or a built-in's (`JSC0213`,
which suggests `newOwner`): `goal` always means the state's `goal`.

### The transaction: built-ins

| Name | Type | Meaning |
|---|---|---|
| `caller` | `Key` | The signer the validator verified |
| `received` | `Int` | Lovelace this call adds (a `payable` method) |
| `balance` | `Int` | Lovelace the instance holds, the min-ADA deposit included |
| `validFrom`, `validTo` | `Int` | The bounds of the transaction's validity interval, POSIX ms: [time values](#time) |

A method gets the transaction (a generated `Ctx ctx` parameter) only when it reads one of these, or has a modifier
that needs it. Views and `fn`s never do (`JSC0415`): pass what they need as arguments.

### require, pay and modifiers

```jsc
require(amount > 0 && amount <= balance, "bad amount")
pay(owner, balance)
```

`require(cond, "message")` fails the call unless `cond` holds: on the JVM it throws `RequireException` before anything
is submitted, on chain it fails the script with the message as a trace. `pay(to, amount)` adds a payout of `amount`
lovelace to the `Key` `to`: payouts are in source order, an amount of 0 is skipped and a negative one fails. `pay` is
allowed only in an action or destroy, never in `init`, a view, a `fn`, a lambda or a value block (`JSC0404`,
`JSC0413`). See [Ctx, funds and payouts](/contracts/ctx-and-funds/).

Modifiers follow the parameter list:

| Modifier | Annotation | Allowed on |
|---|---|---|
| `payable` | `@Payable`: the call may add lovelace (`received`) | `init`, `action` |
| `only f` | `@SignedBy("f")`: the `Key` field `f` must sign | `action`, `destroy` |
| `after f` | `@ValidAfter("f")`: valid only after the `Int` field `f` | `action`, `destroy` |
| `before f` | `@ValidBefore("f")`: valid only before the `Int` field `f` | `action`, `destroy` |
| `open` | none: you state that anyone may call a method that pays | `action`, `destroy` |

<Aside type="danger" title="A method that can pay needs an audience">
An action or destroy that can reach a `pay` in any arm or loop must say who may call it: `only <key field>`, or `open`
if anyone may, in which case its `require`s are the only guard (`JSC0408`). A destroy must pay at least once
(`JSC0409`), and the checker warns when it never reads `balance` (`JSC9001`): a destroy must pay out everything the
instance holds, the deposit included, or every call is rejected.
</Aside>

### Immutable values

A name is bound once, with `const`, and never changes. The JavaScript habits that would change one are errors that
say what to write instead:

| You write | You get |
|---|---|
| `let x = 1`, `var x = 1` | `JSC0128`: values are immutable in .jsc: write `const x = …` |
| `x = 2`, `x += 1`, `x++` | `JSC0130` (`JSC0135` for a prefix `++`): build a new value, e.g. `return { ...state, x: x + 1 }` |
| `a === b` | `JSC0133`: write `==`: `.jsc` equality is always by value |
| `for (let i = 0; …)`, `while`, `for … in` | `JSC1001`, `JSC1003`, `JSC1002`: use `xs.fold(…)`, `range(a, b)`, `for (const x of xs)` or a recursive `fn` |
| `function f() {}` | `JSC0115`: functions are written `fn name(x: Int): Int = …` |
| `class`, `this`, `new` | `JSC0116`/`JSC0140`, `JSC0139`, `JSC0142`: records are `type Name = { f: T }`, a bare field name reads the state |
| `null`, `undefined` | `JSC0138`: use `Option<T>` with `None` and `Some(x)` |
| `async`, `await` | `JSC0123`/`JSC0141`: a call runs in one transaction |
| `switch` | `JSC0908`: write `match e { A => …, B { x } => … }` |
| `return` before the end of a block | `JSC0129`: a block's value is its last expression |

Every `const` must be used (`JSC0215`): JuLC may drop an unused binding on chain while the JVM still evaluates it, so
`const x = 100 / d` must not look like a check. Write a `require` instead.

### Conditionals and match

`if c { a } else { b }` is an expression when both arms end in a value; `c ? a : b` is its short form. Without an
`else`, or with arms that end in statements, an `if` is a statement: its arms may `require` and `pay`. Only the taken
arm runs, on the JVM and on chain.

`match` takes an enum or an `Option`, must be exhaustive, and is an expression or a statement. From `Ledger.jsc`:

```jsc title="examples/dsl/src/main/jsc/org/julclang/state/examples/dsl/Ledger.jsc (excerpts)"
enum Phase {
  Open,
  Paused { reason: Bytes },
  Closed { day: Int, by: Key }
}

  view phaseCode(): Int = match phase {
    Open => 0
    Paused { reason } => 1 + length(reason)
    Closed { day } => 100 + day
  }

  // Closed and every token burned: a closer named in the phase takes half, the admin the rest.
  destroy settle() only admin {
    require(balances.isEmpty, "tokens remain")
    match phase {
      Closed { by } => {
        pay(by, balance / 2)
        pay(admin, balance - balance / 2)
      }
      _ => {
        pay(admin, balance)
      }
    }
  }
```

Patterns are a variant (`Open`), a variant with fields bound by name (`Closed { by }`, or `Closed { day: d }` to
rename), `Some(x)`, `None`, and `_` for every case not named by an earlier arm. A binding must be used; nested patterns
are not supported (bind the value and match it again). An arm whose value is an object literal needs parentheses,
since an arm's `{` starts a block: `Some(it) => ({ ...state, items: items.delete(id) })`.

### Functions and recursion

```jsc
fn total(shares: List<Share>): Int = shares.fold(0, (acc, s) => acc + s.bps)

// Direct self-recursion: the number of digits of n.
fn digits(n: Int): Int = n < 10 ? 1 : 1 + digits(n / 10)
```

A `fn` has typed parameters and a typed result, at the top of the file or in the contract. It is pure: no `pay`, no
transaction built-ins, no state (pass what it needs). A function may call itself directly; mutual recursion is refused
(`JSC0602`), and so is a recursive call from inside a lambda, an `if` or `match` arm, a value block or a `??` default
(`JSC0601`), since the generated helper would join a cycle. Write `cond ? base : … f(…)` instead, as `digits` does.

### Lists

```jsc title="examples/dsl/src/main/jsc/org/julclang/state/examples/dsl/Pledges.jsc (excerpts)"
  view shareOf(who: Key): Int = (shares.find(s => s.to == who) ?? Share { to: who, bps: 0 }).bps

  view isShareholder(who: Key): Bool = shares.map(s => s.to).contains(who)

  // Goal reached after the deadline: pay every share, the rounding remainder to the owner.
  destroy distribute() only owner {
    require(after(deadline) || raised == 0, "too early")
    if raised >= goal {
      for (const s of shares) {
        pay(s.to, balance * s.bps / 10_000)
      }
      pay(owner, balance - shares.fold(0, (acc, s) => acc + balance * s.bps / 10_000))
    } else {
      pay(owner, balance)
    }
  }
```

| Member | Result |
|---|---|
| `xs.length`, `xs.isEmpty`, `xs.head` | `Int`, `Bool`, `Option<T>` (properties: no parentheses) |
| `xs.contains(x)` | `Bool`, by structural equality |
| `xs.any(x => …)`, `xs.all(x => …)` | `Bool`; they stop at the first decisive element |
| `xs.find(x => …)` | `Option<T>`: the first match |
| `xs.filter(x => …)`, `xs.map(x => …)` | a new list |
| `xs.fold(init, (acc, x) => …)` | the accumulated value |
| `xs.sum()` (on `List<Int>`), `xs.reverse()`, `xs.concat(ys)` | |
| `xs.take(n)`, `xs.drop(n)` | a new list; a negative `n` fails on both sides |
| `range(a, b)` | the `Int`s from `a` up to `b`, exclusive, as the receiver of `any`, `all`, `fold`, `filter`, `map` or a `for` list; no list is built |

Lambdas (`x => e`, `(acc, x) => e`, or a block of `const` and `require` ending in its value) exist only as arguments of
these methods. `for (const x of xs) { … }` is a statement whose body may hold `const`, `require`, `if`, `match` and
`pay`; accumulate with `fold`. `std/list` adds `last`, `nth` and `indexOf` ([standard library](/languages/jsc-std/)).

### Records

`type Share = { to: Key, bps: Int }` declares a record. Build one with `Share { to, bps: 0 }`, or with `{ to, bps: 0 }`
where the type is known (a typed parameter, field or `const`, a list element). Read a field with `s.bps`. Two record
types with the same fields are distinct, and records compare by value: `shares.contains(from)`, `s == from`. Type, enum
and variant names start with a capital and share one namespace.

### Option

`Some(x)` and `None`. `o ?? d` is `o`'s value, or `d` when it is `None` (`d` runs only then). `match o { Some(x) => …,
None => … }` reads it. `Option<Option<T>>` and `Some(None)` are refused: JavaScript cannot tell `Some(None)` from
`None`. `??` is not mixed with `&&` or `||` without parentheses, as in JavaScript.

### Map and BigMap

Two map types, for two sizes:

- **`Map<K, V>`** is an inline map in the datum: every entry is in the state UTxO, so its size is bounded by
  `maxDatumBytes`. `m.get(k)` (an `Option`), `m.has(k)`, `m.set(k, v)` and `m.delete(k)` (new maps, always in
  canonical key order), `m.size`, `m.keys`, `m.values`, `m.isEmpty`, `m.any((k, v) => …)`, `m.all(…)`,
  `m.fold(init, (acc, k, v) => …)`, `Map.empty()`. Maps compare by value.
- **`BigMap<K, Int>`** and **`BigMap<K, Bytes>`** are Merkle maps: any number of entries behind a 32-byte root; each
  call proves only the keys it reads and writes. A state field only.

```jsc title="examples/dsl/src/main/jsc/org/julclang/state/examples/dsl/Ledger.jsc (excerpts)"
  // Minting is capped per holder by the limits map, and only while open.
  action mint(to: Key, amount: Int) only admin {
    require(phase == Open, "not open")
    require(amount > 0, "amount must be positive")
    const cap = limits.get(to) ?? 0
    require(balances[to] + amount <= cap, "over the holder's limit")
    return { ...state, balances: balances.set(to, balances[to] + amount), supply: supply + amount }
  }

  // A transfer reads the recipient through the debit, so a self-transfer keeps the balance.
  action transfer(to: Key, amount: Int) {
    require(amount > 0, "amount must be positive")
    const left = balances[caller] - amount
    require(left >= 0, "insufficient balance")
    return { ...state, balances: balances.set(caller, left).set(to, balances.set(caller, left)[to] + amount) }
  }
```

A `BigMap` is read with `m.get(k)`, `m.has(k)` and, on `BigMap<K, Int>`, `m[k]` (0 when absent). It is changed only in
its own field of the next state, by `set` and `delete`: `{ ...state, balances: balances.set(to, v) }`. Its `Int` values
are never negative, and `set(k, 0)` removes the entry. It is never bound to a `const`, passed to a `fn`, captured by a
lambda, compared or chosen by a condition; `BigMap.empty()` starts one in an `init`, and `m.isEmpty` ("empty before
this call") is read only in a destroy. A method reads its own writes through the chain, as `transfer` does.

### Time

`validFrom` and `validTo` are chosen by whoever submits the transaction, within `maxValidityMs`. So `.jsc` 2 keeps
them from deciding anything (ADR-0018 D11):

- **Decide only with `after(t)` and `before(t)`.** They hold for the whole validity window, and they are allowed only
  at the top of a `require`, alone or under `&&` or `||`: `require(after(deadline) || raised == 0, "too early")`.
  Never negated, in an `if`, a `?:`, a `const`, a `fn` or a lambda.
- **A time value never decides.** Any value computed from `validFrom` or `validTo` (through arithmetic, a `const`, a
  `fn` call, a record, a stored field) is a *time value*. It may not be a condition, an operand of `&&`, `||` or `!`, a
  predicate, or a comparison: `require(validFrom < deadline, …)` is refused (`JSC0502`).
- **A time value never makes an operation fail.** It may not be a divisor, a map key, a list index or count, a
  domain-checked `std` argument, or a `BigMap<K, Int>` value. A payout may depend on one only as `pay(to, max(0, …))`.
- **Time values may flow into amounts and state**, with a warning that names the bias (`JSC9003` to `JSC9005`). A
  field that any method sets from a time value becomes a time field, and the ABI manifest lists it.

`std/time` has `elapsedSince(t)` (`max(0, validFrom - t)`, never an over-estimate), `elapsedSinceAtMost(t)`,
`windowStart()` and `windowEnd()`. For a field-based rule on a whole method, prefer the `after f` and `before f`
modifiers. See [Time](/contracts/time/) and [the precise rule](/languages/jsc-reference/#time-d11).

### Checked inputs

Every value that crosses into the contract from a caller (an `init` argument or an action's parameter, in the
redeemer) is checked by generated code before your code sees it, recursively: every `Key` and `Hash` in it is 28
bytes, and every `Map` has unique keys of at most 64 bytes in strictly ascending canonical order. A failing check is
a located `require` failure. So `reassign(from: Share, to: Key)` can trust that `to` and `from.to` are real key hashes.

### The standard library

```jsc
import { blake2b_224 } from "std/crypto"
import { slice, length } from "std/bytes"
```

`std/bytes`, `std/crypto`, `std/math` (`div` and `mod` floor, where `/` and `%` truncate), `std/bits`, `std/list` and
`std/time`, plus the prelude (`min`, `max`, `abs`, `utf8`, `asKey`, `asHash`, `range`, `Some`, `after`, `before`). Every
function, its domain and its Java target: [.jsc standard library](/languages/jsc-std/).

## How it lowers

The lowering is mechanical, and the output is meant to be read. The counter above becomes (imports omitted):

```java title="build/generated/sources/jsc/java/main/app/Counter.java"
/**
 * GENERATED from Counter.jsc by julc-state-dsl (ADR-0018, .jsc 2). Do not edit: change the .jsc file.
 */
// Counter.jsc:9:1
@StateContract(maxDatumBytes = 128)
public class Counter {

    // Counter.jsc:9:1
    public record State(BigInteger count, byte[] owner) {}

    // Counter.jsc:14:3
    @Init
    public static State init(Ctx ctx) {
        return new State(BigInteger.valueOf(0L), ctx.caller());
    }

    // Counter.jsc:19:3
    @Action
    public static State increment(State s__, BigInteger by) {
        // Counter.jsc:20:5
        Require.that((by.compareTo(BigInteger.valueOf(0L)) > 0), "increment must be positive");
        return new State(s__.count().add(by), s__.owner());
    }

    // Counter.jsc:25:3
    @Action
    @SignedBy("owner")
    public static State reset(State s__) {
        return new State(BigInteger.valueOf(0L), s__.owner());
    }

    // Counter.jsc:30:3
    @Destroy
    @SignedBy("owner")
    public static JulcList<Payout> close(State s__, Ctx ctx) {
        // Counter.jsc:31:5
        BigInteger amount__1 = ctx.balance();
        Require.that(amount__1.compareTo(BigInteger.ZERO) >= 0, "Counter.jsc:31: a payout cannot be negative");
        JulcList<Payout> payouts__2 = amount__1.compareTo(BigInteger.ZERO) == 0 ? Payouts.none() : Payouts.add(Payouts.none(), s__.owner(), amount__1);
        return payouts__2.reverse();
    }

    // Counter.jsc:35:3
    @View
    public static BigInteger count(State s__) {
        return s__.count();
    }

}
```

What to notice:

- **Modifiers became annotations**: `only owner` is `@SignedBy("owner")`.
- **`Ctx` appears only where needed**: `init` reads `caller`, `close` reads `balance`; `increment` and `reset` take none,
  so they need no signature and cost less.
- **No loops and no reassigned locals** in the generated Java: `fold`, `for`, `map` and the other list methods become
  typed, self-recursive static helpers; `if` and `match` arms become helpers that run only when taken.
- **Equality is generated**: `==` on bytes lowers to `ByteStringLib.equals`, and on records, enums, lists, options and
  maps to generated helpers, never Java `equals` or a reference comparison.
- **Every line carries its `.jsc` position** (`// Counter.jsc:20:5`), and the generated checks carry it in their
  messages, so a failure on chain points back to your source.

The generated Java is on disk: `build/generated/sources/jsc/java/main/` on Gradle, `build/joust/generated/` with
`joust build`. Beside each file, `<Contract>.jscmap.json` maps each generated line to its `.jsc` line and column; a
javac or processor diagnostic on generated Java is reported at the `.jsc` position, with the generated location as a
note.

## The ABI manifest

The build writes `<Contract>.abi.json` for every `.jsc` 2 contract: the encoding of its datum and of every redeemer
(constructor indices, field names and order, data shapes, the schemas they reach) and its time fields. The project
**commits it beside the `.jsc` file**. Every build compares what the lowering produces with the committed copy, so a
change that would alter how a deployed instance's datum or redeemer is encoded cannot pass unnoticed:

| The build finds | Result |
|---|---|
| The same manifest | builds |
| No committed manifest | fails: `JSC0003` |
| A different manifest | fails: `JSC0002`, naming the first line that differs |

When the change is intended (a new contract, or a new script you will deploy afresh), accept it, review the diff and
commit it:

<Tabs syncKey="lang">
<TabItem label="Java">

```sh
./gradlew acceptJscAbi      # writes the manifests beside the .jsc files
git diff -- '*.abi.json'
```

</TabItem>
<TabItem label="JavaScript">

```sh
npx joust build --accept-abi      # or: joust dev --accept-abi
git diff -- '*.abi.json'
```

</TabItem>
</Tabs>

Nothing else accepts a manifest: no Gradle or system property switches the check off. Each build also checks the
manifest against the processor's own description of the contract (`JSC0004`, an internal error of the lowering if it
ever fires; on Gradle the `checkJscAbi` task, part of `check`). See
[the reference](/languages/jsc-reference/#the-abi-manifest).

## Building .jsc

<Tabs syncKey="lang">
<TabItem label="Java">

With the Gradle plugin `org.julclang.joust` ([Quick start: Java](/start/quick-start-java/)), put `.jsc` files under
`src/main/jsc/`, in directories that match their packages. The plugin adds:

| Task | What it does |
|---|---|
| `generateJsc` | Lowers `src/main/jsc/**/*.jsc` to `build/generated/sources/jsc/java/main/` before `compileJava`; fails on a refused or missing ABI manifest |
| `acceptJscAbi` | Writes the ABI manifests beside the `.jsc` files, accepting new and changed ones |
| `checkJscAbi` | After `compileJava`, checks each manifest against the processor's description; part of `check` |

<FileTree>

- src/main/jsc/org/example/vault
  - Vault.jsc
  - Vault.abi.json committed
- build/generated/sources/jsc/java/main/org/example/vault
  - Vault.java generated, then processed like hand-written Java
  - Vault.jscmap.json its source map

</FileTree>

Each run empties the output directory first, so a deleted or renamed `.jsc` leaves no stale contract behind, and two
files that generate the same class are an error. `examples/dsl/build.gradle` wires the same three tasks by hand.

</TabItem>
<TabItem label="JavaScript">

Put `.jsc` files beside (or instead of) `.java` files in the project's `contracts/` directory. `joust build` compiles
both with no JDK: the lowering runs inside the toolchain's Wasm engine, exactly as in the Gradle build. `joust dev`
rebuilds when you save a `.jsc` file, and keeps serving the last good build when a manifest is refused.

```sh
npx joust build
# build/joust/Counter.json        the contract description
# build/joust/Counter.plutus      the compiled validator
# build/joust/Counter.js/.d.ts    the typed JavaScript client
# build/joust/generated/app/      Counter.java and Counter.jscmap.json
```

<Aside type="caution">
The npm packages are not on npmjs.org yet. Until they are, publish them to a local registry at
`http://127.0.0.1:4873/` from a JOUST checkout: `./gradlew npmPublishLocal -PgraalvmHome=...` builds the two Wasm
engines and runs `js/publish-local.sh`. Then install with `npm_config_registry=http://127.0.0.1:4873/`.
</Aside>

</TabItem>
</Tabs>

Errors and warnings carry their position and a stable code on both paths: Gradle prints
`app/Counter.jsc:20:13: error[JSC0502]: a time value cannot decide here: …`, and `joust build` prints
`error[JSC0502]: app/Counter.jsc:20:13: …`. Each code is in the
[diagnostics catalogue](https://github.com/bloxbean/joust/blob/main/docs/reference/jsc-2-diagnostics.md).

## Testing a .jsc contract

Test it exactly like a Java contract: the generated class, validator and client are ordinary code
([Testing](/contracts/testing/)). `examples/dsl`'s `Dsl2Test` calls the generated methods on the JVM, inputs checked
and refused included, and evaluates the validators with the harness; `julc-state-toolchain`'s four-way tests run every
call through the reference interpreter, the JVM, the transition program and the validator, and require all four to
agree.

## What still needs Java

| Feature | In `.jsc` 2 |
|---|---|
| Native assets, `send`, `mint`/`burn`, deposits, deploy parameters, invariants, events, quorums, reads of other contracts | milestone M2 |
| Owned and keyed objects, moves, `init migrate`, script purposes (staking, governance) | M3 |
| Batched intents | M3; a `BigMap` contract cannot have them at all (ADR-0004 D1) |
| `.jsc` libraries, Java library imports, offline tests | M4 |
| A language server | M5 |

Until then, write such a contract in [Java](/languages/java/); you can start from the generated Java of a `.jsc`
version.
