Quick start: Java & Gradle

This page takes you from an empty machine to a contract running on a local Cardano network, with Java 25 and Gradle. It has two parts: first you run the counter example inside a JOUST checkout (the quickest way to see everything work), then you set up a project of your own.

If you would rather use Node and no JDK, see Quick start: npm & JavaScript.

Experimental, pre-release: nothing is on Maven Central yet

JOUST is a research and learning project: do not use it in production. Its releases, all pre-releases so far, are in the BloxBean release repository, https://repo.bloxbean.org/maven/releases, with the JuLC they need; the releases page lists them. Part 2 shows the Gradle setup.

Prerequisites

Section titled “Prerequisites”

  • JDK 25. The build uses a Java toolchain of version 25.

  • Git, to clone JOUST for the example in Part 1.

  • Yaci DevKit, the local Cardano network, for the last step. Start it with Yaci Store (its Blockfrost-compatible API) enabled:

    Yaci Store then answers on http://localhost:8080, the DevKit admin API on http://localhost:10000, and the Yaci Viewer explorer on http://localhost:5173. See Networks and chain providers.

You do not need Gradle installed: the JOUST checkout has a wrapper (Gradle 9.2), and you can copy it.

Part 1: run the counter in a JOUST checkout

Section titled “Part 1: run the counter in a JOUST checkout”

  1. Get JOUST.

    The build resolves JuLC and cardano-client-lib (the versions in gradle/libs.versions.toml) from Maven Central and the BloxBean repositories; nothing needs to be built first.

  2. Run the counter’s tests.

    This compiles Counter.java, generates CounterValidator and CounterClient, compiles the validator to UPLC, and runs three kinds of tests: the contract’s methods as plain Java, the compiled validator against transactions shaped like the runtime’s, and the attack suite on each accepted transaction. The DevKit test (CounterDevnetTest) runs too if DevKit is up, and skips itself otherwise.

  3. Run it on DevKit.

    CounterApp funds two fresh accounts from the DevKit faucet, deploys a counter as Alice, increments it as Bob and Alice, shows Bob’s reset being refused before anything is submitted, and closes the counter:

    Your hashes will differ. The first run on a fresh DevKit also logs published the Counter reference script in ...: the first deploy of a contract on a network publishes its script once, for every later transaction to read. Open the address in Yaci Viewer (http://localhost:5173) to see the state UTxOs and their datums.

Every example in examples/ runs the same way: ./gradlew :examples:vault:run, :examples:escrow:run, and so on. See Examples.

Part 2: your own project

Section titled “Part 2: your own project”

Create it with joust new

Section titled “Create it with joust new”

  1. Install joust.

    Or unpack the archive for your platform (macOS arm64, Linux x86_64 or arm64) from the releases and put joust on your PATH.

  2. Create the project.

  3. Build, test and run.

joust new (the native joust and the Gradle plugin org.julclang.joust, ADR-0017) writes the files of the sections below, with the Gradle wrapper, and a build.gradle that is only this:

The plugin does what the hand-written build.gradle below spells out:

It adds At
julc-state-runtime, and cardano-client-backend-blockfrost for DevKit (joust { blockfrost = false } leaves it out) implementation
julc-state-processor, julc-annotation-processor, julc-state-api:<v>:onchain the annotation processor path
julc-state-testkit, junit-platform-launcher the tests
UTF-8 and -parameters; native access and in-memory map mirrors for tests; native access for run compile, test and run tasks
generateJsc, when src/main/jsc exists: .jsc contracts lowered to Java before compiling; with it acceptJscAbi, checkJscAbi (the ABI manifest) and remapJscDiagnostics (javac’s errors on the generated Java, at their .jsc positions) the build

joust new fills in the version of the joust that runs it; the newest is the newest release whose tag starts with v on the releases page (npm view @julclang/joust version). Every other version comes from the JOUST release the plugin belongs to, so the JuLC and cardano-client-lib versions always match. It needs a Java 25 toolchain (the default; a lower one is refused with a message).

The same command writes npm projects: joust new my-app -t node gives what npm create joust gives. In a project, the native joust and the npm one answer the same commands; see the native joust.

Or set it up by hand: choose where JOUST comes from

Section titled “Or set it up by hand: choose where JOUST comes from”
  • BloxBean release repository
  • Your checkout, via mavenLocal

Releases are published to https://repo.bloxbean.org/maven/releases. Use as <version> below the newest release whose tag starts with v on the releases page (not the “Development snapshot” entry), without the v. The quickest check is npm view @julclang/joust version, since each release publishes the npm packages at the same version. Nothing is on Maven Central yet.

To try what is on main before it is released, publish the library modules of your checkout to ~/.m2:

This publishes julc-state-api (with its onchain jar), -processor, -runtime, -testkit, -verifier, -dsl and -server. Add mavenLocal() to the repositories below.

The build files by hand

Section titled “The build files by hand”
  • Directorymy-counter/
    • settings.gradle
    • gradle.properties
    • build.gradle
    • gradlew (copied from the JOUST checkout, with gradle/wrapper/)
    • Directorysrc/
      • Directorymain/java/app/
        • Counter.java
        • Devnet.java
        • CounterMain.java
      • Directorytest/java/app/
        • CounterTest.java

julcVersion is JuLC’s processor, the one that compiles your validator, and cclVersion is cardano-client-lib’s. Take both from the release you chose: its gradle/libs.versions.toml (open it at the tag v<version>) names the julc and cardano-client-lib versions it was built and tested with. The Gradle plugin does this for you.

What each line on the annotation processor path is for:

Dependency Why it is there
julc-state-processor The JOUST processor: generates <Name>Validator, <Name>Client and the description
julc-annotation-processor JuLC’s processor: compiles the generated validator to UPLC in the next round
julc-state-api:<version>:onchain The julc-state-api sources, under META-INF/plutus-sources/. JuLC compiles against its own on-chain API plus library sources it finds on the processor path; without these it cannot see Ctx, Require, Payouts and the rest

Inside the JOUST build: a directory, not a jar

Modules inside the JOUST repository use the same bundle as a directory: annotationProcessor project(path: ':julc-state-api', configuration: 'onchainSources'), as in examples/counter/build.gradle. A jar that is rebuilt while a Gradle daemon is running can make JuLC’s source scan silently find nothing (ADR-0001 F8). A published jar does not change, so this rarely matters outside the repository; if a build suddenly reports that JuLC cannot resolve Ctx or Require, run ./gradlew --stop and build again.

Build

Section titled “Build”

The build writes:

Output Where What it is
CounterValidator.java build/generated/sources/annotationProcessor/java/main/app/ The on-chain validator source (MINT + SPEND)
CounterClient.java same The typed client: deploy, at, increment, reset, close, count, state
CounterValidator.plutus.json build/classes/java/main/META-INF/plutus/ The compiled UPLC script; the runtime and the testkit load it from the classpath
app.Counter.json build/classes/java/main/META-INF/joust/ The description (CIP-57 plus x-joust) JavaScript clients are generated from

Read the generated sources: they are ordinary Java, and every check the validator makes is visible in CounterValidator.java. If your contract breaks a rule (an int in a method, two @Init methods, a @Payable without Ctx), the build fails with a compiler error on the offending line; see Java.

Troubleshooting

Section titled “Troubleshooting”
Symptom Cause and fix
Could not find org.julclang:julc-... A repository is missing, or julcVersion is not the one your JOUST needs. Add the BloxBean release repository (and https://repo.bloxbean.org/maven/snapshots for a development snapshot) and use the julc entry of gradle/libs.versions.toml at your JOUST release’s tag
JuLC errors such as “cannot resolve” Ctx or Require The onchain bundle is missing from the annotation processor path, or a long-lived daemon holds a stale jar: check the dependency, then ./gradlew --stop
'int' in a @StateContract ... Use BigInteger SubsetLint: contract code computes in BigInteger only. See Java
PastHorizon from the node The validity window reaches beyond what the network can convert to time. Keep ttl short on DevKit (20 s in the examples)
