Why JOUST

JOUST (State Contract Simplified, pronounced “jowst”) lets you write a Cardano smart contract as a state record plus pure static methods, much as you would write an account-based contract. From that one class it generates the on-chain validator and a typed off-chain client. The same Java method runs in both places: on your machine to build the transaction, and on chain to check it.

The problem: a contract is three programs

Section titled “The problem: a contract is three programs”

Cardano uses the extended UTxO model (eUTxO). There are no accounts with storage. Instead:

  • A UTxO (unspent transaction output) is a coin sitting at an address. A transaction spends some UTxOs and creates new ones.
  • A UTxO at a script address can carry a datum: a piece of data, which is where a contract keeps its state.
  • To spend it, the transaction supplies a redeemer (the arguments of the call), and the validator script decides whether the spending transaction is acceptable.

The validator never computes anything for you. It only says yes or no to a transaction someone else built. So a working contract is really three programs that must agree:

  1. The validator, which inspects the whole transaction and approves or rejects it.
  2. The off-chain builder, which finds the current state UTxO, computes the next state, encodes datum and redeemer, picks inputs and outputs, sets the validity interval and signers, and submits.
  3. The glue between them: the datum and redeemer encodings, which both sides must read and write identically.

Most of the validator’s code has nothing to do with your business rule. It defends the state against transactions that are well formed but malicious:

A validator must check that… Or an attacker can…
the state UTxO carries a unique token, minted once forge a second “instance” with any state
exactly one output continues the state, at the same address drop the state, or move it to their own address
the new datum is exactly the computed next state write any state they like
the output holds exactly the right value skim lovelace, or add junk tokens that make it unspendable
payouts are tagged per instance let one output pay for two contracts (double satisfaction)
the caller signed, and time claims match the transaction act for someone else, or lie about the time
the datum stays small enough for its min-ADA deposit grow the state until the UTxO can never be spent

Get any of these wrong and funds can be stolen or locked forever. And every rule you write on chain you write again off chain, in another shape, and keep in sync by hand.

One method, run twice

Section titled “One method, run twice”

The idea that makes this work is to compute off chain and re-check on chain with the same code:

JuLC compiles a subset of Java to UPLC, Cardano’s on-chain language, and its data types (records, JulcList, JulcMap) also run as plain Java. So the method you wrote is both the transaction builder’s logic and the validator’s logic. There is no second implementation to keep in sync.

Two practical consequences:

  • Rules fail early and cheaply. The generated client runs your method first. A failing Require.that throws a RequireException with your message before anything is built or submitted, and costs nothing.
  • You test the real thing. The same method is unit-testable as plain Java, and the testkit evaluates the validator as compiled, against the transactions the runtime builds.

What is generated and checked for you

Section titled “What is generated and checked for you”

For each @StateContract class, the JOUST annotation processor generates:

  • <Name>Validator: a JuLC multi-validator (minting and spending in one script), compiled to UPLC.
  • <Name>Client: a typed client on cardano-client-lib, with one method per action, destroy and view.
  • A description (META-INF/joust/<package>.<Name>.json): a CIP-57 schema plus JOUST metadata, from which JavaScript clients are generated.

The generated validator enforces the invariants of ADR-0001 §4, whatever your methods do:

ID The validator enforces
I1 One seed UTxO gives one instance: it is consumed, and exactly one thread token is minted, named by its hash
I2 The initial datum equals your @Init result, at the contract’s address
I3 Exact value: no lovelace skimmed or added, no token dust; a destroy allocates everything
I4 Exactly one continuing output, at the same address, whose inline datum equals your method’s result
I5, I6 The Ctx caller signed; received, balance and the validity bounds match the transaction
I7 Every payout is paid, tagged with this instance’s input, so one output cannot satisfy two instances
I8, I9 A destroy burns the thread token; the burn redeemer can only burn
I10 UTxOs at the script address without a thread token can never be spent
I11 @OnlyOwner, @SignedBy, @ValidAfter, @ValidBefore hold against the current state
I12 State outputs sit at the script’s own address, with no reference script attached
I13 The serialised state never exceeds maxDatumBytes, so no call can outgrow the deposit
I14 Actions never spend the min-ADA deposit

Each example runs the attack suite (Attacks in julc-state-testkit), which mutates every accepted transaction in each way these invariants forbid and checks that the validator rejects every mutation. See Testing and the Security model.

The cost is measured, not guessed: the counter’s validator is 5,631 bytes, and an increment costs 73.4M CPU and 213k memory units on chain (from the budgets table in examples/README.md, measured by the harness tests).

Java first; .jsc and JavaScript too

Section titled “Java first; .jsc and JavaScript too”

Java is JOUST’s first-class language: you write the contract in Java (or in .jsc, a smaller syntax that lowers to the same Java) and call it from Java through a generated client on cardano-client-lib. JavaScript is supported too, experimentally: its toolchain and runtime run as WebAssembly built with GraalVM Web Image, itself experimental.

  • Java
  • .jsc
  • JavaScript

Write the contract in Java and build it with Gradle on JDK 25. The processor generates the validator and a Java client; the Java runtime builds, submits and confirms transactions. Start with the Java quick start.

.jsc reads like TypeScript, with immutable values, and is lowered to a Java @StateContract, then compiled exactly like hand-written Java. It is a preview. See .jsc.

Experimental. The npm path needs only Node: the toolchain compiles .java and .jsc contracts in Node (no JDK), and pages and Node apps call them through generated JavaScript clients, with a CIP-30 browser wallet signing. Start with the npm quick start and JavaScript clients.

Beyond one state UTxO

Section titled “Beyond one state UTxO”

A single state UTxO can be updated about once per block, and holds only what fits in one datum. JOUST makes the way state maps onto UTxOs an explicit choice, so you can pick the one your contract needs:

MerkleMaps

Unbounded maps (token balances, registries) in a 32-byte root, with proofs checked by a shared verifier. MerkleMaps

Owned objects

One UTxO per user object beside shared state, so users never contend with each other. Owned objects

Keyed objects

One UTxO per key, at most one per key: ballots, names, positions, updated in parallel. Keyed objects

Batched intents

Users lock requests in parallel; a permissionless batcher applies many in one transaction. Batched intents

Assets and composition

Native tokens, contract-minted tokens, several contracts in one transaction, reads of other contracts. Native assets, Composition

There is more: deploy-time parameters, M-of-N quorums, invariants and events, staking and governance purposes, upgrades, and deposits between contracts. How JOUST works gives the overview.

Who it is for

Section titled “Who it is for”
  • Java developers who want to write Cardano contracts without learning a new language or the eUTxO plumbing.
  • JavaScript and TypeScript developers who want a typed client and a page that verifies every transaction before the wallet signs it.
  • Cardano developers who want the safety invariants generated, attack-tested and the same every time, and the business logic written once.

JOUST is not the right tool if you need to hand-tune every byte of a script, or if your design depends on a transaction shape that the state-machine model does not express. Generated checks cost bytes and budget, though the examples stay far below the limits (see Fees and script size).

Status

Section titled “Status”

Experimental: a research and learning project

JOUST is an experimental project created mainly for research and exploration of state-oriented smart contracts on Cardano. It is AI-generated, with human-assisted design, testing and verification. Do not use it in production.

It is pre-release. Its releases are listed on the releases page: the Maven modules are in the BloxBean release repository, https://repo.bloxbean.org/maven/releases (nothing is on Maven Central yet), and the npm packages (@julclang/joust, @julclang/joust-runtime, @julclang/state-client, create-joust) are on npmjs.org. Both quick starts walk through the setup.

What works today: every example in examples/ is generated, tested against the attack suite, and runs end to end on Yaci DevKit, a local Cardano network. The optimistic L2 (examples/rollup) is a working spike, not a product. APIs can still change before the first release; the Status and roadmap page tracks what is next.
