Quick start: JavaScript & TypeScript

Experimental

The npm path runs JOUST’s compiler and runtime as WebAssembly (built with GraalVM Web Image, itself experimental). For you that means: commands and APIs may change between pre-releases, a page loads about 20 MB of WebAssembly, and it is for DevKit and testnets, not for holding value. Java with Gradle and cardano-client-lib is the supported, first-class path: see Quick start: Java.

This page takes you from an empty folder to a Cardano contract you can call from Node and from a browser page, with Node and npm only: no JDK, no Gradle, no GraalVM. The contract is written in JOUST’s .jsc language (or in Java), and joust build compiles it with a toolchain engine that runs as WebAssembly in Node.

You will:

  • create a project with npm create joust: a Counter contract and a short Node script that calls it;
  • build the contract into a validator and a typed JavaScript client;
  • deploy it on a local network (Yaci DevKit) and call it from the script and from a test;
  • then create the browser version, connect a wallet and call the contract from a page.

Prerequisites

Section titled “Prerequisites”

  • Node 22 or newer. The engines need Wasm exception references, which the runtime switches on itself on Node 22.

  • Yaci DevKit, a local Cardano network, started with its indexer, Yaci Store:

    This gives a Blockfrost-compatible chain API on http://localhost:8080/api/v1, DevKit’s admin API (slot clock, faucet) on :10000, and the Yaci Viewer explorer on http://localhost:5173.

  • The JOUST npm packages come from npmjs.org: npm create joust@latest installs what it needs. Their versions follow JOUST’s releases.

  • Yaci DevKit, installed once with npm install -g @bloxbean/yaci-devkit (Install JOUST). Start it in a terminal of its own and leave it running. It is a private network on your machine: nothing costs real money.

  • Optionally, the native joust (brew install bloxbean/tap/joust), if you also want to create Gradle projects from the same command. Install JOUST covers each tool.

Create and build the app

Section titled “Create and build the app”

  1. Create the project.

    • npm
    • The native joust

    The native joust fetches create-joust at its own version and runs it, so the project gets that JOUST version.

    create-joust writes a Counter contract in .jsc (contracts/app/Counter.jsc) and a Node script that calls it (index.js), and names the package after the folder. It refuses a folder that is not empty. Two options change what it writes (after --, as npm create passes them on):

    Option Values
    --lang jsc (the default) or java: the same counter in Java, contracts/app/Counter.java
    --template node (the default): index.js; web: a browser page instead (below)

    The contract is the same in both languages:

    It is written in .jsc, a language preview (.jsc): a later JOUST may compile the same file to a different script hash, so use it on DevKit and testnets, not to hold value. Beside it, create-joust writes Counter.abi.json, the contract’s ABI manifest: how its state and its calls are encoded on chain. A build fails when the manifest is missing or differs from what the contract now compiles to, so an encoding change cannot slip through; npx joust build --accept-abi accepts a change you intend, to review and commit.

    joust build generates the same description and the same JavaScript client from Counter.jsc as from Counter.java, so nothing else in the project depends on the language.

    In this project, joust <command> means npx joust <command> or the matching npm run script; a native joust hands over to the same package. Run npx joust only inside the project, after npm install.

  2. Check the JOUST version. The three JOUST packages in package.json share one version:

    Compare it with the newest release on the releases page. To upgrade, set all three to the new version and run npm install.

  3. Build the contract.

    joust build compiles every .java and .jsc file under contracts/ into build/joust/:

    The size and hash depend on the contract, its language and the toolchain’s version. The four transitions are the contract’s four methods (init, increment, reset, close), compiled so the runtime engine can run them off chain.

    No DevKit yet? npm test and the playground run offline, with no chain.

  4. Deploy it on DevKit.

    joust deploy publishes the validator as a reference script: a UTxO that carries the script, so later transactions point to it instead of including it. (A UTxO, an unspent transaction output, is a coin on Cardano: an address, a value and optional data. See the glossary.) On DevKit it pays with a key it makes and keeps in .joust/devkit-wallet.json, topped up from DevKit’s faucet. It writes what it published to build/joust/deployments.devkit.json:

  5. Run the script.

    The refusal names where it came from: line 22 of the template’s Counter.jsc, which has comments the copy above leaves out. npm start runs steps 3 to 5 in one go. index.js is the whole app:

    Each call runs the contract’s own code in the runtime engine to compute the next state, builds the transaction, signs it with the wallet’s key and submits it. On chain, the validator runs the same code again and checks the result. counter.deploy() creates a counter (the contract’s init); joust deploy published the contract.

  6. Run the tests.

    test/counter.test.js makes the same calls against an in-memory ledger, with no chain, and checks each result: the count is 7, an increment of 0 is refused, the counter is gone after close, and the attack suite found no mutation the script accepts (offline tests). test/devkit/counter.test.js makes them on DevKit.

Try it in the playground

Section titled “Try it in the playground”

The playground is a page in your browser where you call your contract without writing any code: pick who signs, fill in a form, review the transaction, approve. It needs Node.js 22 or newer, and runs offline (no DevKit) by default.

It builds first, as joust build does, then opens the page.

  1. Click Counter under Contracts. Its operations appear as cards: init, increment, reset and close.
  2. Click Review… on init. The first call publishes the contract’s script, so you approve a Review publication dialog first, then the call’s own. Click Approve and sign as Alice in each. The new counter appears under Instances.
  3. Type 5 into by on the increment card, click Review… and approve. The state shows the count 5.
  4. Choose Bob under Identities and click Review… on reset. Bob is not the owner, so it is refused before anything is signed.

Ctrl-C in the terminal stops it. --mode devkit runs the same page against a running Yaci DevKit. The playground explains everything on the page.

The project

Section titled “The project”
  • Directorycontracts/
    • Directoryapp/
      • Counter.jsc the contract (Counter.java with –lang java)
      • Counter.abi.json its ABI manifest (.jsc only)
  • index.js the app: deploys a counter and calls it
  • Directorytest/
    • counter.test.js the offline test
    • Directorydevkit/
      • counter.test.js the same calls on DevKit
  • Directorybuild/ written by joust build and joust deploy
    • Directoryjoust/
      • Directorygenerated/ the Java lowered from Counter.jsc, with its source map
        • …
      • Counter.js the typed client, with the contract’s description pinned
      • Counter.d.ts its TypeScript types
      • Counter.json the description
      • Counter.plutus the compiled validator (CBOR hex)
      • contracts.json what the runtime engine needs
      • deployments.devkit.json what joust deploy published
      • joust.lock.json the versions that built it
  • joust.config.json contracts, output and networks
  • package.json

In .jsc, a contract is its state and its init, action, destroy and view declarations; joust build lowers it to a Java contract and compiles that (.jsc). In Java, it is a State record and static methods marked @Init, @Action, @Destroy and @View, in the subset JuLC compiles (Your first contract). package.json holds these scripts:

Script Runs What it does
npm start joust build && joust deploy && node index.js build, deploy (once per script) and run the app
npm run build joust build compile contracts/ into build/joust/
npm run deploy joust deploy publish the reference scripts on the config’s network (DevKit)
npm test joust test build, then the offline tests

A browser page

Section titled “A browser page”

--template web makes the same project with a page instead of index.js:

  • Directorycontracts/
    • Directoryapp/
      • Counter.jsc the same contract
      • Counter.abi.json its ABI manifest
  • Directorypage/
    • index.html the Counter page
    • main.js the page’s code: wallet, review dialog, calls
    • engine.worker.js the runtime engine, in a Web Worker
  • Directorytest/
    • counter.test.js the offline test
    • Directorydevkit/ the DevKit test
      • …
  • joust.config.json
  • vite.config.js the page’s Vite config, with @julclang/joust/vite
  • package.json

The Counter dApp tutorial walks through every file (it uses the Java version of the contract, which joust build compiles in Node, with no JDK; the .jsc one works the same). Its package.json has these scripts:

Script Runs What it does
npm run build joust build compile contracts/ into build/joust/
npm run deploy joust deploy publish the reference scripts on the config’s network (DevKit)
npm run deploy:preview joust deploy --network preview the same on the preview testnet
npm test joust test build, then the offline tests
npm run dev joust dev build, deploy, serve the page; rebuild and redeploy on save
npm run dev:preview joust dev --network preview the same on preview
npm run build:page vite build the page as static files in dist/
npm run build:page:preview vite build --mode preview the same, for preview
npm run serve joust serve serve dist/ with the chain API at /chain
npm run serve:preview joust serve --network preview the same on preview

Open the page

Section titled “Open the page”

joust dev attaches to DevKit, builds and deploys, then serves the page at http://127.0.0.1:5178. It keeps watching contracts/: save Counter.jsc and it rebuilds and redeploys.

  1. Wait for the activity log to say Runtime engine ready. The page loads JOUST’s runtime engine (about 20 MB of Wasm) into a Web Worker once per page load, and prepares its own transactions with it.

  2. Choose DevKit key (in this page) and press Connect. Browser wallets cannot join a private devnet, so on DevKit the page offers a key it keeps in localStorage. Press Top up 1000 ADA to fund it from the faucet.

  3. Press Create a counter. A dialog shows what the page checked in the prepared transaction: the redeemer is this call on the pinned script, what your wallet pays in all, the next state, and that nothing else is in it. Press Sign in the wallet.

  4. Press +1 a few times. Then press +0: the contract refuses it (increment must be positive) while the transaction is being prepared, so no wallet is ever asked to sign.

  5. Press Close. Only the owner can close; the counter’s deposit comes back to your wallet.

Each transaction hash in the log links to Yaci Viewer, DevKit’s explorer.

Build the page as static files

Section titled “Build the page as static files”

A build is for one network: the network, its deployments, the contracts and the engine’s integrity hashes are inlined into the page, and the engine’s two files are copied into dist/joust/engine-<id>/. joust serve serves dist/ as plain files, adds the chain API at /chain (and DevKit’s faucet), and does nothing else: no build, no deploy, no prepare service. See Pages.

Note

DevKit’s slot clock changes when DevKit restarts. After a restart, run npm run deploy and npm run build:page again.

Use TypeScript

Section titled “Use TypeScript”

The page can be TypeScript. Vite compiles .ts files (it does not type-check them), so renaming is enough to run:

The generated client is typed already: npm run build writes build/joust/Counter.d.ts beside Counter.js, with a type for every state, argument and result. A call with a wrong argument name fails to compile:

Two modules a page imports ship no declarations yet (virtual:joust/network and @julclang/joust-runtime/page). Declare them in page/joust-env.d.ts, add a tsconfig.json, and type-check with npx tsc --noEmit: the TypeScript page has both declarations and a typed main.ts, checked with strict on. The template’s main.js is plain JavaScript: under strict it needs parameter types before tsc passes.

Try it on preview with Eternl or Lace

Section titled “Try it on preview with Eternl or Lace”

Preview is a public Cardano testnet, so real browser wallets work there. You need a Blockfrost project id for preview and a funded preview key to pay the deployment:

Switch Eternl or Lace to preview, reload the page, choose it in the wallet list and connect. The Deploy to preview tutorial covers this and static hosting step by step.

What you just used

Section titled “What you just used”
  • The toolchain engine (in @julclang/joust) compiled .jsc or Java to a Cardano validator, a description and a typed client, in Node.
  • The runtime engine (in @julclang/joust-runtime) prepared each transaction from the chain, in Node for the script and the test, and in a Web Worker for the page. It holds no keys.
  • The page verifier (in @julclang/state-client) checked every prepared transaction against the contract’s description and the chain before the wallet was asked to sign.
  • The validator re-ran each method on chain and checked that the new state is what the method computes.
