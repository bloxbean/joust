Get started

State contracts for Cardano, in Java or .jsc.

Write a state record and the methods that change it. JOUST compiles the same method into the on-chain validator and into a typed client for your app, in Java on cardano-client-lib or in JavaScript (experimental), so your contract and the code that calls it can never disagree.

@StateContract(maxDatumBytes = 128)
public class Counter {

    public record State(BigInteger count, byte[] owner) {}

    @Init
    public static State init(Ctx ctx) {
        return new State(BigInteger.ZERO, ctx.caller());
    }

    @Action
    public static State increment(State s, BigInteger by) {
        Require.that(by.compareTo(BigInteger.ZERO) > 0, "increment must be positive");
        return new State(s.count().add(by), s.owner());
    }

    @Action @OnlyOwner
    public static State reset(State s) {
        return new State(BigInteger.ZERO, s.owner());
    }

    @Destroy @OnlyOwner
    public static JulcList<Payout> close(State s, Ctx ctx) {
        return Payouts.of(s.owner(), ctx.balance());
    }

    @View
    public static BigInteger count(State s) {
        return s.count();
    }
}
// A runtime over any cardano-client-lib backend: Blockfrost, Yaci Store, ...
BackendService backend = new BFBackendService(Constants.BLOCKFROST_PREVIEW_URL, projectId);
StateRuntime runtime = StateRuntime.builder(backend)
        .network(Networks.preview())
        .chainTime(new SlotChainTime(0, 1_666_656_000_000L, 1000, backend))
        .build();

// CounterClient is generated from Counter.java; alice and bob are CCL Accounts.
CounterClient counter = CounterClient.deploy(runtime, alice);
counter.increment(bob, BigInteger.valueOf(5));   // runs increment() on the JVM, then submits
System.out.println("count = " + counter.count()); // the @View, read from the chain

try {
    counter.reset(bob);                           // bob is not the owner
} catch (RequireException e) {
    // refused on the JVM: nothing was built or submitted
}
counter.close(alice);                             // burns the token, pays the deposit back

package app

contract Counter(maxDatumBytes = 128) {
  state { count: Int, owner: Key }

  init() {
    return { count: 0, owner: caller }
  }

  action increment(by: Int) {
    require(by > 0, "increment must be positive")
    return { ...state, count: count + by }
  }

  action reset() only owner {
    return { ...state, count: 0 }
  }

  destroy close() only owner {
    pay(owner, balance)
  }

  view count(): Int = count
}

One method. Two places.

The idea JOUST is built on: the rule you write is the rule the chain enforces.

Why JOUST

Cardano's model is safe and parallel. Writing for it by hand is slow and easy to get wrong. JOUST keeps the model and removes the plumbing.

No datums, redeemers or UTxO plumbing

Write a state record and the methods that change it. JOUST generates the validator, the minting policy for instance tokens, the redeemers and the transaction building.

One method, never out of sync

The method that computes the next state on the JVM is the method the validator re-runs on chain. The client and the contract cannot disagree.

Safe by construction

Every generated validator enforces a one-shot thread token, the exact datum and value, a verified caller and validity window, and tagged payouts. Each example is attack-tested.

Plain Java, plain Gradle

A JOUST contract is an annotated Java class. The annotation processor runs inside javac; JuLC compiles the on-chain part to Plutus V3.

Typed clients on cardano-client-lib

Each contract gets a generated Java client: deploy, call, read views. A failing rule is caught on the JVM before anything is built or paid for.

All of Cardano

Native assets and minting, MerkleMap state, owned objects, batched intents, composition, staking, DRep votes and upgrades: as annotations, not hand-written scripts.

What JOUST generates

From one annotated class, during your build (Gradle, or joust build with npm): an on-chain validator compiled by JuLC, a typed Java client on cardano-client-lib, and a description for other languages.

Experimental

JavaScript and the browser, with npm

The same contracts from Node and from web pages, with no JDK: JOUST's toolchain and runtime run as WebAssembly built with GraalVM Web Image. Both are experimental. Java is the supported path.

import { Counter } from '../build/joust/Counter.js';   // generated by joust build
import { blockfrostChain } from '@julclang/state-client';
import { engineWorker } from '@julclang/joust-runtime/page';
import net from 'virtual:joust/network';

// The runtime engine runs in a Web Worker: the page builds its own transactions.
const service = engineWorker(new Worker(new URL('./engine.worker.js', import.meta.url),
  { type: 'module' }), net);
const chain = blockfrostChain(new URL(net.chain, location.href).href);
const counter = new Counter({ service, chain, deployment: net.deployments['app.Counter'] });
const wallet = await window.cardano.eternl.enable();          // any CIP-30 wallet, on preview

const { instance } = await counter.deploy(wallet, {});   // the wallet signs
await instance.increment(wallet, { by: 1n });            // verified by the page first
await instance.increment(wallet, { by: 0n })             // refused before signing:
  .catch((e) => console.log(e.message));                 // "increment must be positive"

  • Pages build their own transactions. The runtime engine runs in a Web Worker; no server prepares anything.
  • Verified before signing. The page checks every transaction against the contract's pinned description before a CIP-30 wallet signs.
  • Pinned engine. Static builds pin the engine's hashes (SRI): a browser refuses an engine whose bytes differ.
  • Maps in the browser. MerkleMap state is mirrored in IndexedDB and rebuilt from the chain when missing.
