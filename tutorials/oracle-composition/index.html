Oracle and composition

In this tutorial you run examples/oracle: an Oracle contract that a publisher updates with a price, and a Shop that sells credits at that price. The shop reads the oracle’s state with @Reads, checked on chain, without spending it. Then you compose a purchase and another oracle’s update into one transaction, and see Compose refuse a transaction that would spend the same instance twice.

Experimental, pre-release

JOUST is experimental and pre-release (not for production). The tutorial runs in a JOUST checkout with JDK 25; for your own project, start from joust new (Quick start: Java & Gradle). You also need Yaci DevKit: yaci-devkit up --enable-yaci-store.

The two contracts

Section titled “The two contracts”

  1. The oracle stores a price and when it was set:

    updatedAt is ctx.validFrom(), the start of the transaction’s validity window, which the ledger enforces. A reader can then tell how old the price is.

  2. The shop pins the oracle in its params:

    ForeignInstance(policy, instance) names one oracle instance of one oracle script. Because it is in @Params, it is applied to the shop’s script at deploy: a different oracle means a different shop script and address. @Reads("params.oracle") Oracle.State price hands buy that oracle’s current state.

    What this taught: the trusted source is part of the reader’s identity, never something a caller supplies.

  3. What the shop’s validator checks. For price, the transaction must carry a reference input that holds exactly one token of the oracle’s policy, named with the 32-byte instance id, at the oracle’s script address, with an inline datum shaped like Oracle.State. Freshness is not automatic: a reference input does not run the oracle’s validator, so an old state stays readable. That is why buy checks updatedAt against maxAgeMs.

Run it

Section titled “Run it”

  1. Harness tests: spoofed oracles.

    ShopTest buys at a fresh price, then tries every way to feed the shop a price it should not trust:

    Each is refused by the validator.

    What this taught: @Reads checks where the state comes from; your method checks whether it is recent enough.

  2. Deploy an oracle, then a shop that reads it.

    The oracle starts at 3 ADA. Two credits cost exactly 6 ADA; one credit for 2 ADA is refused by the JVM run before anything is submitted. The client finds the oracle’s UTxO and adds it as a reference input: buy takes only the quantity and the payment.

    What this taught: reading another contract costs the caller nothing extra to write.

  3. Compose a purchase with another contract’s call.

    Inside add, each call is an ordinary client call. Compose runs it in capture mode, so it writes into one shared transaction instead of submitting: the shop’s spend with the first oracle as a reference input, the second oracle’s spend, both redeemers, and the signatures of the buyer and publisher2. It picks a validity window both calls accept, runs both methods in it, checks every output after balancing, and submits once. Both happen, or neither.

    What this taught: composition is a runtime feature; each validator still checks only its own transition.

  4. Watch a composition be refused.

    Two calls on one instance would spend the same UTxO twice. Compose refuses before building, as it does for two mints under one policy, an empty common window, or one key signing for two calls without allowSharedSigners().

From JavaScript

Section titled “From JavaScript”

The npm runtime runs the same contracts, and composes the same way:

To compose, pass steps to rt.compose(wallet, steps), each { contract, method, instance, args, pay }. A composed transaction is verified call by call and as a whole before the wallet signs; see Reads and composition.

What you built

Section titled “What you built”
  • A reader whose trusted source is fixed in its script, checked on chain by token, address and datum shape.
  • A freshness rule, written by you, on top of that.
  • One transaction that calls two contracts, all or nothing.
