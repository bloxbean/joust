Multisig treasury

This tutorial walks through examples/treasury, a multisig treasury, and runs it on Yaci DevKit. A council of keys decides by quorum; a guardian fixed at deploy time can freeze the treasury; every state keeps a reachable quorum; and payments and council changes emit events that indexers can trust.

You will use five features from ADR-0009: @Params, @Quorum, @AuthorizedBy with a script, @Invariant, and events.

Experimental, pre-release

JOUST is experimental and pre-release (not for production). The Java path needs JDK 25; JOUST’s releases are in the BloxBean release repository (see the Java quick start). For the DevKit run, start Yaci DevKit with yaci-devkit up --enable-yaci-store.

Build it

Section titled “Build it”

  1. Deploy-time parameters. The guardian and the payout cap are fixed when the treasury is deployed:

    @Params values are applied to the script itself, so each Config gives a different script hash, policy id and address. Nobody can change them later, and no action can swap the guardian. guardian is a Credential: a key or a script. The council and quorum live in the state, because the council can rotate.

    What this taught: put what must never change in @Params; what may change, in the state.

  2. Open and fund.

    The params come first in @Init (there is no state yet), right after the state elsewhere. fund returns the state unchanged: the validator’s exact value check still requires the treasury’s UTxO to grow by exactly received.

    What this taught: a method declares the params record to read them; callers never pass it.

  3. Pay by quorum, and emit an event.

    • @Quorum(keys = "council", threshold = "quorum") requires at least quorum of the transaction’s signers to be in the current council.
    • Spent has three components the processor recognises by name: state, payouts and events.
    • The events travel in the redeemer, and the validator requires them to equal what the method returned. An event read from a valid JOUST transaction is therefore exactly what the contract emitted.

    What this taught: an M-of-N rule is one annotation; events are part of the checked result.

  4. Rotate the council, guarded by an invariant.

    The quorum check reads the input state, so a rotation needs the current council’s approval and cannot authorise itself. The @Invariant runs on every state the validator accepts as an output (and in the client, first), so no rotation can leave a quorum nobody can reach. Because the contract uses @Quorum, the validator also checks that council keys are strictly ascending and 28 bytes each.

    What this taught: invariants protect the contract from transitions that would lock it.

  5. Freeze through a guardian script.

    @AuthorizedBy("params.guardian") needs the guardian’s approval. On DevKit the guardian is a script, a withdraw-zero governor: a transaction that withdraws zero lovelace from the script’s reward account makes the ledger run it. The governor’s redeemer must list Approval(policy, target, action) naming this treasury, this instance and the freeze action, so one approval cannot be reused elsewhere:

    Guardian approves when its owner signs, and refuses any other purpose, so nobody can deregister it. A real governor would decide by votes or another contract’s state.

    What this taught: another script can authorise an action, bound to exactly that action.

Run it

Section titled “Run it”

The treasury has no app class; its DevKit test plays the whole flow.

  1. Read the flow.

    • Java
    • JavaScript

    The generated client takes @Quorum co-signers as trailing Accounts, and an Authorization for @AuthorizedBy. DevKit.registerScriptStake is the examples’ helper that registers the governor’s stake credential.

    Each co-signer’s wallet signs the same transaction, after the page has verified it.

  2. Run the tests.

    With DevKit up, TreasuryDevnetTest > quorumGuardianEvents() runs the flow above on the local network and passes. Without DevKit it is skipped, and the harness tests still run. Gradle lists each test as PASSED.

  3. See what the harness proved. TreasuryTest evaluates the compiled validator against each transaction and runs the attack suite on every accepted one. Beyond the happy paths, it checks that the validator refuses:

    • a council with duplicate keys, or a quorum above the council’s size, at creation;
    • a payment signed by one of three, or by one member and a stranger;
    • forged events in the redeemer;
    • a rotation to duplicate or unsorted keys;
    • a freeze with no guardian withdrawal, an approval for another instance or another action, or another script’s withdrawal;
    • a close with one signature.

    A payment over maxPayout is refused by the method itself, on the JVM (RequireException).

    Run ./gradlew :examples:treasury:test --info to see the lines the tests print, including each transaction’s budget and how many attacks it rejected.

What you built

Section titled “What you built”

A treasury where:

  • spending needs a quorum of the council, checked against the council before the call;
  • the council can change, but never into one that cannot reach its quorum;
  • an independent script can freeze it, with an approval bound to one instance and one action;
  • the guardian and the payout cap are fixed by the script hash;
  • every payment and council change is recorded as an event the validator checked.

About 70 lines of contract code; every one of those guarantees is generated.
