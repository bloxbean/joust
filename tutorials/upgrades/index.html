Upgrading a contract

A deployed script cannot change. To ship a new version you deploy a new contract and move each live instance into it. In this tutorial you run examples/upgrade: a CounterV1 instance, with a count and some funds, migrates into CounterV2, which adds a step size. Both validators check the move in one transaction, so the funds can only go where both sides agree.

Experimental, pre-release

JOUST is experimental and pre-release (not for production). The Java path needs JDK 25; JOUST’s releases are in the BloxBean release repository (see the Java quick start). For the DevKit run, start Yaci DevKit with yaci-devkit up --enable-yaci-store.

Build it

Section titled “Build it”

  1. Version 1 names its successor. CounterV1 holds an admin, a successor policy (empty at first) and a count:

    Only the admin can set successor. If you are writing a v1 today and may want to upgrade later, this is the hook to add: a field for the successor’s policy id, and an admin-only setter.

    What this taught: an upgradeable contract plans for it; the admin is trusted to name the successor.

  2. Version 1 migrates out.

    @MigrateTo("successor") turns this destroy into a migration. Instead of paying ctx.balance() out, its validator requires that the policy in successor mints a token named blake2b_256(this state UTxO), that one output at that policy’s script address holds it, and that this output holds at least everything the instance held.

    What this taught: the old side lets its funds go only into the successor it names.

  3. Version 2 adopts. CounterV2 pins v1 in its @Params and adopts its state:

    adopt takes the params and v1’s state record, and maps it to v2’s: the admin and count carry over, the new step starts at 1. Its validator checks that the seed is a genuine v1 state UTxO (v1’s 32-byte token at v1’s address, with a datum shaped like CounterV1.State), that v1’s token is burned in the same transaction, and that the new instance holds exactly v1’s lovelace.

    Why does v2 pin v1 in params while v1 names v2 in its state? If both used params, each script hash would depend on the other’s: a cycle. So one side must use a state field.

    What this taught: the new side accepts only an instance of the predecessor it names, and only if that instance ends.

Run the migration

Section titled “Run the migration”

  1. Read the flow. The DevKit test plays the whole migration:

    CounterV2Client.policyIdFor(cfg) computes v2’s policy id from its params before anything is deployed, so v1’s admin can name it. Compose captures the two client calls and builds one transaction from them; on its own, neither half is valid. adopt refuses to run outside a Compose.

  2. Run it.

    With DevKit up, UpgradeDevnetTest > v1MigratesToV2() passes: the v1 counter (count 2, 10 ADA plus its deposit) becomes a v2 counter with the same count and exactly the same lovelace, v1’s instance is gone, and v2’s increment works. Without DevKit it is skipped, and the harness test still runs.

  3. See what the harness proved. UpgradeTest builds the migration transaction and evaluates it with both contracts’ harnesses (v1’s spend and burn, v2’s adoption). It then checks the handshake against tampering:

    • v1 refuses a successor its admin did not name;
    • both sides refuse when the new instance holds less than the old;
    • v1 refuses when no successor token is minted;
    • v2 refuses to adopt when v1’s token is not burned.

A new id

The migrated instance has a new id: blake2b_256 of v1’s state UTxO reference. Keep adopted[0].instanceId(). The old instance is gone: v1.state() throws InstanceNotFoundException.

What you learned

Section titled “What you learned”
  • A migration is a handshake: @MigrateTo on the old side’s @Destroy, @Migrate on the new side’s creation.
  • The old side names the successor in an admin-set state field; the new side pins the predecessor in @Params.
  • Both halves must be in one transaction, built with Compose.
  • State moves through a plain Java function from the old record to the new one; funds move exactly.
  • Not yet supported for contracts with MerkleMaps, owned objects or native assets.
