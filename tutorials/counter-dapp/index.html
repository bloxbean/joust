A counter dApp in the browser

Experimental

The npm path runs JOUST’s toolchain and runtime as WebAssembly built with GraalVM Web Image, which is itself experimental. Java with Gradle and cardano-client-lib is the supported, first-class path: see Quick start: Java.

In this tutorial you build the Counter dApp that npm create joust gives you, and read every file that makes it work. At the end you have a page, served on Yaci DevKit, that creates counters, increments them and closes them, with each transaction prepared in the page itself, checked by the page and signed by a wallet.

You will learn:

  • how one Java method becomes both a validator and the code that builds the transaction;
  • what the generated client (Counter.js, Counter.d.ts) contains;
  • how the page runs the runtime engine in a Web Worker and gets its network from virtual:joust/network;
  • how the page connects CIP-30 wallets, and shows each call for review before signing;
  • what the page verifier checks, and why a bad call never reaches the wallet.

1. The contract

Section titled “1. The contract”

Each counter lives in one UTxO at the contract’s address. The UTxO holds a thread token that names the instance, and its datum (the data attached to the UTxO) is the State record. Calling an action spends that UTxO with a redeemer (the call and its arguments) and creates the next one. (These terms are in the glossary.)

  • @Init creates an instance; ctx.caller() is the key that signed the transaction, so the creator owns it.
  • increment takes no Ctx, so it needs no signature: anyone can call it. Require.that refuses a non-positive amount, on chain and off.
  • @OnlyOwner makes the validator require the owner field’s key to sign.
  • @Destroy ends the instance: its thread token is burned and close says where its value goes.

The contract chapters cover all of this in depth: State and lifecycle, Authorization, Require and errors.

2. What joust build writes

Section titled “2. What joust build writes”

joust dev ran joust build first. Its output, in build/joust/:

  • Directorybuild/joust/
    • Counter.json the description: CIP-57 schemas plus JOUST’s x-joust section
    • Counter.plutus the compiled validator, CBOR hex
    • Counter.js the client, with the description inlined
    • Counter.d.ts its types
    • contracts.json description, script and transition programs, for the runtime engine
    • joust.lock.json the toolchain version and each contract’s script hash
    • deployments.devkit.json written by joust deploy

The description is the contract’s interface: its state, every call and its redeemer, its arguments’ schemas, and the policies the validator enforces. Both the runtime engine and the page work from it. See the description format.

3. The engine in a worker

Section titled “3. The engine in a worker”

The page prepares its own transactions. The runtime engine (Wasm, about 20 MB) runs in a module worker, which is two lines:

page/main.js starts it and wraps it as a prepare service, the object a client asks for transactions:

  • virtual:joust/network comes from the Vite plugin, @julclang/joust/vite. Under joust dev it fetches /joust/network.json and the contracts when the page loads, so a redeploy after a save is picked up on reload. In vite build it is inlined for one network. Its chain is /chain: the dev server’s proxy, so a Blockfrost project id never reaches the page.
  • chain is the page’s own view of the chain. The verifier reads from it, independently of the engine.
  • engineWorker sends the engine’s URL, its integrity hashes and the network to the worker, and returns a service with prepare(request). service.ready resolves once the engine has loaded.
  • new Counter({ service, chain, deployment, onReview }): the deployment (policy, address, reference scripts) is pinned; the service builds; the page checks.

5. Calling the contract

Section titled “5. Calling the contract”

Each button calls the generated client with the wallet’s CIP-30 API:

One call such as inst.increment(app.api, { by: 1n }) does all of this:

  1. Encodes the arguments with the description’s schemas, and reads the wallet: its addresses, keys and the UTxOs it reports.
  2. Asks the service (the worker) to prepare the transaction. The engine fetches what it needs from the chain, runs increment as a compiled transition program to get the next state, and builds the unsigned transaction from the wallet’s own UTxOs.
  3. Verifies the transaction in the page, against the pinned description and deployment, the wallet and the chain.
  4. Calls onReview, which shows the review dialog.
  5. Asks the wallet to sign (signTx(cbor, true)), adds the witness to the original bytes, checks the hash, and submits through the wallet.
  6. Waits until the chain shows the transaction, and returns { txHash, report }.

act wraps each call, logs the outcome and links the transaction to the network’s explorer:

net.explorer is the network’s explorer from joust.config.json, with {tx} standing for the hash. DevKit’s default is Yaci Viewer, http://localhost:5173/transactions/{tx}.

6. The review dialog

Section titled “6. The review dialog”

onReview receives { contract, call, report, txHash } after the transaction has passed verification and before the wallet is asked. Resolve to go on; throw to cancel. The template shows what the page checked:

report.walletNet is what the wallet loses in lovelace, fee included (negative when it gains, as when close pays the deposit back). report.next is the next state, decoded from the new datum.

7. What the page verifier checks

Section titled “7. What the page verifier checks”

Neither the engine nor the chain API is trusted. Before onReview runs, verifyPrepared (in js/state-client/src/verify.js) checks the transaction against what the page knows itself. For a Counter call that means:

Check Refused when
Inputs anything but the wallet’s own UTxOs and this counter’s UTxO is spent
Redeemer it is not exactly the call the page asked for, with the page’s arguments, on the counter’s input
Script the counter’s UTxO is not at the pinned address, or a reference input is not a pinned one
Continuation there is not exactly one new counter UTxO with the token, an inline datum that decodes as State
Mint an action mints anything; close burns anything but its own token; a creation mints more than its new token
Wallet’s loss the wallet loses more than it pays, plus the fee (plus the new UTxO’s minimum ADA for a creation)
Others an output gives anyone else more than the script releases
Extras certificates, withdrawals, votes, metadata, other required signers, another network
Fee above what the protocol asks for this size and budget (times 1.2, plus 0.5 ADA), or above 3 ADA
Collateral not the wallet’s, not returned to the wallet, or more than 5 ADA at risk
Validity it ends more than 900 slots (15 minutes) from now, or starts later than 60 slots from now
Plan the engine’s plan of the transaction differs from the one the page derives from the bytes

What the page does not check, the validator does: that the next state is what increment computes, that close pays the owner, and that the script’s value is conserved. Together, the wallet risks nothing beyond the call it was shown. A refusal throws VerificationError, whose problems the page lists; the wallet is never opened.

8. The +0 refusal

Section titled “8. The +0 refusal”

Press +0 on a counter. The activity log marks increment(0) as failed, with the contract’s own message: increment must be positive.

This refusal does not come from the page verifier. When the engine prepares the call, it runs increment itself, compiled from the same Java method, and Require.that fails with the contract’s own message. No transaction is built, so no wallet is asked. The validator would refuse the same call on chain for the same reason; JOUST finds it before anything is signed or paid.

9. Try it

Section titled “9. Try it”

With npm run dev running, open http://127.0.0.1:5178 and:

  1. Choose DevKit key (in this page), Connect, then Top up 1000 ADA.
  2. Create a counter and review it: your wallet pays the fee and the counter’s deposit.
  3. Press +1 twice. The count shows 2; each review shows the next state.
  4. Press +0: refused before signing.
  5. Reset, then Close. Close’s review shows your wallet receiving the deposit back, net of the fee.
  6. Change increment in Counter.java (for example, also refuse amounts over 100) and save. The dev server rebuilds and redeploys a new script; reload the page and the new rule holds. Counters made by the old script stay with it.

What you learned

Section titled “What you learned”
  • A JOUST contract is a state record and pure methods. joust build turns it into a validator, a description and a typed client, and joust deploy publishes the validator as a reference script.
  • The page prepares transactions in a Web Worker with the runtime engine, which runs the contract’s own methods. A contract refusal surfaces there, before any wallet is involved.
  • The page verifies every transaction against the pinned description and deployment before onReview and the wallet see it. The validator enforces the rest on chain.
  • CIP-30 wallets and the DevKit key are interchangeable: the client only needs the CIP-30 API.
