Escrow and crowdfunding

Two contracts from the examples, each adding something the vault did not have:

  • examples/escrow: three parties, two ways to end (two @Destroy methods), and a rule that mixes identity and time.
  • examples/crowdfund: many backers in a JulcMap in the state, kept in canonical order with SortedMaps, refunds paid to the caller, and a capacity bounded by maxDatumBytes.

Experimental, pre-release

JOUST is experimental and pre-release (not for production). The Java path needs JDK 25; JOUST’s releases are in the BloxBean release repository (see the Java quick start). Start Yaci DevKit with yaci-devkit up --enable-yaci-store before the run steps.

Part 1: escrow

Section titled “Part 1: escrow”

A buyer locks the price. The buyer (or an arbiter) releases it to the seller once the goods arrive; the seller (or the arbiter) can refund the buyer at any time, and anyone can once the deadline has passed. Either way the instance ends and everything it holds goes to the winner.

  1. The state and the opening. The buyer deploys and funds the escrow in one step:

    seller and arbiter are arguments, payment key hashes. The buyer is whoever signs the deploy.

    What this taught: a payable @Init creates and funds an instance in one transaction.

  2. Release: two @Destroy methods. A contract may have several ways to end. release pays the seller:

    “Buyer or arbiter” is a choice between two keys, so it is written in the body with ctx.caller() (verified by a signature) and ByteStringLib.equals (never == on byte[]).

    What this taught: use Ctx and Require for authorisation an annotation cannot express.

  3. Refund: identity or time.

    Clock.after(ctx, t) holds only if the whole transaction happens at or after t. After the deadline the buyer, or anyone, can get the money back, so funds can never be stuck if the seller and arbiter disappear.

    What this taught: Clock composes with other conditions; give every contract a way out.

    Note

    .jsc allows after(t) and before(t) at the top of a require, alone or under && or ||, so this refund fits in .jsc too (caller == seller compares bytes by value):

    open says anyone may call a method that pays out; the body’s require is then its only guard.

  4. Run it.

    The output (ids and hashes differ):

    The escrow holds the 25 ADA price plus its 2.4 ADA deposit, and the release pays all of it to the seller: a destroy must allocate everything.

Part 2: crowdfund

Section titled “Part 2: crowdfund”

Backers contribute before a deadline. After it, if the goal was reached the creator claims everything; if not, each backer takes their contribution back, and the creator closes the empty campaign.

  1. A map in the state.

    backers maps each backer’s key hash to what they put in. The whole map lives in the datum, so its size is bounded by maxDatumBytes = 1024 (which sets a 6 ADA deposit).

    What this taught: collections can live in the state, and their size has a price.

  2. Contribute, keeping the map canonical.

    Why SortedMaps and not JulcMap.insert? insert prepends, so the map’s order depends on who contributed when. But cardano-client-lib writes inline datums in canonical CBOR, which sorts map keys. A map out of canonical order would be written differently from the state the validator recomputes, and the call would fail on chain. (It did, on DevKit, whenever backers arrived out of key order; that is how JOUST found the problem.) SortedMaps.put keeps the keys in canonical order on the JVM and on chain alike, and the runtime refuses a non-canonical state before it submits anything.

    What this taught: state maps must be canonical; SortedMaps does it for byte[]-keyed amounts.

  3. Refund the caller.

    The payout goes to ctx.caller(), the verified signer, so a backer can only refund themselves. containsKey comes before get, because get on a missing key aborts on chain without a message.

    What this taught: an action can pay the caller; check map membership before reading.

  4. Claim or close: @SignedBy("creator").

    @SignedBy("creator") names the state field whose key must sign. Two destroys again: one when the goal was met, one after a failed campaign is emptied.

    What this taught: @SignedBy works with any byte[] field, not only owner.

  5. Capacity. Each backer adds an entry to the datum. With maxDatumBytes = 1024, the harness test fills the campaign with 2 ADA contributions until the next one would not fit: 27 backers. Two choices keep this safe:

    • the minimum contribution (at least 2 ADA) makes filling the campaign expensive;
    • refunds, claims and closes only shrink the state, so they never fail on size. The test checks a refund at capacity (286.6M CPU, 559k memory, well within limits).

    A contract that needs many more entries should use a MerkleMap.

    What this taught: bound growth with maxDatumBytes, add an economic floor, and keep the shrinking paths open.

  6. Run it. The app runs a campaign that misses its goal:

    Ann’s two contributions were added under one key; after the deadline each backer got their own amount back, and the creator closed the empty campaign and took back the 6 ADA deposit.

Test them

Section titled “Test them”

Each example’s harness test evaluates the compiled validator for its paths and runs the attack suite on each accepted transaction. EscrowTest also checks the refusals: a release by the seller, and a refund by a stranger before the deadline (accepted after it). CrowdfundTest checks that contributions keep the map canonical, that a refund pays the caller, and the capacity case above. The …DevnetTest classes run the clients end to end when DevKit is up, and are skipped otherwise.

What you learned

Section titled “What you learned”
  • A contract can have several @Destroy methods, each with its own rules.
  • Ctx.caller with ByteStringLib.equals expresses “one of these parties”; @SignedBy("field") expresses “this one”.
  • Clock.after and Clock.before turn deadlines into rules that hold for the whole transaction.
  • A JulcMap in the state must stay in canonical key order: SortedMaps.
  • maxDatumBytes caps growth; design the shrinking paths so they always work.
