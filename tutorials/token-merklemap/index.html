Token balances in a MerkleMap

In this tutorial you run examples/token: a fungible token in the account model, where every holder’s balance sits in one MerkleMap. The datum stays about 100 bytes however many holders there are. You will run it twice: from Java against Yaci DevKit, then from a browser page that prepares its own transactions and reads balances from the map’s mirror in a Web Worker.

You need Yaci DevKit running: yaci-devkit up --enable-yaci-store (Yaci Store’s API on :8080, the admin API on :10000).

Experimental, pre-release

JOUST is experimental and pre-release (not for production). The Java part runs in a JOUST checkout with JDK 25; the page part needs Node 22 or newer and the npm packages. Both are covered in the steps below and in the quick starts (Java, npm).

The contract

Section titled “The contract”

Three things to notice:

  • balances is a MerkleMap, a direct component of the state, created with MerkleMaps.empty().
  • Every read and write goes through MerkleMaps. The methods never look at the map’s internals.
  • An emptied balance is removed, so close can require MerkleMaps.isEmpty(...) and never discard live balances.

Part 1: from Java

Section titled “Part 1: from Java”

  1. Check the example compiles. From a JOUST checkout, with JDK 25:

    The annotation processor generates TokenValidator (the on-chain script, compiled by JuLC) and TokenClient (the typed Java client) under examples/token/build/generated/. Because the state has a MerkleMap, every redeemer gains the map witnesses and the validator looks for the map verifier’s claims.

    What this taught: a MerkleMap field changes what is generated, not how you write the method.

  2. Run the tests.

    TokenTest runs each method the way the runtime does (reads from an in-memory mirror, then proofs), evaluates the compiled validator against the resulting transactions, runs the attack suite on each, and attacks the map witnesses directly: a forged read value, a read claimed absent, a missing or reordered write. Every one is rejected. The DevKit test, TokenDevnetTest, runs too when DevKit is up.

    What this taught: the same transfer runs on the JVM and on chain, and the proofs are what tie the two together.

  3. Run the app on DevKit.

    TokenApp deploys a token, mints 1,000 to Ann and 500 to Ben, and has Ann send Ben 250:

    It prints ann 750, ben 750, supply 1500. Look at the transfer in Yaci Viewer (http://localhost:5173, under the contract’s address): beside the token’s spend there is a zero withdrawal from the map verifier, whose redeemer carries the two reads and two writes. The first map call of a network also publishes the verifier’s reference script and registers its stake credential.

    What this taught: balanceOf is a @View, run on the JVM against the mirror with no transaction; the transfer carries its proofs to the shared verifier.

  4. Lose the mirror and carry on. The runtime keeps the map in RocksDB at ./.joust/mpf by default. A process that never saw this map rebuilds it from the chain. The DevKit test shows it with a fresh in-memory store:

    What this taught: the chain holds everything needed to rebuild a map; the mirror is a cache, checked against the root on chain.

Part 2: from a page

Section titled “Part 2: from a page”

Now the same contract in a browser. The page runs JOUST’s runtime engine (Wasm) in a Web Worker, which prepares each transaction; the page verifies it before the key signs. The worker also keeps the map’s mirror, in IndexedDB.

  1. Create a project. With Node 22 or newer:

    The web template in Java holds a Counter contract (Counter.java), a page and a test.

  2. Swap in the token. Delete contracts/app/Counter.java and test/counter.test.js. Copy examples/token/src/main/java/org/julclang/state/examples/token/Token.java to contracts/app/Token.java and change its first line to package app;.

    • Directorycontracts
      • Directoryapp
        • Token.java
    • Directorypage
      • index.html
      • main.js
      • engine.worker.js
    • joust.config.json
    • vite.config.js

    npm run build compiles it with the toolchain (no JDK) into build/joust/: the validator, the contract’s description and a typed client, Token.js.

    What this taught: the npm path compiles the same Java source, through JuLC in Wasm.

  3. Write the page. Replace page/index.html:

    And page/main.js. engine.worker.js stays as the template has it (import '@julclang/joust-runtime/worker';).

    Three calls do the map work:

    • token.at(id).state() decodes the datum. The map field is just { root, reads, writes }: the datum holds only the root.
    • service.mapValue(root, key, units) asks the worker’s mirror for one key under that root. units is the instance’s token (policy plus instance id): if the mirror has never seen the root, it rebuilds the map from that token’s chain history first.
    • mint and transfer look like any other call. The engine discovers the keys each method reads, asks the mirror for proofs, checks every proof against the on-chain root, and attaches the map verifier.

    What this taught: a page never needs the whole map; it asks for the keys it shows.

  4. Run it.

    joust dev builds, deploys the Token (and the map verifier) to DevKit, and serves the page at http://127.0.0.1:5178. Click Create a token (it tops up the in-page key first), Mint 1000 to me, then Send 250. The page shows Mine: 750 · Theirs: 250 · Supply: 1000.

  5. Reload, then try another browser profile. Reload the page: the balances come back without reading the chain’s history, because the worker kept the map in IndexedDB (database joust-mirrors).

    Now open the page in a private window, which starts with an empty IndexedDB and localStorage. In its console, run localStorage.setItem('joust.token', '<the instance id>') and reload. The worker has no copy of the map, so the first mapValue rebuilds it from the token’s chain history, checking every claim against its root, and the page shows Theirs: 250 · Supply: 1000. Mine is 0: the private window made itself a new key.

    What this taught: mirrors are caches. The chain is the source of truth, and a second device catches up from it without trusting anyone.

What you built

Section titled “What you built”
  • A token whose datum is constant-size, with each call proving only the balances it touches.
  • The same Java contract driven from a JVM app and from a browser page with no JDK.
  • Balances read from a mirror that survives reloads and rebuilds itself from the chain.

js/joust/test/page.test.js runs this flow in Chromium (its third test): a reload served from IndexedDB, a fresh profile rebuilding from history, and the page built as static files.
