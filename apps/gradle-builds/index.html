Gradle builds

A JOUST project on the JVM is an ordinary Gradle build. joust new writes one that applies the Gradle plugin org.julclang.joust, and the plugin does the JOUST setup. This page explains what the plugin adds, and how to write the same build by hand when you need to: an existing build, or a JOUST built from a checkout. For a first project, start with Quick start: Java & Gradle.

The build joust new writes

Section titled “The build joust new writes”

Plugins in the org.julclang groups (JOUST’s) come from the BloxBean release repository and from nowhere else. This block replaces Gradle’s default plugin repository: to use other plugins (foojay, Spotless and so on), add gradlePluginPortal() after exclusiveContent.

joust new fills in the version of the joust that runs it, on the plugin line (the comment above it records the version the project was created with). To upgrade JOUST, change the plugin line’s version to the newest release whose tag starts with v on the releases page (or npm view @julclang/joust version; each release publishes the npm packages at the same version). Every other version comes from the JOUST release the plugin belongs to, so the JuLC and cardano-client-lib versions always match. The build needs a Java 25 toolchain (the default; a lower one is refused with a message).

What the plugin adds

Section titled “What the plugin adds”

The plugin does what the hand-written build.gradle below spells out:

It adds At
julc-state-runtime, and cardano-client-backend-blockfrost for DevKit (joust { blockfrost = false } leaves it out) implementation
julc-state-processor, julc-annotation-processor, julc-state-api:<v>:onchain the annotation processor path
julc-state-testkit, junit-platform-launcher the tests
UTF-8 and -parameters; native access and in-memory map mirrors for tests; native access for run compile, test and run tasks
generateJsc, when src/main/jsc exists: .jsc contracts lowered to Java before compiling; with it acceptJscAbi, checkJscAbi (the ABI manifest) and remapJscDiagnostics (javac’s errors on the generated Java, at their .jsc positions) the build
joustHostSpec: what joust playground and editor plugins run to start the dev host build/joust/host-spec.json

You rarely run joustHostSpec yourself: joust playground runs it. The dev host explains what it records and how a tool starts the host from it.

In a Gradle build, joust build, joust test and joust run run ./gradlew build, test and run (a subproject’s directory selects the subproject); see the native joust.

Where JOUST comes from

Section titled “Where JOUST comes from”
  • BloxBean release repository
  • Your checkout, via mavenLocal

Every release is published to https://repo.bloxbean.org/maven/releases, with the JuLC it needs; that is the repository joust new configures. Recent releases are on Maven Central too. Use as <version> the newest release whose tag starts with v on the releases page (not the “Development snapshot” entry), without the v. The quickest check is npm view @julclang/joust version, since each release publishes the npm packages at the same version.

To try what is on main before it is released, publish the library modules of your checkout to ~/.m2:

This publishes julc-state-api (with its onchain jar), -processor, -runtime, -testkit, -verifier, -dsl, -serve, -host, -server, and the Gradle plugin org.julclang.joust. Without -Pversion, it publishes under the version in gradle.properties, which is usually a released version: the unreleased code in ~/.m2 would then shadow that release in every build that lists mavenLocal().

To use it, keep the plugin build and add mavenLocal() to both repository lists: in settings.gradle’s pluginManagement, inside forRepositories(...) (only the listed repositories may serve org.julclang), and in build.gradle’s repositories. Set the plugin line to the version you published. The build files below work too.

The build files by hand

Section titled “The build files by hand”
  • Directorymy-counter/
    • settings.gradle
    • gradle.properties
    • build.gradle
    • gradlew (with gradle/wrapper/: copy them from a project joust new wrote, or run gradle wrapper)
    • Directorysrc/
      • Directorymain/java/app/
        • Counter.java
        • Devnet.java
        • CounterMain.java
      • Directorytest/java/app/
        • CounterTest.java

julcVersion is JuLC’s processor, the one that compiles your validator, and cclVersion is cardano-client-lib’s. Take both from the release you chose: its gradle/libs.versions.toml (open it at the tag v<version>) names the julc and cardano-client-lib versions it was built and tested with. The Gradle plugin does this for you.

What each line on the annotation processor path is for:

Dependency Why it is there
julc-state-processor The JOUST processor: generates <Name>Validator, <Name>Client and the description
julc-annotation-processor JuLC’s processor: compiles the generated validator to UPLC in the next round
julc-state-api:<version>:onchain The julc-state-api sources, under META-INF/plutus-sources/. JuLC compiles against its own on-chain API plus library sources it finds on the processor path; without these it cannot see Ctx, Require, Payouts and the rest

This build is Java only and has no playground: it adds no generateJsc (so .jsc contracts are not compiled) and no joustHostSpec (which joust playground runs). Use the plugin for those.

The source files are the ones joust new writes; Quick start: Java & Gradle shows each of them.

Inside the JOUST build: a directory, not a jar

Modules inside the JOUST repository use the same bundle as a directory: annotationProcessor project(path: ':julc-state-api', configuration: 'onchainSources'), as in examples/counter/build.gradle. A jar that is rebuilt while a Gradle daemon is running can make JuLC’s source scan silently find nothing. A published jar does not change, so this rarely matters outside the repository; if a build suddenly reports that JuLC cannot resolve Ctx or Require, run ./gradlew --stop and build again.

Troubleshooting

Section titled “Troubleshooting”
Symptom Cause and fix
Could not find org.julclang:julc-... A repository is missing, or julcVersion is not the one your JOUST needs. Add the BloxBean release repository (and https://repo.bloxbean.org/maven/snapshots for a development snapshot) and use the julc entry of gradle/libs.versions.toml at your JOUST release’s tag
JuLC errors such as “cannot resolve” Ctx or Require The onchain bundle is missing from the annotation processor path, or a long-lived daemon holds a stale jar: check the dependency, then ./gradlew --stop
