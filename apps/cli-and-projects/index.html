The joust CLI and projects

Experimental

The npm path runs JOUST’s toolchain and runtime as WebAssembly built with GraalVM Web Image, which is itself experimental. Java with Gradle and cardano-client-lib is the supported, first-class path: see Quick start: Java.

@julclang/joust is the command line of a JOUST project. It compiles contracts with the toolchain engine (JOUST’s annotation processor and JuLC’s compiler, compiled to Wasm), publishes their reference scripts, and serves pages during development and after a build. It needs Node 22 or newer and nothing else: no JDK, no Gradle.

A project

Section titled “A project”

npm create joust <dir> makes one from its template. By default the contract is .jsc and a Node script calls it; -- --lang java writes it in Java, and -- --template web writes a page instead of the script (create-joust):

  • Directorycontracts/ your contracts: .java and .jsc files, in package folders
    • Directoryapp/
      • Counter.jsc
      • Counter.abi.json the .jsc contract’s ABI manifest, committed
  • index.js the Node script (node template)
  • Directorypage/ the page (web template): index.html, main.js, engine.worker.js
    • …
  • Directorytest/ Node tests (node –test)
    • …
  • Directorybuild/
    • Directoryjoust/ everything joust build and joust deploy write
      • …
  • Directorydist/ the built page (vite build)
    • …
  • Directory.joust/ local state: the DevKit deployer key
    • …
  • joust.config.json
  • vite.config.js the page’s Vite config (web template)
  • package.json

joust.config.json says where the contracts are, where the build goes, and which networks to use. The template’s:

Every key, with its default, is in the joust.config.json reference. The template’s .gitignore leaves out node_modules/, build/, .joust/ and dist/.

Keep .joust/ out of version control

.joust/devkit-wallet.json holds a mnemonic (written with mode 0600). It is a DevKit key, never to be used on a public network, but it is still a key.

joust build

Section titled “joust build”

Compiles every .java and .jsc file under contracts/ (or --src) into build/joust/ (or --out), with the toolchain engine, in-process. The .jsc language is JOUST’s contract language (.jsc). Plain JuLC validators (@WithdrawValidator, @SpendingValidator, …) in the same folder are compiled too, for use as governors. Diagnostics are printed as <file>:<line>: error: <message>, a .jsc diagnostic with its column and code (app/Counter.jsc:20:13: error[JSC0502]: <message>, as Gradle prints it); on an error the command exits with status 1 and writes no contract.

Each .jsc contract has an ABI manifest, <Contract>.abi.json, committed beside the .jsc file. The build fails when it is missing (JSC0003) or differs from what the contract now compiles to (JSC0002); --accept-abi writes it instead, to review and commit (the ABI manifest). The Java each .jsc file lowered to is written to build/joust/generated/, with its source map, also when the build failed (not for a file whose manifest was refused).

File in build/joust/ What it is
contracts.json for the runtime engine: [{ description, script, transitions, manifest, built: { joust } }], one per contract
<Contract>.json the contract’s description (CIP-57 schemas plus x-joust, version 2)
<Contract>.plutus the compiled validator, CBOR hex
<Contract>.js, <Contract>.d.ts the typed client and its types (JavaScript clients)
validators.json plain JuLC validators, if any: [{ name, package, purpose, script, scriptHash, params, built }]
<Validator>.plutus each plain validator’s script (parameters not applied)
joust.lock.json the toolchain version, the description version and each contract’s script hash
deployments.<network>.json written by joust deploy (below)

Each contract in contracts.json records the toolchain version that built it. The runtime refuses a description of another version than 2, and a contract built by an incompatible toolchain: another major version, or another minor while the major is 0. Rebuild with a matching @julclang/joust if you see built by JOUST ...; this runtime is ....

The toolchain compiles exactly as the Gradle build does: ADR-0015’s parity tests compare the outputs byte for byte. So a contract can move between the npm path and the Java path unchanged.

Program manifests

Section titled “Program manifests”

The runtime engine runs each contract method as its transition program: the same Java, compiled by JuLC, evaluated by JuLC’s VM. Each contract’s manifest in contracts.json records what its programs were compiled from and how: the JuLC version and compiler options, hashes of the validator script, the description (in canonical JSON, so a description given as an object matches too), every library source and each program, and each program’s argument layout (ADR-0020 D8). The engine checks it before it runs any program, and refuses a contract whose programs do not match their script, description or manifest, or were compiled by another JuLC version or with other options, with the transition programs do not match their manifest and the remedy: build the contracts again with the @julclang/joust that matches the runtime. The runtime checks a bundle’s manifests when it is created, and their JuLC version once the engine has loaded, before any call. A contracts.json from before manifests is refused the same way.

The manifest gives consistency, not integrity: whoever can change the programs can change the manifest too, and the validators still decide what the chain accepts. The engine cannot read the library sources, so their hashes are checked by JOUST’s CI (a fresh compile must equal the manifest), not at run time.

Caution

The engine accepts programs compiled by its own JuLC version only. A runtime with a newer JuLC refuses an older build until you run joust build again; if the newer JuLC compiles your validator differently, its script hash (and so its address and policy) changes, and live instances stay at the old one. How to upgrade deployed apps across JuLC versions is an open decision (ADR-0020 §12.4).

The engine also checks each program’s inputs (the state, the arguments, the Ctx) against the contract’s declared types before it runs it, and refuses a malformed one by name: Counter.increment: the argument by does not fit its declared type. A contract’s own refusal (Require.that) keeps its message, whatever it starts with.

joust deploy

Section titled “joust deploy”

For each contract in contracts.json, on the config’s network (or --network):

  1. Asks the runtime engine for the contract’s deployment: its policy (the script hash), address and reference scripts.
  2. If its reference script is not on chain yet, has the engine build the publishing transaction, checks that it pays only the contract’s address (with the script) and the deployer, signs and submits it.
  3. Publishes JOUST’s map verifier or output verifier once per network, when the contract needs one (MerkleMaps; sends, deposits).
  4. Writes build/joust/deployments.<network>.json.

This file is what apps and pages pin: a page built for a network inlines it. The deployer is:

  • JOUST_MNEMONIC, when it is set (required on any network without a DevKit admin API);
  • otherwise, on DevKit only, a key joust deploy makes and keeps in .joust/<network>-wallet.json, topped up with 1000 ADA from the faucet whenever it holds less than 200 ADA.

A contract with @Params is deployed with the values in the config’s params, under its full title or simple name; without them it is skipped, with a message. Each params value is its own deployment (Params, invariants and events):

Here Shop is examples/oracle’s, whose @Params record is Config(ForeignInstance oracle, BigInteger maxAgeMs). The values follow the description’s schema in the JSON conventions.

joust dev

Section titled “joust dev”

The development loop, on one port (default 5178, or the config’s dev.port):

  1. Attach to the network’s chain: probe the chain API (/blocks/latest) and, on a DevKit, its admin API. If it does not answer and the network has a start command, run it and wait up to three minutes.
  2. Build and deploy, then start a prepare service over the result.
  3. Serve: the page, the chain proxy, the build, the engine and the faucet (routes below).
  4. Watch contracts/: a saved .java or .jsc file rebuilds and redeploys (debounced; one run at a time, and a save during a run queues one more). A failed build waits for the next save. A .jsc file whose ABI manifest is missing or changed fails the build unless joust dev was started with --accept-abi; the server keeps serving the last good build meanwhile.
Route What it serves
/chain/<path> the network’s chain API, proxied (GET, and POST /chain/tx/submit); a project id stays in the server
/joust/network.json { network, networkId, chain: "/chain", engine, contracts, service, clock, ttlMs, explorer, deployments }
/joust/<file> the build: contracts.json, validators.json, deployments.<network>.json, the clients
/joust/engine/<file> the runtime engine, streamed with an ETag (a reload revalidates instead of downloading 20 MB)
POST /joust/service/prepare the engine in this process as a prepare service, for httpService('/joust/service'); a contract’s refusal answers 422 with { error }
POST /dev/topup { address, ada? } (default 1000 ADA) from DevKit’s faucet; DevKit only
anything else the page: through Vite when the project has vite and page/index.html, else the page directory’s files

The page directory is the config’s page, else page/ if it exists, else the project root. With Vite, the dev server uses the project’s vite.config.js (beside the page, or at the root), which should use @julclang/joust/vite; without one, it uses that plugin alone. Vite runs in middleware mode behind the dev server, with live reload over the same port, so two dev servers do not collide.

The deploys, the prepare service and the page’s /chain share one upstream session: Blockfrost’s load-balancer affinity cookie is kept, so the page verifies against the chain state the engine built from.

joust serve

Section titled “joust serve”

Serves a built page (vite build, default dist/) as a static host would, plus what a static page cannot carry itself: the chain API at /chain and, on DevKit, the faucet at /dev/topup. Nothing is built, deployed or bundled, and there is no engine route or prepare service: the page brings the engine, with its integrity hashes, and prepares its own transactions. It refuses to start without <dir>/index.html.

joust version

Section titled “joust version”

Prints the package’s version, the one recorded in contracts.json and joust.lock.json.
