Java runtime API

The public API of julc-state-runtime (package org.julclang.state.runtime) and julc-state-server (package org.julclang.state.server), from the sources in julc-state-runtime/src/main/java. For how to use them, see Java off-chain runtime.

Most applications use only the generated <Name>Client, StateRuntime, Compose, WalletAccount, PreparedTx and the exceptions. The rest is what generated clients, the testkit and the JavaScript engines are built on; it is public so that they can reach it, and it is marked internal below where you should not need it.

Caution

JOUST is pre-release. These signatures can change before the first release.

policyIdFor(P params) static With @Params only: the policy id of that parameter set

<action>(Account callerAccount, args... [, payLovelace] [, payAssets] [, Account... cosigners or Authorization authorization]) instance Runs an @Action or @Destroy; returns CallResult<S>

Contracts with owned objects also get, per owned type, a creation method returning a typed object wrapper (for example BankClient.open(Account, BigInteger) returning AccountObject with objectId(), value(), lovelace(), fullValue() and the owned actions), an accessor by id (account(String objectId)) and a <TYPE>_CODEC. Contracts with @Batched actions also get INTENTS (an IntentCodec<S>), <action>Intent(...) methods returning IntentHandle<S>, batch(Account, int), pendingIntents() and intent(String). Contracts with keyed types (ADR-0016) get, per keyed type T, <t>List(), <t>(byte[] key), <t>Exists(byte[] key), <t>Keys(), one insert method per @OwnedInit, a <T>Object wrapper and a <T>_TYPE constant: see Keyed objects.

Compose

Section titled “Compose”

public final class Compose: several calls in one atomic transaction (ADR-0011 D1).

Method Returns Description
static of(StateRuntime runtime, Account payer) Compose payer pays the fee
add(Runnable call) Compose Any client call: action, destroy, deploy, owned call
allowSharedSigners() Compose Lets one key’s signature count for several calls (refused by default)

Inside another composition, submit()/prepare() join the outer transaction (prepare() cannot be nested).

Exceptions

Section titled “Exceptions”
Class Extends Thrown when
org.julclang.state.api.RequireException RuntimeException A contract rule failed on the JVM; nothing was submitted
JoustException RuntimeException Base class of the runtime’s failures
SubmitException JoustException The builder failed or the node rejected the transaction; nothing was accepted
ContentionException JoustException The state kept moving; gave up after maxRetries. For a keyed operation, attempts() and designatedInput() name what was tried
PendingTransactionException JoustException Submitted but not seen on chain in time, or the node’s answer was not a definite rejection (see below); txHash() gives the hash. Do not resubmit blindly. For a keyed operation, attempts() lists every attempt handed out and designatedInput() the input they all spend
InstanceNotFoundException JoustException No UTxO holds the instance’s thread token

A submission’s answer decides between SubmitException and PendingTransactionException. Only a definite answer is a rejection: an HTTP 4xx with a body (other than 408, 425 and 429). A 5xx, an answer without a status, a timeout, an empty body or a network error may hide an accepted transaction, so it is pending, with its inputs still claimed. A backend that reports the node’s rejection that way (CCL’s Ogmios 5 service answers a 500, its GraphQL service no status) therefore turns a lost race into a pending outcome: such a call is not retried, and its inputs stay claimed until its window ends. Prefer a backend that answers a rejection with a 4xx (Blockfrost, Yaci Store).
