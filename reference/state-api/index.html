State API (julc-state-api)

julc-state-api (package org.julclang.state.api) is the library your contract code calls. Every class here runs in two places: on the JVM, when the generated client runs your method to compute the next state, and on chain, compiled by JuLC into the validator. Both must give the same answer on the same inputs, so the API is written in the JuLC subset of Java and a few classes ship a separate on-chain body (see On-chain variants).

This page covers the records and helper classes. The annotations have their own page: Annotations. Sources: julc-state-api/src/main/java/org/julclang/state/api/.

Types such as JulcList, JulcMap and PlutusData come from JuLC (org.julclang.core), and Value, Address, Credential, OutputDatum, TxOutRef, TxCert and DRep from JuLC’s ledger types (org.julclang.ledger).

Ctx

Section titled “Ctx”

Transaction facts an @Init, @Action or @Destroy method (and owned methods) may read. Declare it as the method’s last parameter, or the last before Funds. The client supplies it; the generated validator verifies every field against the transaction before calling your method (ADR-0001 D3).

Component Meaning
caller Key hash of the party calling. The transaction is signed by it. In a @Batched run, the intent’s owner
received Lovelace this call adds to the contract. Zero unless the method is @Payable
balance Funds the call may allocate. In actions: the contract’s lovelace before the call minus the min-ADA deposit. In destroys: everything the state UTxO holds, deposit included. Zero in @Init
validFrom Start of the transaction’s validity interval (POSIX ms, inclusive)
validTo End of the validity interval (POSIX ms, exclusive)

The validator checks that validFrom and validTo equal the transaction’s finite bounds, and that validTo - validFrom is at most @StateContract(maxValidityMs) (default one hour). For deadlines prefer Clock. A method without Ctx needs no signature and costs less.

Source: Ctx.java. Guide: Ctx, funds and payouts.

Require and RequireException

Section titled “Require and RequireException”

Require.that(cond, "message") fails the call when cond is false. On the JVM it throws RequireException with the message, so the client reports why a call was rejected before submitting anything. On chain (the bundled source in src/onchain/java) it traces the message and fails the script. Both fail on exactly the same inputs (ADR-0001 D7). A third variant, src/discovery/java, is compiled only into the transition programs the runtime engine runs: it traces joust:require <message> before failing, so the engine tells the contract’s refusal from any other failure by that tag (ADR-0020). Validators never use it.

Thrown only on the JVM. Contract code never constructs it (JuLC has no throw): use Require.that.

Sources: Require.java, on-chain Require.java, RequireException.java. Guide: Require and errors.

Clock

Section titled “Clock”

Deadline checks against the transaction’s validity interval [ctx.validFrom(), ctx.validTo()). They hold for every moment the transaction could be valid, which makes them the safe way to use time.

Method Returns True when
static boolean after(Ctx ctx, BigInteger t) boolean ctx.validFrom() >= t: the call happens at or after t
static boolean before(Ctx ctx, BigInteger t) boolean ctx.validTo() <= t: the call happens strictly before t

Caution

Clock.before needs the whole validity window to end before the deadline. On Yaci DevKit, whose time horizon is minutes, keep the transaction’s TTL short (the DevKit runtime uses 20 s).

Source: Clock.java. Guide: Time.

Payout and Payouts

Section titled “Payout and Payouts”

Lovelace the contract pays to a public-key payment credential: to is the recipient’s payment key hash, lovelace is greater than zero. The validator tags payouts against double satisfaction.

Payouts builds the payout list an action or destroy returns:

Method Returns Meaning
static JulcList<Payout> none() JulcList<Payout> No payouts
static JulcList<Payout> of(byte[] to, BigInteger lovelace) JulcList<Payout> One payout
static JulcList<Payout> add(JulcList<Payout> payouts, byte[] to, BigInteger lovelace) JulcList<Payout> Prepends one payout
static BigInteger total(JulcList<Payout> payouts) BigInteger Sum of the payouts’ lovelace

Note

The Java runtime pays a payout to the key’s enterprise address unless you map the key to another address with StateRuntime.Builder.address(pkh, bech32). Never map it to the fee payer’s address: CCL’s QuickTx takes the fee from an output there.

Sources: Payout.java, Payouts.java.

Funds

Section titled “Funds”

Native assets seen by a method of an asset-aware contract (ADR-0007 D1). Declare it as the last parameter, after Ctx if there is one. The client supplies it; the generated validator checks every field.

Component Meaning
policy This contract’s policy id (its script hash): name your own tokens with it
self The token name of what the method acts on: the instance id, or the object id for owned methods
received Native assets the caller adds in this call. No lovelace entry (that is Ctx.received), positive amounts only, empty unless the method is @Payable
held Native assets the UTxO holds before the call, without lovelace and without its own thread token. Empty when creating
deposits Deposits from other contracts into this call’s continuing output, in registry order. Filled only for a @Receives action

A @Payable method with Funds must return a result record with accepted: exactly the native assets it takes.

Source: Funds.java. Guide: Native assets, mints and sends.

Send and Sends

Section titled “Send and Sends”

An output a method sends from the UTxO it acts on (ADR-0007 D5): to any address, key or script, with any datum. The generated validator requires an output at to with exactly datum, no reference script and at least value, claimed for this call in the shared output registry so no other obligation can count it. For lovelace to a key, Payout is cheaper.

Sends method Returns Meaning
static JulcList<Send> none() JulcList<Send> No sends
static JulcList<Send> of(Address to, Value value, OutputDatum datum) JulcList<Send> One send
static JulcList<Send> add(JulcList<Send> sends, Address to, Value value, OutputDatum datum) JulcList<Send> Prepends one send

Sources: Send.java, Sends.java.

Datum

Section titled “Datum”

Output datums for sends, the same on the JVM and on chain.

Method Returns
static OutputDatum inline(PlutusData d) An inline datum
static OutputDatum none() No datum

Caution

A record cannot be passed as data in shared code: (PlutusData) (Object) record works on chain but throws on the JVM. Build the datum with Builtins.constrData, bData, iData and mkCons, which run on both. A record R(a, b) is constrData(0, mkCons(a, mkCons(b, mkNilData()))).

Source: Datum.java.

Assets

Section titled “Assets”

Multi-asset values for contract code (ADR-0007), with the same results on the JVM and on chain. Every value these functions return is canonical, as the ledger writes values: policies and token names in ascending byte order, no zero quantities, no empty token maps. Lovelace is the entry with the empty policy and the empty token name.

Method Returns Meaning
static Value none() Value The empty value
static Value of(byte[] policy, byte[] name, BigInteger quantity) Value quantity of (policy, name); empty if the quantity is zero
static Value lovelace(BigInteger quantity) Value quantity lovelace
static Value add(Value a, Value b) Value Entry-wise sum; zero sums vanish
static Value subtract(Value a, Value b) Value Entry-wise a - b; zero differences vanish, negative ones stay
static BigInteger quantity(Value v, byte[] policy, byte[] name) BigInteger Quantity of (policy, name), zero if absent
static BigInteger lovelaceOf(Value v) BigInteger The lovelace in v
static Value withoutLovelace(Value v) Value v without its lovelace
static boolean isEmpty(Value v) boolean True if v holds nothing
static boolean covers(Value a, Value b) boolean True if a holds at least b of every entry. Both must be non-negative: on chain a negative quantity fails the script, on the JVM it throws
static void check(Value v, String what) void JVM only. Throws unless v is canonical (sorted, no zero quantities, no empty token maps, keys at most 32 bytes). The runtime and the harness run it on every value a method returns
static TreeMap<String, TreeMap<String, BigInteger>> read(Value v) TreeMap JVM only. Entries by policy and token name, as lower-case hex, in ledger order

On chain the functions use the PV11 native Value builtins (CIP-153), which reject a non-canonical argument; ledger values and the results of these functions always are canonical. The JVM body normalises instead, and check makes sure a JVM test never passes on a value the chain would reject.

Caution

A native Value cannot be a JuLC loop accumulator (use recursion). A redeemer field typed Value mis-decodes in JuLC: use PlutusData there.

Sources: Assets.java, on-chain Assets.java. Guide: Native assets, mints and sends.

Deposit, Deposits and DepositClaim

Section titled “Deposit, Deposits and DepositClaim”

Deposits are payments from one JOUST contract’s call into another instance’s continuing output in the same transaction (ADR-0011 D3).

value goes into the continuing output of instance instance of contract policy, which must be spent in the same transaction by an action that @Receives deposits. memo is any data the receiver may read (a beneficiary, an order id). A method returns its deposits in a deposits result component.

Deposits method Returns Meaning
static JulcList<Deposit> none() JulcList<Deposit> No deposits
static JulcList<Deposit> of(ForeignInstance target, Value value, PlutusData memo) JulcList<Deposit> One deposit into target
static JulcList<Deposit> add(JulcList<Deposit> deposits, ForeignInstance target, Value value, PlutusData memo) JulcList<Deposit> Prepends one deposit
static BigInteger lovelace(JulcList<DepositClaim> deposits) BigInteger The lovelace of every deposit a receiver got (funds.deposits())

A deposit in the shared output registry: output output receives value from the input by, with memo. The output verifier checks the value is canonical and positive, free of reserved tokens, and that by is an input. The depositor checks its own claims; the receiver counts every claim on its continuing output exactly once.

Sources: Deposit.java, Deposits.java, DepositClaim.java. Guide: Deposits.

ForeignInstance

Section titled “ForeignInstance”

Another JOUST contract’s instance (ADR-0011 D2): its applied script hash (policy) and its 32-byte instance id. Held only in a @Params record, so the script it trusts is fixed at deploy. @Reads("params.x") and Deposits.of take it.

Source: ForeignInstance.java. Guide: Reads and composition.

Approvals and Approval

Section titled “Approvals and Approval”

Approvals is the Rewarding redeemer a Plutus governor script uses to approve JOUST actions for @AuthorizedBy with a script credential (ADR-0009 r2). Each Approval says the JOUST contract policy may run its action with redeemer tag action on target (an instance or object id). The governor’s own rules decide which approvals it lists; each JOUST validator accepts only the one naming itself, its target and its action.

Sources: Approval.java, Approvals.java. Guide: Authorization.

Certs

Section titled “Certs”

Exact certificate checks for @Certify handlers (ADR-0010 r2), the same on the JVM and on chain.

Method True when
static boolean isRegistration(TxCert cert) A stake registration (with or without a deposit)
static boolean delegatesOnlyTo(TxCert cert, byte[] pool) A stake delegation (alone or with registration) to exactly pool, and only stake: no vote delegation
static boolean delegatesVoteTo(TxCert cert, DRep drep) A vote delegation (alone or with registration) to exactly drep, and only votes
static boolean isDRepLifecycle(TxCert cert) DRep registration or update of the contract’s own credential
static boolean sameDRep(DRep a, DRep b) DRep equality that also holds on the JVM
static boolean sameCredential(Credential a, Credential b) Credential equality that also holds on the JVM

Records with byte arrays do not compare by value on the JVM, which is why sameDRep and sameCredential exist.

Source: Certs.java. Guide: Staking and governance.

MerkleMap and MapEntry

Section titled “MerkleMap and MapEntry”

A MerkleMap is a map stored as a Merkle Patricia Forestry root (ADR-0002). Use it as a component of the state record (or of an owned record) to hold an unbounded map: the datum keeps only the 32-byte root, and each call proves the keys it touches. reads and writes exist only while a contract method runs: the proven entries this call may read, and this call’s writes, latest first. In the datum both are empty.

A MapEntry is one key: present with a value, or absent (with an empty value).

Caution

Use MerkleMap and MapEntry only as top-level components of the state or owned record. Never construct them, never pass them as arguments, and never read .reads(), .writes() or .root() in contract code: go through MerkleMaps.

Sources: MerkleMap.java, MapEntry.java.

MerkleMaps

Section titled “MerkleMaps”

Reading and changing a MerkleMap (ADR-0002 D2). A lookup sees this call’s writes (latest first), then its read set. Writes add to the map’s pending writes; the root never changes inside a method. The verifier (a shared withdraw-zero script) proves the reads and computes the new root.

Method Returns Meaning
static MerkleMap empty() MerkleMap A new, empty map (for @Init and @OwnedInit)
static boolean isEmpty(MerkleMap m) boolean The map was empty before this call and this call wrote nothing. Check it before destroying
static boolean contains(MerkleMap m, byte[] key) boolean The key is present
static byte[] get(MerkleMap m, byte[] key, byte[] otherwise) byte[] The value, or otherwise
static BigInteger getInt(MerkleMap m, byte[] key, BigInteger otherwise) BigInteger The value as an unsigned big-endian integer, or otherwise
static MerkleMap put(MerkleMap m, byte[] key, byte[] value) MerkleMap Sets key to value
static MerkleMap putInt(MerkleMap m, byte[] key, BigInteger value) MerkleMap Stores a non-negative integer as its minimal big-endian bytes (zero is the empty byte string). Fails on a negative value
static MerkleMap remove(MerkleMap m, byte[] key) MerkleMap Removes key
static MapEntry lookup(MerkleMap m, byte[] key) MapEntry This call’s latest write for key, else the read set
static JulcList<MapEntry> netWrites(MerkleMap m) JulcList<MapEntry> The latest write of each key (used by generated code)

Methods are pure: always use the returned map.

A key outside the read set behaves differently on each side, which is the only difference between the sources:

Where Source What happens
JVM src/main/java Read from the ReadSource the runtime (or the test harness) binds, and recorded so it joins the read set
On chain src/onchain/java Fails the script (ADR-0002 D3)
Transition programs src/discovery/java Answered as absent and named in a joust:read <root hex> <key hex> trace, so the engine can prove every read and run again (ADR-0015 D3)

The empty root holds no key, so lookups on an empty map need no proof (this lets @Init read the maps it creates). The JVM source also has runtime hooks you do not call from contract code: the ReadSource interface (MapEntry read(byte[] root, byte[] key)), static <T> T withReads(ReadSource source, Supplier<T> body), and static MapEntry read(byte[] root, byte[] key).

Sources: MerkleMaps.java, on-chain, discovery. Guide: MerkleMaps. Tutorial: Token balances in a MerkleMap.

SortedMaps

Section titled “SortedMaps”

Maps with byte[] keys kept in canonical CBOR key order (shorter key first, then byte-wise), on the JVM and on chain alike. Use them for JulcMap fields of the state.

Method Returns Meaning
static boolean before(byte[] a, byte[] b) boolean a sorts before b in canonical CBOR order
static JulcMap<byte[], BigInteger> put(JulcMap<byte[], BigInteger> m, byte[] k, BigInteger v) JulcMap m with k set to v, keeping canonical order
static JulcMap<byte[], BigInteger> remove(JulcMap<byte[], BigInteger> m, byte[] k) JulcMap m without k (order is kept)
static BigInteger getOr(JulcMap<byte[], BigInteger> m, byte[] k, BigInteger otherwise) BigInteger The value for k, or otherwise

Why: a JulcMap is an ordered association list and insert prepends, but cardano-client-lib writes inline datums in canonical CBOR, which sorts map keys. A state map not already in canonical order would be written differently from what the validator recomputes, and the call would fail on chain. The runtime refuses to submit such a state.

Source: SortedMaps.java. Tutorial: Escrow and crowdfunding.

OutputClaim and OutputClaims

Section titled “OutputClaim and OutputClaims”

The shared output-claim registry (ADR-0007 D5). An OutputClaim says output output of the transaction is a Send of the transition whose UTxO is by. OutputClaims is the redeemer of the JOUST output verifier: every send claim, by strictly increasing output index (no output is claimed twice), and every deposit claim, by non-decreasing output index (an output may receive several deposits). The runtime builds it; contract code does not.

Sources: OutputClaim.java, OutputClaims.java.

The mpf package

Section titled “The mpf package”

org.julclang.state.api.mpf holds the Merkle Patricia Forestry code behind MerkleMaps. Generated validators, the shared map verifier and the runtime use it; contract code uses MerkleMaps instead.

Mpf

Section titled “Mpf”

Roots and updates compatible with Aiken’s aiken-lang/merkle-patricia-forestry and cardano-client-lib’s MpfTrie (blake2b-256, radix 16, keys and values hashed). A port of CCL’s WireProof in the JuLC subset: it runs on chain and on the JVM alike. Proofs are in the form MpfTrie.getProofPlutusData returns.

Method Returns Meaning
static byte[] emptyRoot() byte[] The empty trie’s root: 32 zero bytes
static boolean has(byte[] root, byte[] key, byte[] value, JulcList<ProofStep> proof) boolean key -> value is in the trie
static boolean miss(byte[] root, byte[] key, JulcList<ProofStep> proof) boolean key is absent
static byte[] insert(byte[] root, byte[] key, byte[] value, JulcList<ProofStep> proof) byte[] Root after inserting an absent key; fails if the proof does not show it absent
static byte[] delete(byte[] root, byte[] key, byte[] value, JulcList<ProofStep> proof) byte[] Root after deleting key -> value; fails if not present with that value
static byte[] update(byte[] root, byte[] key, JulcList<ProofStep> proof, byte[] oldValue, byte[] newValue) byte[] Root after changing key from oldValue to newValue
static byte[] including(byte[] key, byte[] value, JulcList<ProofStep> proof) byte[] Root of a trie holding key -> value at the position the proof describes
static byte[] excluding(byte[] key, JulcList<ProofStep> proof) byte[] Root of the trie the proof describes, without key

Proof and claim records

Section titled “Proof and claim records”
Type Definition Meaning
ProofStep sealed interface ProofStep permits Branch, Fork, Leaf One proof step, in Aiken’s Plutus encoding
ProofStep.Branch record Branch(BigInteger skip, byte[] neighbors) A branch node: the neighbour hashes along the path (4 x 32 bytes)
ProofStep.Fork record Fork(BigInteger skip, Neighbor neighbor) A branch with exactly one other child
ProofStep.Leaf record Leaf(BigInteger skip, byte[] key, byte[] value) A branch whose one other child is a leaf: its key hash and value hash

MapClaim record MapClaim(byte[] policy, TxOutRef owner, BigInteger field, byte[] oldRoot, JulcList<ReadProof> reads, JulcList<WriteProof> writes, byte[] newRoot) What the verifier proves for one map of one instance; found by (policy, owner, field) (ADR-0014)
MapClaims record MapClaims(JulcList<MapClaim> claims) The map verifier’s redeemer: every claim of the transaction

MapWitnesses

Section titled “MapWitnesses”

MerkleMap checks, split between the generic map verifier (a withdraw-zero script that does the MPF work) and each contract’s validator (which only matches claims to its own maps). ADR-0002 D3 and D9.

Method Side Meaning
static boolean verify(MapClaim c) verifier The claim’s reads are proven against its old root, and its writes, applied in order, turn the old root into the new root
static MapClaim claimFor(MapClaims claims, byte[] policy, TxOutRef owner, long field) contract The claim for map field of the instance whose state input (or seed) is owner; fails if none
static MerkleMap open(byte[] root, MapClaim c) contract The map a method sees: the claim’s verified reads over root, which must be the claim’s old root
static byte[] commit(byte[] root, MerkleMap after, MapClaim c) contract The new root, once the claim’s writes are exactly the method’s net writes in order

Sources: mpf/. The verifier itself is the julc-state-verifier module.

On-chain variants

Section titled “On-chain variants”

A few classes need a different body on chain. Their on-chain sources live in src/onchain/java and replace the JVM source in the bundle JuLC compiles; ADR-0001 D7 keeps that set tiny.

Class JVM body (src/main/java) On-chain body (src/onchain/java)
Require Throws RequireException(message) ContextsLib.trace(message), then Builtins.error(); transition programs (src/discovery/java): ContextsLib.trace("joust:require " + message), then Builtins.error()
Assets TreeMap arithmetic that normalises; adds check and read PV11 native Value builtins (insertCoin, unionValue, scaleValue, lookupCoin, …)
MerkleMaps Reads missing keys from the bound ReadSource A missing key fails the script

src/discovery/java holds a third MerkleMaps, compiled only into transition programs (ADR-0015 D3), never into validators.

The build’s bundleOnchainSources task writes the JuLC library sources (META-INF/plutus-sources/) with these overrides in place. A consumer puts them on its annotation processor path: inside the JOUST build as project(path: ':julc-state-api', configuration: 'onchainSources') (a directory), and from the snapshot repository as org.julclang:julc-state-api:<version>:onchain.

Caution

Shared code (contracts and this API) must never compare byte[] with == or .equals: on chain that compares bytes, on the JVM it compares references. Use ByteStringLib.equals.
