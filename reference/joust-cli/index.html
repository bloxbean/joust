@julclang/joust (CLI, Vite)

Experimental

The npm path runs JOUST’s toolchain and runtime as WebAssembly built with GraalVM Web Image, which is itself experimental. Java with Gradle and cardano-client-lib is the supported, first-class path: see Quick start: Java.

@julclang/joust is JOUST’s command line and Vite plugin. It carries the toolchain engine: JOUST’s annotation processor and JuLC’s compiler, compiled to Wasm, which build .java and .jsc contracts in Node exactly as the Gradle build does. Source: js/joust. For a guided tour, see The joust CLI and projects. It needs Node 22 or newer.

Entry point Contents
bin joust the CLI
@julclang/joust build, deploy, loadConfig, network, loadToolchain, VERSION (the commands as functions)
@julclang/joust/vite the Vite plugin, joust(options) (also the default export)

Commands

Section titled “Commands”

Every command reads joust.config.json from the working directory (see joust.config.json). --network <name> defaults to the config’s network (devkit).

Command Flags What it does
joust build --src <dir> (default config contracts), --out <dir> (default config out), --accept-abi, --accept-lock, --traces compiles every .java and .jsc file under the source folder into the output folder, with the libraries of the project’s npm packages (joust-lib/); exits 1 on a compile error, on a .jsc ABI manifest that is missing or changed unless --accept-abi writes it (the ABI manifest), or on a library from a package that joust.lock does not pin at its hash unless --accept-lock writes it (library packages). --traces keeps the contracts’ traces in the scripts (larger scripts; for debugging)
joust fmt [--check], [<file or dir>...] (default: the configured contracts directory, only inside the project) formats .jsc files in place, changing only whitespace (style version 1: editors). A file that does not parse, is not valid UTF-8, or is read-only is refused and left as it was; a formatted file keeps its permissions. --check writes nothing and lists the files that are not formatted. Exits 0 formatted (with --check: already was), 1 not formatted (--check), 2 a file refused, 3 a usage error. Gradle projects use JscMain --fmt [--check], with the same codes
joust test [-- <node --test args>] builds, then runs test/*.test.js with Node’s test runner (one file at a time). Tests that use @julclang/joust/test run offline: see offline tests
joust deploy --network <name> publishes each contract’s reference script (once) and writes <out>/deployments.<network>.json
joust dev --network <name>, --port <port> (default config dev.port, else 5178), --accept-abi attaches to the chain (starting it with the network’s start command if needed), builds, deploys, serves the page; rebuilds and redeploys on save
joust serve --network <name>, --dir <dir> (default dist), --port <port> (default as dev) serves a built page as static files, with the chain API at /chain and on DevKit the faucet
joust version (also joust --version, -V, -v) prints joust <version> (npm)
joust help (also --help, -h, <command> --help) the usage; never runs a command
joust playground --mode offline|devkit (default offline), --network <name> (with --mode devkit), --port <port>, --accept-abi, --accept-lock, --no-open builds, then opens a browser playground for every contract: test identities, a form per call, an offline ledger or Yaci DevKit. In a Gradle project it runs ./gradlew build joustHostSpec and the JVM dev host. See The playground
joust new prints the npm create joust command to run (Gradle projects come from the native joust); creates nothing

In a project, a project command (build, test, deploy, dev, serve, playground) runs at the project’s root (the nearest directory with joust.config.json, or a package.json that depends on @julclang/joust), and by the project’s own @julclang/joust: a global or other copy hands over to it, as the native joust does.

joust with no command prints the usage; an unknown command prints it and exits 1. Errors are printed as joust: <message> with exit status 1. joust dev and joust serve bind to 127.0.0.1 and stop on SIGINT or SIGTERM.

Offline tests

Section titled “Offline tests”

@julclang/joust/test runs a project’s contracts without a chain:

net.ledger is an in-memory ledger behind the same provider interface as Yaci Store or Blockfrost. Before it applies a transaction it checks these phase-1 rules (each refusal names the node’s error):

  • the transaction is tagged valid, is at most max_tx_size bytes, and its inputs, reference inputs and collateral exist and are unspent; at protocol versions 9 and 10 an output is not both spent and referenced (the ledger lifts that at 11);
  • the validity interval holds at the ledger’s slot (ledger.advance(ms) moves its clock);
  • withdrawals come from registered reward accounts and take exactly their balance (always 0: no rewards are paid);
  • the transaction balances, with the fee and the deposits, and every output holds its minimum ADA, the collateral return included;
  • the fee is at least the size’s, the declared execution units’ and the reference scripts’ fee;
  • every key that must sign has a verifying witness, every script credential that must authorise (a script-locked input, a mint policy, a script withdrawal or certificate) has its script, witnessed or referenced; native scripts are evaluated; each Plutus purpose has a redeemer and no redeemer is extra; a Plutus-locked input’s datum hash has its datum (a key-locked output with a datum hash needs none), and a witness datum is either needed or named by an output (the collateral return included) or a reference input;
  • certificates: a stake registration (once, paying key_deposit) and a deregistration (when registered, refunding the deposit held); a certificate that states another amount is refused;
  • with Plutus scripts: the collateral is key-locked, at most max_collateral_inputs, ADA only unless returned, at least collateral_percent of the fee, and matches total_collateral when it is declared; the script integrity hash matches; the declared units are within the per-transaction limit;
  • phase 2: every Plutus script that must run, evaluated by the runtime engine (joust.evaluate, the evaluator that prices transactions), within its redeemer’s declared units.

Concurrent submissions are applied one at a time. A transaction carrying what the ledger does not model is refused (NotModelled): votes, proposals, treasury donations and values, and every certificate but stake registration and deregistration (delegation to a pool or a DRep, DRep, committee and pool certificates); test those on DevKit. Not modelled otherwise: rewards (withdrawals take 0), PlutusV1’s integrity hash, and the collateral loss of a failing script (an invalid-tagged transaction is refused; a failing script refuses the whole transaction).

A refusal is a LedgerRefusal. For each transaction a script ran in, the ledger also runs the attack suite (joust.attacks, a subset of the JVM testkit’s Attacks) on it: the state datum replaced or hashed, one lovelace skimmed, token dust added, the output sent to a key address or given a stake credential, the output dropped, the required signer replaced, the validity bounds moved or removed. Only a script’s refusal counts as refused; any other failure of a mutation is reported as accepted, with its reason, so that it fails the test. ledger.attacks() lists every attack with its outcome; ledger.acceptedAttacks() lists those the scripts accepted, which should be none. Pass { attacks: false } to offline to skip the suite. joust test runs offline: a network provider (Blockfrost, Yaci Store, Ogmios) refuses to start under it.

The template’s test/counter.test.js is such a test: npm test runs joust test. Its DevKit test is in test/devkit/.

joust deploy

Section titled “joust deploy”

<out>/deployments.<network>.json is { network, networkId, chain, clock, contracts: { <title>: deployment } }, each deployment { contract, policy, address, networkId, referenceScripts } plus params, mapVerifier and outputVerifier when the contract has them. The deployer is JOUST_MNEMONIC’s key; without it, on a network with an admin API (DevKit), a key kept in .joust/<network>-wallet.json, topped up with 1000 ADA when it holds less than 200 ADA. A contract with @Params is deployed with the config’s params for it (by title or simple name) and skipped without them.

Environment variables

Section titled “Environment variables”
Variable Read by Meaning
JOUST_MNEMONIC joust deploy, joust dev the deployer’s mnemonic; required on networks without an admin API
BLOCKFROST_PREVIEW_PROJECT_ID any command on preview the Blockfrost project id (the built-in preview’s projectIdEnv)
(a network’s projectIdEnv) any command on that network its chain API’s project id
JOUST_NETWORK the Vite plugin, in vite build the network a build is for, unless the plugin’s network option names one
JOUST_VITE_LOG joust dev Vite’s log level (default warn); info shows dependency bundling and reloads

A command on a network whose projectIdEnv is not set stops and names the variable.

The dev server

Section titled “The dev server”

joust dev serves one origin (default http://127.0.0.1:5178):

Route Method Answers
/chain/<path> GET, POST (/chain/tx/submit) the network’s chain API, proxied with its project id; one upstream session (Blockfrost’s affinity cookie)
/joust/network.json GET { network, networkId, chain: "/chain", engine: { url, integrity: { script, wasm } }, contracts: "/joust/contracts.json", service: "/joust/service", clock, ttlMs, explorer, deployments }
/joust/engine/<file> GET the runtime engine (joust-runtime.js, joust-runtime.js.wasm), streamed, with an ETag
/joust/service/prepare POST the engine in the dev server as a prepare service (httpService('/joust/service')); 422 { error } on a contract’s refusal
/joust/<file> GET files of the build folder
/dev/topup POST { address, ada? } DevKit only: funds the address from the faucet (default 1000 ADA)
anything else the page: Vite in middleware mode when the project has vite and an index.html in the page folder, else the page folder’s files

Responses carry access-control-allow-origin: *. The page folder is the config’s page, else page/ if it exists, else the project root.

joust serve answers /chain/<path>, /dev/topup (DevKit only) and the files of its folder (/ is index.html). It has no /joust routes.

The Vite plugin

Section titled “The Vite plugin”
Option Default Meaning
root the working directory the project: where joust.config.json and the build folder are
network JOUST_NETWORK, else Vite’s mode if it names a network, else the config’s network the network a vite build is for

It returns a list of plugins that:

  • alias Node’s buffer, events, util, stream, process and assert to browser versions, resolved from the plugin’s own package by absolute path, and inject the Buffer (one class, src/shims/buffer.js) and process globals;
  • set global to globalThis and target es2022 for the dev server’s dependency bundling and for builds;
  • build workers as ES modules with the same aliases and globals (injected post in workers);
  • scan **/*.html and **/*.worker.{js,mjs,ts} for dependencies (unless the config sets optimizeDeps.entries), and pre-bundle node:buffer;
  • allow the project root in server.fs.allow, so a page imports build/joust/*.js;
  • provide virtual:joust/network.

vite-plugin-node-polyfills and @rollup/plugin-inject are dependencies of the package; vite (5 or newer) is an optional peer dependency.

virtual:joust/network

Section titled “virtual:joust/network”

The default export, in a build:

Field Value
network the network’s name
networkId the network’s networkId, else the deployments file’s
chain the network’s pageChain, else "/chain"
clock the deployments file’s clock, else the network’s
ttlMs the config’s dev.ttlMs, else 20 000 on a DevKit, 180 000 elsewhere
explorer the network’s explorer, or null
deployments the deployments file’s contracts
contracts contracts.json
validators validators.json, or []
engine { url: "<base>joust/engine-<id>/joust-runtime.js", integrity: { script, wasm } }

A build emits the engine’s two files to joust/engine-<id>/ (id: 8 hex characters from the files’ hashes) and fails without contracts.json or deployments.<network>.json. Under joust dev, the module instead fetches /joust/network.json and then its contracts when the page loads (the fields of the dev server’s network.json, above).

The native joust

Section titled “The native joust”

The native joust needs no Node and no JDK to run: brew install bloxbean/tap/joust, or the release archives (macOS arm64, Linux x86_64 and arm64). It creates projects and hands project commands to the project:

Command Native joust
joust new <dir> [-t gradle|node|web] [-l java|jsc] [-p <package>] gradle (default, java by default): a Gradle project with the plugin org.julclang.joust; node, web: what npm create joust writes, fetched with npm pack create-joust@<its version> and run by its own node, isolated from the directory’s npm configuration
joust version joust <version> (native), and in an npm project project: @julclang/joust <version> (npm)
joust help, <command> --help the usage; never runs a command
any other command, in an npm project the project’s own @julclang/joust (node_modules), at the project’s root, with the arguments unchanged and its exit code; run npm install first if it is missing, never a stand-in
joust build, test, run, in a Gradle build the build’s ./gradlew <task> (a subproject’s directory selects the subproject); deploy, dev and serve explain that they are npm commands
joust playground, in a Gradle build the @julclang/joust of this joust’s own version, installed once into ~/.joust/playground/<version> (needs Node 22), over ./gradlew build joustHostSpec and the JVM dev host; never a copy from the project

Both joust commands answer new, version and help themselves, and both hand project commands to the project’s own @julclang/joust. So joust build does the same, whichever binary PATH finds. Install the native one globally and @julclang/joust per project (both global at once is not supported: with Homebrew’s Node they share one path).

The walk up to a project does not enter directories owned by another user (a planted package.json in /tmp is ignored); list directories you trust, such as a container bind mount, in JOUST_SAFE_DIRS (:-separated). Both CLIs apply this rule, as git’s safe.directory does: in a container or CI job that runs as another user than the one owning the checkout (for example root over a mounted workspace), run as its owner, or set JOUST_SAFE_DIRS. Its entries are absolute paths and trust those exact directories, not their subdirectories: JOUST_SAFE_DIRS=/workspace works for joust build run in /workspace; run from /workspace/contracts, list that directory too. Otherwise joust build reports that it found no project.

To check a downloaded archive before using it: shasum -a 256 -c joust-<version>-SHA256SUMS.txt --ignore-missing, then gh attestation verify joust-<version>-<platform>.zip -R bloxbean/joust; on macOS, xattr -d com.apple.quarantine joust (the binary is not notarised; Homebrew installs need none of this).

create-joust

Section titled “create-joust”

Writes a new project into dir (default joust-app), which must be empty or absent, and names the package after the folder. Every project has a Counter contract, joust.config.json for DevKit, an offline test (test/counter.test.js, run by npm test), the same calls on DevKit (test/devkit/counter.test.js) and .gitignore.

Option Values
--template, -t node (default): index.js, a Node script that deploys and calls the contract; scripts start, build, deploy, test. web: a page (page/) with the Cardano Foundation’s connect button and an in-page DevKit key, and vite.config.js; the scripts listed under A browser page
--lang, -l jsc (default): contracts/app/Counter.jsc in .jsc (a language preview), with its ABI manifest Counter.abi.json. java: contracts/app/Counter.java. Both give the same description and client
--help, -h the usage

Options go after -- with npm create (npm passes them on); npx create-joust my-app --lang java takes them directly.
